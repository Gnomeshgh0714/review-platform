## 三、存在问题与可优化点

### 3.1 问题一：平台入口级缺陷存活整个开发期，「完成」的定义过晚才校准

**问题描述**：`send_task_created` 从未实现——建任务即 500，平台入口级缺陷自立项起存在，直到 2026-10-12 补开发自测才暴露（#011）。同批发现的还有分配 500、并发撞号、自动转 SUBMITTED 死逻辑（AC-T-14 实测才命中——说明该用例写对了，但直到自测期才存在）。

**影响**：技术方案 8-06 定稿到 10-12 自测之间两个月，「可运行」从未被验证过。如果 10-12 不做集中自测，这批缺陷会直接流入评审轮 1，混在真实的评审发现里抬高返工成本。

**改进**：开发完成的定义从「代码写完」校准为「E2E 冒烟通过」；技术方案阶段的任务清单（T-00~T-56）应附带每任务的最小验收动作，task 完成即跑，不留到集中自测。

### 3.2 问题二：git 仓库初始化过晚，开发期无版本控制

**问题描述**：仓库 2026-10-21 才初始化（P2 修复批后建基线快照）。技术方案（8-06）、第一轮补开发（10-12）、P0/P1 修复批的历史只有决策日志文字记录，无代码 diff 可溯。评审轮 2 的「复核两批修复」实际靠的是日志描述而非 diff 逐行比对（轮 3 才补上）。

**影响**：修复的可追溯性打折；若中途工作区损坏，两个月工作无法恢复。

**改进**：git init 是项目第一步，不是「评审基线」才需要的东西。各批次提交粒度按本仓库 10-21 之后的实践执行即可（每批一提交、commit message 带决策编号与批名）。

### 3.3 问题三：敏感信息一度随代码入库

**问题描述**：LLM API Key 曾硬编码在 `ai_review.py` 并随代码入库，#011 才改为环境变量注入并提请轮换（仓库当时未公开，风险未外溢，但纪律上属于红线触碰）。

**改进**：密钥永不入代码——哪怕仓库是私有的。`.env.example` 占位 + 环境变量注入从第一行代码起执行。

### 3.4 问题四：前后端契约靠「事后对齐」而非「事前定义」

**问题描述**：#013 前端契约对齐批暴露的是大面积键名/枚举/端点不一致（task_number/discipline 不存在、MINOR_REVISE vs MINOR_REVISION）——前后端在同一份技术方案下各自实现，没有共享契约源，问题拖到 P1 批才修。

**改进**：以后端序列化器字段名为唯一契约源这一原则有效，但应前移：序列化器定稿后前端才开工，或直接由后端导出 schema/类型给前端消费。

### 3.5 问题五：36 个 `(1)` 后缀重复文件入库并推到公开仓库

**问题描述**：macOS 同步盘产物（`README(1).md`、`settings(1).py`、`PRD(1).md` 等 36 个）被 git 跟踪并已推送 GitHub——第一轮复盘 4.3 就记录过文件冗余问题，本轮不仅没解决，还随公开化放大了。

**改进**：`.gitignore` 增加 `*(1).*` 模式并 `git rm` 存量；这属于下一批的低成本清理项（记入遗留）。

### 3.6 问题六：测试补课滞后一个批次

**问题描述**：#015/#016 两批安全修复落地时，前端测试设施为零、相关链路只有手工浏览器验证，#017 才补课（前端 16 项 + E2E --frontend 路径）。401 刷新重放这类刚修完的逻辑，在修复与补课之间处于无回归保护状态。

**改进**：修复批与测试同批出，回归保护不留窗口——这正是 #017 之后「测试与断言同步纪律」的来源，纪律本身已固化，此问题不会复现，但代价已经付过一次。

### 3.7 问题七：增长运营专员三轮迭代零参与

growth/ 目录自 7-16 建立至今为空。定版后产品进入运营阶段（部署、演示、推广），该角色定义与产出的空缺将在下一阶段变成实际阻塞。

## 五、可沉淀技能（第 4 个）

### 5.4 技能四：多角色协作「开发-评审-定版」全周期工作流

**适用场景**：AI 多角色协作（或多人类团队）从 PRD 定稿到产品定版的落地执行全程；也适用于任何「生成式开发 + 对抗性评审」的软件项目收尾定版。

**核心流程**（本轮验证有效的最小闭环）：

```
开发自测闭环 → 评审轮 1（分级发现）→ 分级修复批（每批验证+备案）
→ 评审轮 2（对抗性复核）→ ……迭代直到评审收敛（致命/严重清零）
→ 全量清账（修复落地 + 暂缓/不采纳留痕理由）
→ 验收包三件套（清单/审核记录/AC映射表）→ 独立审核复现
→ 产品落签 → 语义裁决落地批（最小代码批+测试同步+全量回归）→ tag 定版
```

**八项机制**（§2.2 表格，为 skill 的核心资产）：评审与开发角色分离、蓝军对抗复核、分级分批清账、现状锁定观察点、测试同步纪律、独立审核复核、验收包三件套、裁决落地批。

**关键要点**：
- 评审只列问题不附方案，修复方案由开发侧独立设计——避免评审意见绑架实现
- 语义未定行为用测试断言现状（观察点），把「要不要改」变成显式裁决而非默认漂移
- 验收不由产出者自证：独立环境复现 + 留痕逐格比对
- 定版必须打 tag，后续所有批以 tag 为回归锚点
