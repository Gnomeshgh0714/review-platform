# PRD修改追踪技能（PRD Revision Tracking Skill）

> **技能名称**：prd-revision-tracking
> **适用角色**：产品设计专员
> **适用场景**：产品设计专员收到评审意见和总监终审修改指令后，对PRD进行修改并保留修改痕迹，确保修改可追溯、可验证、可复审。
> **技能来源**：第一轮迭代复盘（2026-07-16）§五.2 可沉淀技能
> **版本**：v1.0 | **创建日期**：2026-07-17

---

## 一、技能概述

本技能定义产品设计专员执行PRD修改时的标准化流程、痕迹保留规范、版本管理规则和完整性自检方法。

修改追踪的核心原则：
1. **保留原文是红线**：禁止删除历史记录，修改痕迹是可追溯性的基础
2. **每处修改必须标注编号**：便于复审专员逐项验证
3. **修改后需自检新问题**：防止修改引入新的逻辑矛盾或数据不一致
4. **不跳过复审直接定稿**：修改完成后必须提交复审

---

## 二、修改指令结构化解析方法

### 2.1 解析目标

收到总监终审决策后，首先将终审决策中的修改指令（必须修改+建议修改）解析为结构化清单，作为修改执行的依据。

### 2.2 解析步骤

```
1. 通读终审决策全文，识别所有修改指令
2. 将每项指令解析为以下结构化字段
3. 按优先级排序（必须修改在前，建议修改在后）
4. 形成修改指令清单表
5. 对照清单逐项执行修改
```

### 2.3 修改指令清单格式

| 编号 | 对应评审问题 | 修改类型 | 修改要求 | 完成标准 | 优先级 | 对应PRD位置 |
|------|------------|---------|---------|---------|--------|------------|
| M01 | Q1 状态机死锁 | 必须修改 | 补全REVIEWING→PENDING状态转换路径 | 状态机6状态完整，所有异常路径覆盖，无死锁/不可达 | 阻断 | §3.2 状态机定义 |
| M02 | Q2 跨模板对齐 | 必须修改 | 强制同一任务统一模板 | 任务创建时确定模板，分配审稿人时自动关联，消除跨模板对齐问题 | 阻断 | §4.1 表单模板 |
| ... | ... | ... | ... | ... | ... | ... |

### 2.4 字段说明

| 字段 | 说明 |
|------|------|
| 编号 | M01, M02, ...（按终审决策中的顺序编号） |
| 对应评审问题 | 关联评审意见中的问题编号（Q1, Q2, ...） |
| 修改类型 | 必须修改（阻断性）/ 建议修改（非阻断但强烈建议） |
| 修改要求 | 终审决策中明确的具体修改要求 |
| 完成标准 | 可验证的完成条件（复审专员据此验证） |
| 优先级 | 阻断（必须修改）/ 非阻断（建议修改） |
| 对应PRD位置 | 需修改的PRD章节+行号 |

### 2.5 解析注意事项

- **不得遗漏任何指令**：终审决策中的每项修改指令都必须解析到清单中
- **不得自行增减要求**：严格按照终审决策内容解析，不自行添加或省略
- **完成标准必须可验证**：每项的完成标准必须是复审专员可以客观验证的条件
- **有疑问及时反馈**：如对修改指令理解有歧义，及时向总监反馈确认，不自行解读

## 三、修改痕迹保留规范

### 3.1 痕迹保留原则

- **不删除原文**：原文内容保留，通过标记方式表明修改
- **修改可见**：每处修改都有明确的视觉标记
- **可追溯**：通过标记可定位到对应的修改指令编号

### 3.2 修改标注方法

#### 3.2.1 [Vx.x修改]标注块

对修改的内容，使用标注块标记修改起始和对应编号：

```markdown
<!-- [V1.1修改] M01：补全状态机REVIEWING→PENDING路径 -->
> **[V1.1修改 M01]** 状态机新增转换路径：REVIEWING → PENDING（审稿人提交意见后，如需补充可退回待处理状态）

修改后的状态定义：
...

<!-- [/V1.1修改] M01 -->
```

**标注块规则**：
- 起始标记：`<!-- [Vx.x修改] M编号 -->`
- 内容标记：`> **[Vx.x修改 M编号]** 修改说明`
- 结束标记：`<!-- [/Vx.x修改] M编号 -->`
- 每处修改必须标注对应修改指令编号

#### 3.2.2 删除线标记

删除的原文使用删除线保留：

```markdown
~~dimensionId（模板内唯一，用于跨模板维度对齐）~~
```

**规则**：
- 被删除的原文不物理删除，用`~~删除线~~`标记
- 删除线内容后可附简要说明删除原因：`~~原文~~ [V1.1修改 M02：改为强制统一模板，dimensionId模板内唯一即可]

#### 3.2.3 新增标记

新增内容使用明确标记：

```markdown
<!-- [V1.1新增] M05：新增User实体 -->

**User实体**（新增）

| 字段名 | 类型 | 说明 |
|--------|------|------|
| id | String | 用户唯一标识（主键） |
| name | String | 用户姓名 |
| roles | Array<String> | 用户角色数组（支持多角色） |
| ... | ... | ... |

<!-- [/V1.1新增] M05 -->
```

### 3.3 痕迹保留示例

修改前（V1.0原文）：
```markdown
### 3.2 状态机定义

审稿任务状态包括：PENDING（待处理）、REVIEWING（审稿中）、COMPLETED（已完成）、REJECTED（已拒绝）。

状态转换：
- PENDING → REVIEWING（分配审稿人）
- REVIEWING → COMPLETED（所有审稿人提交意见）
- REVIEWING → REJECTED（审稿人全部拒绝）
```

修改后（V1.1）：
```markdown
### 3.2 状态机定义

~~审稿任务状态包括：PENDING（待处理）、REVIEWING（审稿中）、COMPLETED（已完成）、REJECTED（已拒绝）。~~

<!-- [V1.1修改] M01：补全状态机路径，新增PENDING汇总状态 -->
> **[V1.1修改 M01]** 状态机新增PENDING_SUMMARY（待汇总）状态，补全REVIEWING→PENDING_SUMMARY路径，消除死锁

审稿任务状态包括：PENDING（待处理）、REVIEWING（审稿中）、~~COMPLETED（已完成）~~ PENDING_SUMMARY（待汇总）、COMPLETED（已完成）、REJECTED（已拒绝）。

状态转换：
- PENDING → REVIEWING（分配审稿人）
- REVIEWING → PENDING_SUMMARY（审稿人提交意见，进入待汇总）
- PENDING_SUMMARY → COMPLETED（汇总完成）
- REVIEWING → REJECTED（审稿人全部拒绝）

<!-- [/V1.1修改] M01 -->
```

## 五、修改完整性自检清单

### 5.1 自检流程

修改完成后，设计专员必须按以下清单逐项自检，确认每项修改指令已落实：

```
修改完整性自检清单

□ 1. 修改指令清单中每项指令是否都已执行？
   - 逐项核对，在清单中标注"已落实"或"未落实"
   - 未落实的需说明原因

□ 2. 每处修改是否标注了对应的修改项编号？
   - 检查每处[Vx.x修改]标注块是否包含M编号
   - 检查删除线内容是否附有修改说明

□ 3. 修改记录表是否完整？
   - 文档头部修改记录表是否覆盖所有修改项
   - 每项修改的版本、日期、摘要、编号是否齐全

□ 4. 版本号是否正确升级？
   - V1.0 → V1.1（评审修改）
   - 文档标题、头部版本号、文件名是否同步更新

□ 5. 修改是否引入新的逻辑矛盾？
   - 新增实体后，所有外键引用是否更新
   - 状态机修改后，是否重新绘制验证无死锁
   - 规则修改后，是否检查与其他规则的冲突

□ 6. 旧版本是否保留？
   - V1.0文件未被删除
   - V1.1为新文件，不覆盖V1.0

□ 7. 边界声明是否需要同步更新？
   - 如修改涉及功能边界调整（如退稿重审移P1），边界声明是否同步更新

□ 8. 验收标准是否需要同步更新？
   - 如修改涉及功能变化，验收标准是否同步更新
```

### 5.2 自检记录输出

自检完成后，输出自检记录：

```markdown
## 修改完整性自检记录

> 自检人：产品设计专员
> 自检日期：2026-07-16
> 自检版本：V1.0 → V1.1

### 修改指令落实情况

| 编号 | 修改要求 | 落实状态 | 落实位置 | 备注 |
|------|---------|---------|---------|------|
| M01 | 补全状态机REVIEWING→PENDING路径 | ✅ 已落实 | §3.2 L165-178 | 新增PENDING_SUMMARY状态 |
| M02 | 强制统一模板 | ✅ 已落实 | §4.1 L295-310 | 任务创建时确定模板 |
| M03 | 两阶段匿名化方案 | ✅ 已落实 | §6.3 L580-605 | — |
| M04 | 事务+行锁并发控制 | ✅ 已落实 | §3.5 L220-235 | — |
| M05 | 新增User实体+重命名 | ✅ 已落实 | §5.1 L450-480 | Reviewer→ReviewAssignment |
| ... | ... | ... | ... | ... |

### 新引入问题检查
- [x] 状态机重新绘制验证：无死锁、无不可达 ✅
- [x] 数据模型外键引用检查：新增User实体后所有引用已更新 ✅
- [x] 规则引擎冲突检查：无新增冲突 ✅
```

## 六、版本管理规则

### 6.1 版本号升级规则

| 修改场景 | 版本号升级规则 | 示例 |
|---------|--------------|------|
| 初版创建 | V1.0 | V1.0_审稿协作平台_PRD.md |
| 评审修改（终审后修改） | 小版本号+1 | V1.0 → V1.1 |
| 复审修改（复审发现问题后修改） | 小版本号+1 | V1.1 → V1.2 |
| 自主优化（非评审驱动的修改） | 小版本号+1 | V1.1 → V1.2 |
| 大范围重构（功能边界调整） | 大版本号+1 | V1.x → V2.0 |

### 6.2 文件命名规范

```
V{版本号}_{产品名}_PRD.md

示例：
V1.0_审稿协作平台_PRD.md    # 初版
V1.1_审稿协作平台_PRD.md    # 评审修改版
```

### 6.3 旧版本保留规则

- **旧版本保留不删除**：修改后创建新版本文件，旧版本文件保留在原位置
- **旧版本不修改**：旧版本文件内容不再修改，作为历史记录保留
- **版本间可追溯**：通过文档头部修改记录表可追溯版本间的变更

### 6.4 版本间关联

```markdown
# 审稿协作平台PRD V1.1

> **版本**：V1.1
> **基于版本**：V1.0
> **上一版本文件**：V1.0_审稿协作平台_PRD.md
> **修改依据**：总监终审决策_20260716.md（14项修改指令）
```

## 八、使用流程

```
1. 接收评审意见和总监终审决策
2. 修改指令结构化解析（§二）
   ├─ 通读终审决策
   ├─ 解析每项指令为清单
   └─ 形成修改指令清单表
3. 版本号升级（§六）
   ├─ 确定新版本号（V1.0→V1.1）
   ├─ 创建新版本文件（不覆盖旧版本）
   └─ 文档头部添加版本关联信息
4. 逐项执行修改（§三、§四）
   ├─ 按修改指令清单逐项修改
   ├─ 每处修改使用[Vx.x修改]标注块
   ├─ 删除内容用删除线保留
   ├─ 新增内容用新增标记
   └─ 文档头部更新修改记录表
5. 修改完整性自检（§五）
   ├─ 逐项核对修改指令落实情况
   ├─ 检查修改标注编号完整性
   ├─ 检查修改记录表完整性
   ├─ 检查版本号正确性
   ├─ 检查是否引入新问题
   └─ 输出自检记录
6. 提交复审
   ├─ 提交修改后PRD + 自检记录
   └─ 不跳过复审直接定稿
```

## 九、注意事项

1. **修改指令有歧义时及时反馈**：不自行解读终审决策，有疑问向总监确认
2. **修改范围严格限定在指令内**：不自行扩大修改范围，不在修改中夹带个人优化
3. **保留原文是红线**：任何情况下都不删除原文，修改痕迹是可追溯性的基础
4. **修改后自检不是可选步骤**：自检是防止修改引入新问题的最后一道防线
5. **轻微问题主动记录**：自检中发现的轻微问题主动记录为遗留问题，不隐瞒
6. **提交复审时附自检记录**：自检记录帮助复审专员快速定位验证重点
