# 总监终审裁决技能（Director Final Review Skill）

> **技能名称**：director-final-review
> **适用角色**：产品总监
> **适用场景**：产品总监对评审意见和PRD做最终裁决，决定通过/打回/有条件修改后通过；复审通过后执行二次终审定稿。
> **技能来源**：第一轮迭代复盘（2026-07-16）§五.3 可沉淀技能
> **版本**：v1.0 | **创建日期**：2026-07-17

---

## 一、技能概述

本技能定义产品总监执行终审裁决和二次终审的标准化流程、裁决方法、决策记录规范和修改产出要求。

终审裁决的核心原则：
1. **终审不干预专业细节**：仅做方向裁决和方案取舍，不替代设计专员做具体设计
2. **每项裁决必须有明确理由**：采纳/部分采纳/不采纳均需记录理由
3. **必须修改项的完成标准必须明确、可验证**：复审专员据此验证
4. **终审结论必须明确**：通过/打回/有条件通过，不留模糊空间
5. **关键决策必须写入决策日志**：全程留痕，可追溯

---

## 二、逐项裁决方法

### 2.1 裁决对象

对评审意见中的**每条问题**做独立裁决，不跳过任何一条。

### 2.2 裁决选项

| 裁决选项 | 含义 | 适用场景 |
|---------|------|---------|
| 采纳 | 认同评审意见，要求设计专员按评审方向修改 | 评审意见准确，问题确实存在，需修改 |
| 部分采纳 | 认同问题存在，但修改方式调整 | 问题存在但评审建议的修改方向需调整（如修改范围扩大/缩小、改为延后处理） |
| 不采纳 | 不认同评审意见，不要求修改 | 评审意见不准确（误报）、问题已在其他修改中覆盖、或按当前边界不需要处理 |

### 2.3 裁决记录格式

每项裁决必须记录以下内容：

```markdown
### 裁决项 M01：状态机死锁（对应评审Q1）

- **对应评审问题**：Q1（严重）
- **裁决结果**：采纳
- **裁决理由**：状态机REVIEWING→PENDING路径缺失确实存在死锁，属阻断性问题，必须在P0修复
- **修改指令**：补全REVIEWING→PENDING汇总状态路径，确保状态机6状态完整
- **修改类型**：必须修改（阻断性）
- **完成标准**：状态机6状态完整，所有异常路径覆盖，无死锁/不可达路径
- **对应PRD位置**：§3.2 状态机定义
```

### 2.4 裁决流程

```
1. 逐条阅读评审意见
2. 对每条问题做独立裁决：
   ├─ 判断问题是否确实存在
   ├─ 判断是否需在当前阶段修复
   ├─ 确定修改方式（采纳评审方向/调整方向/延后处理/不处理）
   ├─ 明确完成标准（可验证）
   └─ 记录裁决理由
3. 汇总所有裁决，形成修改指令清单
4. 对涉及方案取舍的决策记录为关键决策（§四）
5. 给出终审结论
```

### 2.5 裁决注意事项

- **不跳过任何评审问题**：即使是不采纳的问题，也必须记录裁决结果和理由
- **裁决理由必须具体**：不可仅写"同意"或"不同意"，必须说明判断依据
- **完成标准必须可验证**：复审专员能据此客观判断是否达标
- **部分采纳需说明调整内容**：明确说明在评审建议基础上做了哪些调整及原因

## 三、修改指令分类标准

### 3.1 分类定义

| 类别 | 定义 | 阻断性 | 处理要求 |
|------|------|--------|---------|
| 必须修改 | 阻断性问题，如不修复将导致技术设计无法落地或上线后事故 | 阻断 | 本轮必须完成，复审必须验证通过 |
| 建议修改 | 非阻断但强烈建议修改，如不修复会在特定场景下产生问题 | 非阻断 | 本轮建议完成，如时间紧迫可延后但必须记录处理计划 |

### 3.2 分类判定标准

**必须修改（阻断性）的判定条件**（满足任一）：
- 问题导致核心流程无法运行（如状态机死锁）
- 问题导致数据不一致或数据丢失风险（如并发竞态）
- 问题涉及安全漏洞（如匿名化失效）
- 问题导致数据模型不完整（如基础实体缺失）
- 问题导致PRD自身逻辑矛盾（如跨模板对齐错误）

**建议修改（非阻断）的判定条件**：
- 问题在特定场景下产生不便但不影响核心流程（如冷启动无兜底）
- 问题属优化项，不修复不影响系统正确性（如分配效率优化）
- 问题涉及体验优化，可延后处理（如信息展示优化）
- 问题涉及边界扩展，建议移至后续阶段（如退稿重审移P1）

### 3.3 修改指令清单格式

| 编号 | 对应问题 | 裁决 | 修改指令 | 修改类型 | 完成标准 | 对应PRD位置 |
|------|---------|------|---------|---------|---------|------------|
| M01 | Q1状态机死锁 | 采纳 | 补全状态机路径 | 必须修改 | 状态机完整无死锁 | §3.2 |
| M02 | Q2跨模板对齐 | 采纳 | 强制统一模板 | 必须修改 | 任务创建时确定模板 | §4.1 |
| M08 | Q8退稿重审越界 | 部分采纳 | 退稿重审移至P1，P0仅预留字段 | 必须修改 | P0不含退稿重审流程，预留round字段 | §3.2, §5.2 |
| M10 | Q10分配效率 | 采纳 | 标签匹配排序 | 建议修改 | 审稿人按标签匹配度排序 | §4.3 |
| ... | ... | ... | ... | ... | ... | ... |

### 3.4 分类统计

终审决策中必须包含修改指令分类统计：

```
修改指令统计：
- 必须修改：7项（M01-M07）
- 建议修改：7项（M08-M14）
- 合计：14项
```

## 四、关键决策记录格式

### 4.1 关键决策定义

涉及**方案取舍**的决策（而非简单的问题修复）需记录为关键决策。典型场景：
- 功能边界调整（如将某功能从P0移至P1）
- 技术方案选型（如并发控制选择事务+行锁而非分布式锁）
- 架构决策（如新增实体、重命名实体）
- 范围裁剪（如移除某子功能以保持P0聚焦）

### 4.2 关键决策记录格式

每项关键决策记录以下内容：

```markdown
### 关键决策 KD-01：退稿重审移至P1

- **决策背景**：评审Q8指出PRD中包含退稿重审流程，但退稿重审未在P0边界声明中，属功能越界。退稿重审涉及复杂的状态回退和重新分配逻辑，复杂度超出L1验收目标。
- **决策内容**：退稿重审功能从P0移至P1。P0仅在ReviewOpinion和SummaryReport实体中预留round字段，状态机标注P1预留转换路径。
- **决策理由**：
  1. P0聚焦核心流程验证（审稿任务管理→表单→汇总→知识库），退稿重审非核心流程
  2. 退稿重审复杂度高（状态回退+重新分配+意见保留），实现成本大
  3. 移至P1不影响P0核心功能验证，降低L1验收风险
- **影响范围**：§3.2状态机（标注P1预留）、§5.2 ReviewOpinion（预留round字段）、§5.4 SummaryReport（预留round字段）
- **写入决策日志**：是（决策日志 #005）
```

### 4.3 关键决策记录要素

| 要素 | 说明 |
|------|------|
| 决策背景 | 为什么需要做这个决策（问题的来龙去脉） |
| 决策内容 | 具体决定了什么 |
| 决策理由 | 为什么这样决定（可列多条理由） |
| 影响范围 | 该决策影响PRD的哪些章节 |
| 写入决策日志 | 是否写入决策日志及对应编号 |

### 4.4 决策日志写入规范

关键决策必须同步写入团队决策日志（`team-rules/决策日志.md`），格式如下：

```markdown
| 编号 | 日期 | 决策类型 | 决策摘要 | 决策理由 |
|------|------|---------|---------|---------|
| #005 | 2026-07-16 | 方案裁决 | PRD V1.0终审有条件通过，7项必须修改 | 评审发现5项严重问题+7项中等问题，需修改后复审 |
| #008 | 2026-07-16 | 方案裁决 | PRD V1.1定稿通过，进入技术设计阶段 | 14项修改全部落实，4项专项检查通过，无阻断性新问题 |
```

## 六、二次终审检查清单

### 6.1 二次终审触发条件

评审专员复审通过后，产品总监执行二次终审，做最终定稿决策。

### 6.2 二次终审检查清单

```
二次终审检查清单

□ 1. 修改落实检查
   - 逐项确认修改指令清单中每项是否落实
   - 对照复审意见中的逐项验证结果
   - 确认必须修改项全部落实（阻断性项不可遗漏）

□ 2. 新引入问题检查
   - 查看复审意见中是否发现修改引入的新问题
   - 如有新问题，判断是否阻断性
   - 阻断性新问题：打回修改
   - 非阻断性新问题：记录为遗留问题，指明处理时机

□ 3. 验收标准达成检查
   - 对照L1/L2验收标准逐项确认
   - PRD格式规范、逻辑自洽、无明显低级错误
   - 评审攻防机制有效（严重问题已发现并修复）
   - 分歧已按规则解决

□ 4. 4项专项检查结果确认
   - 状态机完整性检查：通过/未通过
   - 数据模型一致性检查：通过/未通过
   - 规则引擎一致性检查：通过/未通过
   - 边界声明一致性检查：通过/未通过

□ 5. 遗留问题确认
   - 遗留问题是否已记录
   - 遗留问题是否指明了处理时机和处理计划
   - 遗留问题是否非阻断（阻断性问题不可留为遗留）

□ 6. 终审结论
   - 通过定稿 / 打回修改 / 需补充修改后通过
   - 如通过，明确下一阶段（如进入技术设计阶段）
```

### 7.5 关键经验

1. **逐项裁决确保无遗漏**：12条评审问题全部裁决，形成14项修改指令（部分问题拆分为多项指令）
2. **必须/建议各半平衡效率与质量**：7必须+7建议，既保证阻断性问题修复，又不过度增加修改负担
3. **关键决策记录是方案取舍的依据**：5项关键决策（退稿重审移P1、统一模板、事务+行锁、精简NLG、重命名实体）均有明确的背景-内容-理由记录
4. **二次终审不只是签字**：二次终审检查修改落实+新引入问题+验收标准，2个轻微问题在二次终审中被确认并记录为遗留问题
5. **遗留问题指明处理时机**：N-01和N-02明确指明"技术设计阶段处理"，不留模糊空间

## 八、使用流程

```
【第一次终审】
1. 接收评审意见和PRD
2. 逐条阅读评审意见
3. 逐项裁决（§二）
   ├─ 对每条问题做采纳/部分采纳/不采纳裁决
   ├─ 记录裁决理由
   ├─ 明确修改指令和完成标准
   └─ 分类为必须修改/建议修改（§三）
4. 识别关键决策并记录（§四）
   ├─ 涉及方案取舍的决策记录背景-内容-理由
   └─ 同步写入决策日志
5. 明确修改产出要求（§五）
6. 给出终审结论（通过/打回/有条件通过）
7. 输出终审决策文档

【修改阶段】（由设计专员执行，使用prd-revision-tracking技能）

【复审阶段】（由评审专员执行，使用prd-reverse-review技能）

【二次终审】
8. 接收复审意见和修改后PRD
9. 执行二次终审检查清单（§六）
   ├─ 修改落实检查
   ├─ 新引入问题检查
   ├─ 验收标准达成检查
   ├─ 4项专项检查结果确认
   ├─ 遗留问题确认
   └─ 终审结论
10. 输出二次终审文档
11. 如通过，写入决策日志，明确下一阶段
```

---

## 九、注意事项

1. **终审不干预专业细节**：总监做方向裁决和方案取舍，不替代设计专员做具体设计，不替代评审专员做技术验证
2. **不采纳也需记录理由**：不采纳的评审问题必须记录不采纳理由，不可静默忽略
3. **部分采纳需说明调整**：部分采纳时必须明确说明在评审建议基础上做了哪些调整及原因
4. **完成标准是复审的依据**：必须修改项的完成标准必须明确、可验证，复审专员据此验证
5. **轻微非阻断问题可留待后续**：但必须记录并指明处理时机，不可遗漏
6. **终审结论不留模糊空间**：通过/打回/有条件通过三选一，不用"基本通过""大致可以"等模糊表述
7. **关键决策必须写入决策日志**：决策日志是全程留痕的核心，关键决策不同步写入日志视为流程违规
