# PRD反向评审技能（PRD Reverse Review Skill）

> **技能名称**：prd-reverse-review
> **适用角色**：产品评审专员
> **适用场景**：对PRD（含初版和修改版）进行反向评审，发现逻辑漏洞、边界遗漏、数据一致性问题、安全风险和边界合规问题；修改完成后执行复审验证。
> **技能来源**：第一轮迭代复盘（2026-07-16）§五.1 可沉淀技能
> **版本**：v1.0 | **创建日期**：2026-07-17

---

## 一、技能概述

本技能定义产品评审专员对PRD进行反向评审的标准化流程、检查清单、输出格式和复审规范。评审专员的职责定位为**"只提问题，不给方案"**——发现问题、定位位置、分析场景、评估风险，但不越权直接修改PRD或给出具体实现方案，具体修改由设计专员执行、总监裁决。

反向评审的核心原则：
1. **禁止无原则通过**：必须提出实质性反对意见，不得走过场式评审
2. **每条问题指明具体位置**：章节+行号，便于设计专员定位和复审验证
3. **不得越权修改**：仅提出问题方向，不修改PRD原文
4. **场景化验证**：对每个疑似问题构建极端场景验证PRD覆盖度

## 二、评审5维度检查清单

### 2.1 逻辑维度（Logic）

检查PRD自身逻辑是否自洽、是否有死循环或不可达路径。

| 检查项 | 检查方法 | 典型问题模式 |
|--------|---------|-------------|
| 状态机完整性 | 绘制状态转换图，验证每个状态是否有出口、是否存在死锁/不可达路径 | 状态机死锁（如REVIEWING状态无回退到PENDING的路径） |
| 跨实体引用自洽性 | 检查外键引用是否指向已定义实体，跨实体字段语义是否一致 | dimensionId声明"模板内唯一"却用于跨模板对齐，逻辑矛盾 |
| 规则引擎一致性 | 检查规则之间是否存在冲突、是否存在永不触发的死规则 | 规则触发条件逻辑上不可能满足；多规则匹配时无优先级机制 |
| 流程闭环性 | 检查所有流程的起点和终点是否明确，异常分支是否有归宿 | 异常处理后无后续状态转换 |
| 数据模型完整性 | 检查PRD引用的所有实体类型是否在数据模型中定义 | User实体缺失（用户系统基础实体遗漏） |

### 2.2 边界维度（Boundary）

检查PRD是否处理了异常场景、并发场景、极端数据等边界情况。

| 检查项 | 检查方法 | 典型问题模式 |
|--------|---------|-------------|
| 异常场景覆盖 | 逐一列出每个功能的异常场景，验证是否有处理逻辑 | 审稿人超时/拒绝/中途退出无处理 |
| 并发数据一致性 | 检查多用户同时操作时是否有数据一致性策略 | 并发分配审稿人时产生竞态条件，无锁机制 |
| 数量边界 | 检查最小/最大值是否定义，边界值行为是否明确 | 最少审稿人数未定义；重试次数无上限（无限重试） |
| 功能越界 | 检查PRD实际实现是否超出P0边界声明 | P0边界未含"退稿重审"但PRD中包含退稿重审流程 |
| 边界声明一致性 | 检查文档头部边界声明与各功能章节实际内容是否一致 | 声明P0不含某功能，但功能描述中隐含了该功能 |

### 2.3 场景维度（Scenario）

构建极端场景验证PRD覆盖度，详见§三"场景化问题分析方法"。

| 检查项 | 检查方法 | 典型问题模式 |
|--------|---------|-------------|
| 极端角色组合 | 构建特殊用户角色组合场景 | 同一用户既是编辑又是审稿人，PRD未定义角色切换逻辑 |
| 极端状态组合 | 构建多个审稿人不同状态的组合场景 | 3审稿人中1接受1拒绝1超时，PRD未定义此组合的处理 |
| 冷启动场景 | 检查系统初始无数据时的行为 | 审稿知识库为空时终审建议规则引擎无匹配，无兜底逻辑 |
| 跨阶段场景 | 检查跨流程阶段的数据传递 | 审稿意见汇总阶段引用了表单中不存在的字段 |

### 2.4 风险维度（Risk）

检查安全风险、技术风险、体验风险。

| 检查项 | 检查方法 | 典型问题模式 |
|--------|---------|-------------|
| 匿名化/双盲安全 | 检查双盲审稿场景下作者身份是否可能泄露 | 文件元数据泄露作者信息，匿名化方案不充分 |
| 权限控制 | 检查各角色的操作权限是否定义且无越权 | 审稿人可查看其他审稿人意见（应双盲） |
| 数据泄露风险 | 检查日志、缓存、文件传输中是否可能泄露敏感信息 | 文件下载时含作者元数据 |
| 技术可行性 | 检查PRD要求的技术方案是否有实现风险 | 复杂自然语言生成功能超出P0实现能力 |

### 2.5 体验维度（Experience）

检查用户体验设计是否充分。

| 检查项 | 检查方法 | 典型问题模式 |
|--------|---------|-------------|
| 操作反馈 | 检查关键操作是否有明确反馈 | 审稿意见提交后无确认，用户不知道是否成功 |
| 错误提示 | 检查错误场景是否有友好提示 | 系统异常时仅显示技术错误码 |
| 信息展示完整性 | 检查关键信息是否完整展示 | 审稿意见汇总未展示意见分布信息，无法判断分歧程度 |
| 冷启动体验 | 检查无数据状态的用户体验 | 空白页面无引导 |

## 三、场景化问题分析方法

### 3.1 方法说明

对每个疑似问题，不直接下结论，而是构建一个**具体、极端的场景**，验证PRD的定义是否覆盖该场景。如果PRD未覆盖，则确认为问题。

### 3.2 场景构建步骤

1. **识别变量**：从PRD中提取影响该问题的关键变量（如审稿人数量、审稿意见类型、状态组合）
2. **构建极端组合**：将变量取极端值或特殊组合
3. **推演流程**：按PRD定义的流程逐步推演该场景下的系统行为
4. **判断覆盖度**：如果推演到某一步PRD无定义（流程中断、状态无出口、规则无匹配），则确认为问题

### 3.3 场景构建示例

| 问题类型 | 场景示例 | 验证目标 |
|---------|---------|---------|
| 状态机死锁 | 审稿人A提交意见后想修改，但状态已从REVIEWING变为PENDING汇总，REVIEWING→PENDING无回退路径 | PRD状态机是否覆盖"已提交意见后修改"场景 |
| 跨模板对齐错误 | 审稿人A用模板1（含"方法论"维度），审稿人B用模板2（无"方法论"维度），汇总时如何对齐dimensionId | PRD跨模板维度对齐逻辑是否自洽 |
| 并发竞态 | 3位审稿人同时接受分配，但任务仅需2位，无锁机制导致3位都被分配 | PRD是否定义并发控制策略 |
| 规则冲突 | 审稿意见为1接收+1大修+1拒稿，Rule-4触发条件（接收/大修/拒稿均有）同时Rule-7（接收与拒稿对立）也触发 | PRD规则引擎是否有优先级机制 |
| 冷启动 | 系统首次使用，审稿知识库为空，终审建议规则引擎无匹配数据 | PRD是否定义兜底场景 |

### 3.4 场景化分析输出要求

每个场景化分析必须包含：
- **场景描述**：具体的角色、数据、状态组合
- **推演过程**：按PRD流程逐步推演
- **覆盖判断**：PRD是否覆盖该场景（覆盖/未覆盖/部分覆盖）
- **风险说明**：如未覆盖，该场景实际发生时的后果

### 4.2 字段说明

| 字段 | 说明 |
|------|------|
| 问题编号 | Q1, Q2, ...（按发现顺序编号） |
| 级别 | 严重（阻断性）/ 中等（需修改但非阻断）/ 轻微（可延后处理） |
| 类别 | 逻辑 / 边界 / 场景 / 风险 / 体验 |
| PRD位置 | 章节号 + 行号（如 §3.2 L156），必须精确到行 |
| 问题描述 | 客观描述问题本身，**不含改进建议** |

### 4.3 级别判定标准

| 级别 | 判定标准 |
|------|---------|
| 严重 | 阻断性问题，如不修复将导致技术设计无法落地或上线后安全/稳定性事故（如状态机死锁、数据模型缺失基础实体、安全漏洞） |
| 中等 | 需修改但非阻断，如不修复会在特定场景下产生问题但不影响核心流程（如规则冲突、冷启动无兜底） |
| 轻微 | 可延后处理，不影响系统正确性，属优化项（如信息展示不够友好） |

> **重要**：评审专员按角色定义**"只提问题，不给方案"**。问题描述中不得包含具体改进建议或实现方案，仅描述问题本身、场景分析和风险。改进方案由设计专员提出、总监裁决。

## 五、复审4项专项检查

PRD修改后复审时，除逐项验证修改落实外，必须执行以下4项专项检查，确保修改未引入新问题：

### 5.1 状态机完整性检查

| 检查步骤 | 具体操作 |
|---------|---------|
| ① 重绘状态转换图 | 基于修改后的PRD重新绘制状态机图 |
| ② 验证所有状态有出口 | 每个状态至少有一个出边（终态除外） |
| ③ 验证无死锁 | 不存在只能进入无法离开的状态 |
| ④ 验证无不可达 | 不存在从初始状态无法到达的状态 |
| ⑤ 验证异常路径覆盖 | 所有异常场景（超时、拒绝、错误）都有对应的状态转换 |

### 5.2 数据模型一致性检查

| 检查步骤 | 具体操作 |
|---------|---------|
| ① 实体完整性 | PRD引用的所有实体类型都在数据模型中定义 |
| ② 外键有效性 | 所有外键引用指向已定义实体的主键 |
| ③ 字段语义一致 | 同一字段在不同实体中语义一致（如userId在所有实体中含义相同） |
| ④ 新增实体检查 | 修改后新增的实体是否被所有应引用它的位置正确引用（如新增User实体后，Reviewer等实体的userId是否更新为引用User.id） |
| ⑤ 命名无歧义 | 实体命名是否清晰，无一词多义（如Reviewer既是角色又是记录→需重命名） |

### 5.3 规则引擎一致性检查

| 检查步骤 | 具体操作 |
|---------|---------|
| ① 规则无冲突 | 检查规则之间是否存在触发条件重叠且结论矛盾 |
| ② 无死规则 | 检查是否有规则因触发条件逻辑上不可能满足而永远不会被触发 |
| ③ 优先级机制 | 多规则匹配时有明确的优先级排序机制 |
| ④ 兜底场景 | 所有审稿意见组合都有规则匹配或兜底处理 |
| ⑤ 规则覆盖完整性 | 检查所有可能的意见类型组合是否被规则覆盖 |

### 5.4 边界声明一致性检查

| 检查步骤 | 具体操作 |
|---------|---------|
| ① 头部声明 vs 功能章节 | 文档头部P0/P1/P2边界声明与各功能章节实际内容一致 |
| ② 无隐含越界 | 功能描述中不隐含超出当前边界范围的功能 |
| ③ 预留字段标注 | 为P1/P2预留的字段/状态有明确标注（如"P1预留"） |
| ④ 验收标准对齐 | 验收标准覆盖范围与边界声明一致 |

## 六、红线规则

以下规则为评审专员的不可逾越红线：

| 序号 | 红线规则 | 说明 |
|------|---------|------|
| R1 | **至少3条有效问题** | 每次评审必须提出至少3条实质性有效问题，否则视为评审未尽责。少于3条需在评审意见中说明PRD质量已达高标准的依据 |
| R2 | **只提问题不给方案** | 评审专员角色定位为发现问题，不越权给出改进方案。问题描述中不得包含"建议改为..."等具体方案，仅描述问题本身和风险 |
| R3 | **禁止无原则通过** | 评审结论不得为无条件"通过"。即使PRD质量高，也必须经过完整的5维度检查流程，确认无严重问题后方可给出"通过"结论，且须说明检查依据 |
| R4 | **每条问题精确到行号** | PRD位置必须精确到章节+行号，禁止仅写章节名或"某处"等模糊位置 |
| R5 | **不得修改PRD原文** | 评审专员不得直接修改PRD文件，仅产出评审意见文档 |

## 七、本轮实战参考

> 以下数据来自第一轮迭代（2026-07-16）实际评审实践，供后续迭代参考校准。

### 7.1 问题分布

| 维度 | 问题数 | 占比 | 典型问题 |
|------|--------|------|---------|
| 逻辑 | 5 | 42% | Q1状态机死锁、Q2跨模板对齐错误、Q4并发竞态、Q5 User实体缺失、Q6规则冲突 |
| 边界 | 3 | 25% | Q8退稿重审越界、Q9无限重试、Q10分配效率边界 |
| 场景 | 2 | 17% | Q7冷启动无兜底、Q12分歧标注场景未覆盖 |
| 风险 | 1 | 8% | Q3匿名化安全风险 |
| 体验 | 1 | 8% | Q11双盲文件展示 |
| **合计** | **12** | **100%** | — |

**级别分布**：严重5条（42%）、中等7条（58%，含2条轻微并入中等项）

### 7.2 发现方法分布

| 发现方法 | 问题数 | 对应问题 |
|---------|--------|---------|
| 逐章精读+状态机图绘制 | 3 | Q1状态机死锁、Q5 User实体缺失、Q6规则冲突 |
| 跨章节对照检查 | 2 | Q2跨模板对齐错误、Q4并发竞态 |
| 安全维度专项检查 | 2 | Q3匿名化风险、Q11双盲文件 |
| 场景化极端场景构建 | 3 | Q7冷启动、Q8退稿重审越界、Q9无限重试 |
| 边界声明对照 | 1 | Q10分配效率边界 |
| 体验维度检查 | 1 | Q12分歧标注 |

### 7.3 关键经验

1. **状态机图绘制是最有效的方法**：3条严重问题中2条通过绘制状态机图发现
2. **跨章节对照是发现数据一致性问题的关键**：单看某一章节无法发现问题，必须跨章节比对
3. **场景化分析对边界问题最有效**：构建极端场景能发现静态阅读容易遗漏的边界问题
4. **严重问题占比42%远超L2标准的20%**：说明评审机制有效运转，评审攻防质量高
5. **5项严重问题全部为阻断性**：如未在评审阶段发现，将直接导致技术设计无法落地

### 7.4 复审实践

- 逐项验证14项修改落实，引用V1.1具体行号为依据
- 4项专项检查（状态机/数据模型/规则引擎/边界声明）全部通过
- 发现2个轻微非阻断问题（Rule-4死规则、attemptCount语义模糊），记录为遗留问题留待技术设计阶段处理

## 八、使用流程

```
1. 接收PRD（含版本号）和用研报告
2. 逐章精读PRD全文
3. 对照用研报告痛点映射，检查覆盖度
4. 按5维度检查清单逐项检查
   ├─ 逻辑维度：绘制状态机图、检查跨实体引用、检查规则引擎
   ├─ 边界维度：列举异常场景、检查并发策略、检查边界声明一致性
   ├─ 场景维度：构建极端场景验证覆盖度
   ├─ 风险维度：检查匿名化/权限/双盲/数据泄露
   └─ 体验维度：检查操作反馈/错误提示/信息展示
5. 对每个疑似问题执行场景化分析（§三）
6. 按4.1格式输出评审意见文档
7. 给出评审结论（通过/需修改/需重大修改）
8. [如需修改] 修改完成后执行复审：
   ├─ 逐项验证修改落实（引用修改后行号）
   ├─ 执行4项专项检查（§五）
   └─ 检查是否引入新问题
9. 输出复审意见，给出复审结论
```

---

## 九、注意事项

1. **评审不等于否决**：评审目的是发现问题提升质量，不是否定设计专员的工作。问题措辞应客观、对事不对人
2. **严重问题需充分论证**：标记为"严重"的问题必须有场景分析支撑，不可主观臆断
3. **轻微问题也需记录**：不因问题轻微就不记录，轻微问题可能积累或与其他问题叠加放大
4. **复审不只是验证修改**：复审除验证修改落实外，必须执行4项专项检查，防止修改引入新问题
5. **遗留问题必须记录处理时机**：非阻断问题留待后续处理时，必须明确记录"在哪个阶段处理"，不可遗漏
