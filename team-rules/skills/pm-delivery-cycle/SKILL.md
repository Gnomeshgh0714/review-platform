# PM 交付周期：开发-评审-定版全流程

从 PRD/技术方案定稿到产品定版打 tag 的落地执行工作流。适用多角色协作（多 agent 或人机混合）的软件项目；单项机制也可拆用（如只做评审轮、只做验收定版）。

**在技能矩阵中的位置**：与 PRD 阶段技能（prd-reverse-review / prd-revision-tracking / director-final-review，覆盖需求→定稿）前后衔接，本技能覆盖其后全部：开发→评审→清账→验收→定版。与 ai-tool-* 三条职责线互补不重叠（研究线 eval-report、运营线 ops-blueprint、推广线 enablement-guide）。

## 全周期流程

```
PRD/技术方案定稿
    ↓
① 开发自测闭环 ──────── 完成的定义 = E2E 冒烟通过（不是代码写完）
    ↓
② 评审轮 1 ─────────── 分级发现（致命/严重/一般/建议），只列问题不附方案
    ↓
③ 分级修复批 ────────── P0→P1→P2 逐批出，每批：修复+测试同步+独立验证+决策日志备案
    ↓
④ 对抗性复核（蓝军）── 问「能否绕过」，通道级扫描
    ↓ ……循环②-④，直到收敛：致命/严重清零且发现量级递减
⑤ 全量清账 ─────────── 修复落地 + 暂缓/不采纳留痕理由，评审周期闭环
    ↓
⑥ 验收包三件套 ─────── 定版清单（签核）+ 审核记录（独立复现）+ AC 映射表（免测依据）
    ↓
⑦ 产品落签 ─────────── 待裁决语义项逐项给结论（维持/变更）
    ↓
⑧ 裁决落地批 ────────── 最小代码批 + 测试同步改名改断言 + 全量回归
    ↓
⑨ tag 定版 ─────────── 后续所有批以 tag 为回归锚点
```

## 八项核心机制

| 机制 | 做法 | 为什么 |
|------|------|--------|
| 评审与开发角色分离 | 评审按角色准则「只列问题、不附解决方案」执行，修复方案由开发侧独立设计 | 防止评审意见绑架实现；问题定位与方案设计解耦 |
| 蓝军对抗复核 | 修复批完成后不直接采信，下一轮评审先问「这个修复能否绕过」，再做通道级扫描（同类入口/枚举两端/口径/保留字/影响面/修复间互踩） | 修复本身可能引入旁路或互踩，逐条读 diff 才算复核 |
| 分级分批清账 | 按致命→严重→一般→建议分级出批，每批独立验证、独立决策备案，不混批 | 批次小才可独立验证回滚；严重度决定节奏 |
| 现状锁定观察点 | 语义待裁决的行为，用测试**断言现状**（注释标「现状锁定，非缺陷判定」），把「要不要改」变成显式裁决 | 避免语义在评审-修复循环中默默漂移；裁决变更时测试断言同步改有据可依 |
| 测试同步纪律 | 修复导致行为/文案变更时，测试必须同批改名改断言 | 「修代码不修测试」会让测试基线变成假保护 |
| 独立审核复核 | 验收材料不由产出者自证：独立环境复现测试基线、留痕逐格比对、口径误差照实修正并回写 | 定版签核需要「不经作者之手也成立」的事实底座 |
| 验收包三件套 | 定版清单（勾选签核）+ 审核记录（事实核验）+ AC 映射表（PRD 验收标准×测试用例对照） | 让验收方免重测签核：自动覆盖项信任基线，人工项明确列出 |
| 裁决落地批 | 语义裁决→最小代码批（不动架构）→测试同步→全量回归→打 tag，当日闭环 | 裁决不能停在文档上；落地批是「定版语义完整」的最后一步 |

## 阶段执行要点

**① 开发自测闭环**
- git init 是项目第一步；每批一提交，commit message 带批名与决策编号
- 密钥永不入代码（环境变量注入 + .env.example 占位），仓库私有也一样
- 前后端契约先定源（如「后端序列化器字段名为唯一契约源」），序列化器定稿前端才开工
- 每个任务的完成定义附带最小验收动作（至少能跑通的用例/E2E），不留到集中自测

**② 评审轮**
- 发现分级四档：致命 / 严重 / 一般 / 建议；每条含位置（文件:行）、问题描述、场景分析、严重度理由
- 原始发现全量留档（附录 JSON/表格），报告只做核实后的收敛视图
- 每条标注核实状态（✓核实成立 / ◐抽查属实），未核实的不进结论

**③ 分级修复批**
- 批内闭环：修复 → 测试同步 → 全量回归（后端/前端/构建/E2E 四组数字）→ 环境还原 → 决策日志备案
- 备案必含：执行内容（对 diff）、验证记录、遗留问题、待确认项、生效时间

**⑥⑦ 验收定版**
- AC 映射表逐条对照 PRD 验收标准：自动（免测）/ 部分（核心有测+缺口）/ 人工（走查），统计占比
- 审核记录复现测试基线 + 抽查口径（数字与代码/留痕/实测三方一致）
- 清单签核项：基线认可 / 清账闭环认可 / 低危处置认可 / 遗留项裁决（维持 or 变更）/ 定版结论

**⑧⑨ 裁决落地与 tag**
- 落地批只做语义变更，不改架构与数据模型；对应观察点测试改名改断言
- 全量回归通过才打 tag；tag message 记录评审收敛轨迹与测试基线

## 红线与反模式

- **红线**：密钥入库；修代码不修测试；验收材料自证（无独立审核）；清账不留痕（暂缓/不采纳必须记录理由）
- **反模式**（真实教训）：
  - 「可运行」拖到集中自测才验证——入口级缺陷可存活数月，修复成本翻倍
  - git 仓库到评审期才建——前期工作无 diff 可溯，复核只能靠日志文字
  - 契约靠事后对齐——前后端各写各的，返工一批才能对上
  - 测试滞后于修复批——刚修完的逻辑处于无回归保护窗口

## 产出物骨架

评审报告、决策日志执行批条目、验收清单三件套、观察点测试注释、裁决落地批提交等骨架见 [template.md](template.md)。

## 留痕规范

- 评审报告与验收材料归 `review/`，命名 `V{版本}_{类型}_{YYYYMMDD}.md`
- 每批执行记录进决策日志，编号递增，格式见 template.md
- 复盘报告归 `retrospective/`，对照上轮设定的验收标准逐项核验
