## 二、总体评价

**P0/P1 修复本体经对抗复核全部成立**：6 个维度共 122 项 checked_ok——V1.1 的致命项（账号接管、roles 自报提权、双盲 API 失效、决策不落库、归档链路缺失、匿名化键名穿透、task_opinions IDOR、force_summarize 契约、意见提交载荷）在各自修复点均未被直接攻破；P1 的 19 项字段对齐经穷举式契约复核未发现新的键位错位；state_logs 审稿人脱敏、模板快照冻结、并发提交 AC-T-14、规则引擎 Rule-1~7 优先级等均有独立确认。

但本轮发现表明修复是「**点防御**」而非「**通道防御**」，存在三类结构性缺口：

1. **两条致命链断在轮 1 已报未修的通道上**：审稿人提交 UI 调用不存在的 `formApi.submit`（P1 批对齐了载荷键名却漏改方法名，轮1#4 残留）；任务 PATCH 通道未收口（轮1#15）与 `ai_review` 的绝对路径直开组合成任意服务端文件读取链，同一 PATCH 还击穿 P0 新增的双盲序列化裁剪与发布门控。
2. **姊妹通道绕过**：force_summarize 按 AC-T-11 补全三要素，但 `handle_overdue(action=summarize)` 走同一状态转换、零校验，0 份意见的任务可被推入无出边的 SUBMITTED 永久死局；回退待分配不清退分配与意见、round 恒为 1，旧轮数据污染新一轮。
3. **访问权不随生命周期收敛**：文件下载/任务可见性的「被分配审稿人」判定不看 assignment_status——未接受（INVITED）、已拒绝（REJECTED）、已过期/被标记（EXPIRED）的审稿人永久保留稿件全文下载权与元数据窥探权。

另需记录：E2E 冒烟 22/22 通过的同时，前端审稿人提交主流程 100% 失效——E2E 只驱动 HTTP 接口、不经过前端构建产物，对前端 JS 运行时错误（如方法名不存在）是盲区，「E2E 通过」不能作为前端可用性证据。

## 五、结论

1. **P0/P1 修复本体成立，但未形成通道级闭环**。122 项 checked_ok 确认修复点本身无一处被直接攻破；新发现的问题几乎全部是「姊妹入口未按同一标准收口」（#7/#8/#10）与「踩在轮 1 未修通道上的绕过」（#2/#9）。建议 P2 批次以通道为单位收口，而非以端点为单位。
2. **两项致命使主流程与机密性底线仍不成立**。建议 P2 第一优先级：ReviewTaskSerializer 的 manuscript_file/review_mode/publish_opinions_to_author 只读化 + ReviewTaskViewSet/TemplateViewSet 的 update/partial_update/destroy 收口（轮1#15/#16）——单项修复同时消灭致命#2、严重#9 并封堵文件路径关联旁路；第二优先级：formApi.submit 方法名修正（致命#1）与 401 拦截器重置 Pinia store（严重#11）；第三优先级：handle_overdue 对齐 force_summarize 三要素、assignment_status 纳入授权判定、rollback 轮次隔离。
3. **生命周期与隔离语义缺失是本轮新暴露的系统性主题**：assignment_status 不参与任何授权判定、回退无轮次隔离、归档失败无补救入口、删文件不看任务引用。建议裁决时将其列为与「逐项修 bug」并列的设计补课项。
4. **测试体系三个盲区**：知识库/forms 端点零 API 测试、通知矩阵零断言（E2E 声称覆盖但实际未调用）、前端零测试设施。86 项后端测试全绿的状态下，本轮 63 条中约三分之一位于无测试路径上；且 E2E 不经过前端构建产物，「22/22 通过」对前端运行时错误无检出能力（致命#1 即为例证）。
