## 1. 目标用户画像

本平台聚焦三类核心用户角色，每类角色在审稿协作链路中承担不同职责，具有差异化的需求特征和痛点。

### 1.1 审稿人（Reviewer）

| 维度 | 描述 |
|------|------|
| **典型特征** | 高校学者、博士/硕士研究生，以学术研究为主业，审稿为兼职工作。通常同时收到多本期刊审稿邀请，审稿时间碎片化（利用课题间隙、晚间、周末完成）。对学术规范有认知但未必系统，审稿水平参差不齐。多数审稿人靠"师徒传承"和个人摸索积累审稿经验，缺乏系统培训。 |
| **核心需求** | ① 高效完成审稿任务，减少重复性操作（如反复下载稿件、手动填写多个表单）；② 有结构化的审稿框架引导，降低"不知道从何评起"的认知负担；③ 能快速参考历史审稿案例和模板，提升审稿质量和效率；④ 清晰了解审稿任务的截止时间和优先级，避免遗漏；⑤ 审稿意见提交后能看到编辑部反馈，形成闭环。 |
| **使用频次** | 中高频。活跃审稿人每周接到1-3篇审稿任务，每篇审稿耗时2-6小时（分多次完成）。使用平台频次集中在接到任务后的1-2周内，呈脉冲式而非持续式。 |
| **当前痛点** | ① 审稿邀请通过邮件接收，任务散落在邮箱中，缺乏统一管理，容易遗漏截止日期；② 审稿意见往往以自由文本方式撰写，格式因人而异，缺乏结构化引导，新手审稿人尤其困扰；③ 审完一篇后经验无法沉淀，下次审类似论文仍要从头思考；④ 审稿意见提交后"石沉大海"，不知道编辑部是否采纳、作者如何回应；⑤ 多个期刊使用不同审稿系统，操作习惯无法迁移，学习成本高。 |

### 1.2 编辑部（Editor）

| 维度 | 描述 |
|------|------|
| **典型特征** | 期刊责任编辑、编委成员。负责稿件分配、审稿进度跟踪、多审稿人意见汇总对比、终审决策。通常一人管理多本期刊或一期多篇稿件，工作量大且时效性强。需要协调多位审稿人的排期，处理审稿人拒绝邀请、超时未返回等异常情况。 |
| **核心需求** | ① 高效匹配合适的审稿人，缩短任务分配周期；② 实时掌握所有在审稿件的进度状态，及时发现超时风险；③ 能快速对比多审稿人意见，自动标注分歧点，辅助终审决策；④ 统一审稿意见格式，便于横向对比和归档；⑤ 生成审稿决策报告，支撑终审结论可追溯。 |
| **使用频次** | 高频且持续。编辑工作贯穿稿件从投稿到录用的全生命周期，日均使用频次远高于审稿人。在稿件集中期（如专刊截稿后）工作量激增。 |
| **当前痛点** | ① 审稿人分配依赖个人经验和人脉，匹配效率低且容易找错人，审稿人拒邀率高导致反复分配；② 多审稿人意见汇总全靠手动整理，格式不统一导致对比困难，耗时耗力；③ 审稿进度不透明，需要逐一邮件催问审稿人，沟通成本极高；④ 审稿人意见分歧时缺乏结构化对比工具，难以快速定位分歧核心；⑤ 审稿过程数据分散，难以沉淀为可复用的审稿人画像和质量评估依据。 |

### 1.3 作者（Author）

| 维度 | 描述 |
|------|------|
| **典型特征** | 投稿人，以高校教师、研究生为主。投稿后处于被动等待状态，对审稿进度高度焦虑。关注审稿结果和具体意见反馈，尤其是修改建议。可能同时投递多篇稿件到不同期刊，需要管理多个投稿状态。 |
| **核心需求** | ① 实时了解投稿稿件处于审稿的哪个阶段（初审/外审/返修/终审）；② 审稿结束后能及时获取结构化的审稿意见，明确修改方向；③ 返修时能逐条对照审稿意见进行修改和回应；④ 审稿周期过长时能获得预期反馈（是否超时、预计完成时间）。 |
| **使用频次** | 低频但高关注。投稿后密集查看状态（每日1-2次），收到审稿意见后集中使用（修改阶段）。单篇稿件的使用周期长（数月到一年以上），但日均使用频次低。 |
| **当前痛点** | ① 审稿进度完全不透明，投稿后"黑箱"等待，不知道稿件到了哪一步；② 审稿意见往往格式混乱、表述模糊，难以准确理解修改要求；③ 返修时缺少审稿意见与修改内容的逐条对照工具，容易遗漏修改点；④ 审稿周期不可预期，长时间无反馈时无法判断是否正常。 |

## 2. 核心痛点分析

基于用户画像和现有审稿流程调研，梳理出以下5个核心痛点。每个痛点均包含具体场景描述、影响范围和严重程度评估。

> **严重程度评级标准**：
> - **高**：直接阻断核心流程或导致重大效率损失，影响全部三类角色
> - **中**：显著降低协作效率或体验质量，影响两类角色
> - **低**：造成局部不便，影响单一角色且有变通方案

### 痛点 P1：任务分配效率低

| 维度 | 详情 |
|------|------|
| **痛点描述** | 编辑部分配审稿任务时，缺乏智能匹配工具，主要依赖编辑个人经验、人脉记忆和手动查找。审稿人信息散落在通讯录、往期审稿记录、学术数据库等多处，编辑需要逐一筛选、邮件邀请、等待回复，流程冗长且成功率不稳定。从稿件分配到审稿人确认接受，平均耗时3-7天。 |
| **具体场景** | 某经济学期刊收到一篇关于"数字经济与区域经济增长"的投稿。编辑需要找3位审稿人。编辑先从自己记忆中想到2位同行学者，发邮件邀请；其中1位拒绝（近期出差），编辑又去学术数据库搜索相关领域作者，找到3位候选，逐一发邮件；等待2天后仅1位回复确认，不得不再次寻找。整个过程耗时5天，期间稿件处于"待分配"状态，作者焦虑催问。 |
| **影响范围** | 编辑部（分配负担重）、审稿人（收到不匹配的邀请）、作者（等待周期拉长）——三类角色全受影响 |
| **严重程度** | **高** |

### 痛点 P2：审稿意见格式不统一

| 维度 | 详情 |
|------|------|
| **痛点描述** | 现有审稿系统中，审稿人提交的意见多为自由文本（free-text），各期刊虽有审稿指引但缺乏强约束的结构化表单。不同审稿人对同一稿件的评审维度、详略程度、评分标准理解差异巨大，导致编辑部收到的审稿意见五花八门——有的仅一段总评，有的分点详述，有的只给分数无文字说明。 |
| **具体场景** | 某期刊一篇稿件收到3位审稿人的意见。审稿人A提交了200字总体评价+总体推荐意见（"小修"），未分维度评分；审稿人B按"研究意义/创新性/方法/写作"四个维度各写了一段，每维度给了1-5分，但未写总体推荐意见；审稿人C只写了一条"建议拒稿"和3条修改意见，无评分无维度划分。编辑收到后无法直接横向对比，需要花1-2小时重新整理归纳三份意见，才能形成决策依据。 |
| **影响范围** | 审稿人（缺乏审稿引导，新手尤其困难）、编辑部（汇总整理负担重）——两类角色受影响 |
| **严重程度** | **高** |

### 痛点 P3：多审稿人意见难以汇总对比

| 维度 | 详情 |
|------|------|
| **痛点描述** | 一篇稿件通常由2-4位审稿人评审，各审稿人独立提交意见。编辑部需要手动阅读、提取关键信息、对比分歧点、综合判断。现有系统仅提供意见的原文展示，无自动汇总、分歧标注、可视化对比功能。当审稿人意见严重分歧时，编辑需要逐字研读多份长文意见，耗费大量时间且容易遗漏关键信息。 |
| **具体场景** | 某稿件3位审稿人意见分歧明显：审稿人A建议"接收"（认为方法创新），审稿人B建议"大修"（认为数据有缺陷），审稿人C建议"拒稿"（认为研究问题不重要）。三份意见合计4000余字。编辑需要手动提取每位审稿人在"方法""创新性""研究意义"等维度上的具体评价，对比分歧所在，再结合自己判断做终审决策。整个汇总对比过程耗时约2-3小时，且高度依赖编辑个人经验，存在主观偏差风险。 |
| **影响范围** | 编辑部（汇总对比负担最重）、作者（间接影响，决策延迟导致返修周期拉长）——两类角色受影响 |
| **严重程度** | **高** |

### 痛点 P4：审稿经验难以复用积累

| 维度 | 详情 |
|------|------|
| **痛点描述** | 审稿人在完成审稿后，审稿意见通常随稿件归档，审稿过程中的思考框架、评价标准、常见问题清单等经验性内容无法独立沉淀和复用。审稿人每审一篇新论文几乎从零开始，无法借鉴自己或他人的历史审稿经验。编辑部层面，历史审稿数据也未能结构化存储和检索，无法用于审稿人能力评估或审稿模板沉淀。 |
| **具体场景** | 某博士研究生首次被导师推荐审稿，研究领域是"教育经济学"。他从未审过稿，不知道审稿意见应该写什么、怎么评。导师口头指导了几句，但缺乏可参考的审稿模板或历史审稿案例。他只能去网上搜索"审稿意见怎么写"，找到的资料泛泛且不适用于经济学领域。最终花了6小时才完成审稿，且意见质量不高（过于简略，缺乏方法层面的深入分析）。如果有一份该领域的历史审稿意见模板可供参考，审稿时间可缩短至2-3小时，且意见质量更有保障。 |
| **影响范围** | 审稿人（尤其是新手审稿人，经验无法积累复用）、编辑部（无法利用历史数据优化分配和模板）——两类角色受影响 |
| **严重程度** | **中** |

### 痛点 P5：审稿进度不透明

| 维度 | 详情 |
|------|------|
| **痛点描述** | 现有审稿流程中，稿件状态更新滞后且颗粒度粗。作者只能看到"Under Review"等笼统状态，无法知道具体处于分配审稿人、审稿中、意见汇总、终审决策哪个环节。编辑部对审稿人的审稿进度也缺乏实时可见性，通常需要邮件催问才知道审稿人是否已经开始、进行到哪一步。进度不透明导致多方焦虑和反复沟通。 |
| **具体场景** | 某作者投稿后2个月，系统状态仍显示"Under Review"，无任何更新。作者不知道稿件是否已分配审稿人、审稿人是否已开始审稿、预计何时出结果。作者不敢频繁催问编辑部（怕留下不好印象），但内心焦虑。编辑部这边，3位审稿人中1位已提交意见、1位超期未交、1位刚接受邀请尚未开始，但这些信息作者完全看不到。编辑部需要逐个邮件催促超期审稿人，审稿人可能遗忘或低估优先级。 |
| **影响范围** | 作者（焦虑、反复催问）、编辑部（催促沟通成本高）、审稿人（被频繁邮件催促打扰）——三类角色全受影响 |
| **严重程度** | **高** |

### 痛点汇总矩阵

| 痛点编号 | 痛点名称 | 严重程度 | 影响角色 | 对应P0功能 |
|---------|---------|---------|---------|-----------|
| P1 | 任务分配效率低 | 高 | 审稿人、编辑部、作者 | 审稿任务管理 |

## 3. 竞品分析

对三个主流学术审稿平台进行系统分析，提取对本产品的设计启发。

### 3.1 ScholarOne (Manuscript Central)

| 维度 | 详情 |
|------|------|
| **平台简介** | Clarivate Analytics 旗下产品，全球使用最广泛的学术期刊投稿审稿系统之一。服务于数万家期刊，覆盖理工、医学、社科等全学科领域。 |
| **核心功能** | ① 稿件投递与在线提交系统；② 审稿人推荐与自动匹配（基于关键词和学术领域）；③ 审稿任务分配与进度追踪；④ 审稿意见在线提交（含结构化评分表单）；⑤ 编辑决策工作流（接收/修改/拒稿）；⑥ 稿件全生命周期管理（投稿到发表）。 |
| **优势** | ① 功能全面，覆盖投稿-审稿-决策全流程，适合大型期刊集群使用；② 审稿人数据库庞大，支持基于关键词的自动匹配推荐；③ 与 Web of Science 深度整合，审稿人学术信息丰富；④ 经过长期迭代，工作流成熟稳定，被大量期刊作为标准工具使用。 |
| **不足** | ① 界面设计陈旧复杂，学习成本高，新用户（尤其是审稿人和作者）经常抱怨操作困难；② 审稿表单虽有结构化字段，但灵活性差，不同期刊配置差异大，审稿人跨期刊审稿时体验割裂；③ 审稿意见汇总仅做原文罗列，无自动对比或分歧标注功能，编辑仍需手动整理；④ 无审稿知识库功能，历史审稿意见不可检索复用；⑤ 系统封闭，不支持与外部工具集成，数据导出困难；⑥ 审稿进度对作者极度不透明，仅有笼统状态码。 |
| **对本产品的启发** | ① **简化交互设计**是核心差异化机会—— ScholarOne 的复杂界面是公认痛点，本产品应以"审稿人友好"为核心设计原则，降低操作门槛；② **审稿人匹配推荐**值得借鉴，但应结合领域知识库提升匹配精度；③ **结构化审稿表单**需兼顾标准化与灵活性，支持期刊自定义维度但保持统一的数据结构；④ **审稿意见汇总对比**和**审稿知识库**是 ScholarOne 的功能空白区，正是本产品的核心差异化价值所在。 |

### 3.2 Editorial Manager (EM)

| 维度 | 详情 |
|------|------|
| **平台简介** | Aries Systems 公司产品，与 ScholarOne 并列为两大主流投稿审稿系统。在医学、生物、化学等自然科学期刊领域占据主导地位。 |
| **核心功能** | ① 稿件投递与元数据管理（支持结构化元数据采集）；② 审稿人管理（含审稿人库、冲突利益声明、工作量统计）；③ 审稿任务分配（支持编辑手动分配 + 系统推荐）；④ 审稿表单配置（期刊可自定义审稿问题和评分维度）；⑤ 多轮审稿支持（初稿-返修-复审）；⑥ 审稿决策与通知自动化。 |
| **优势** | ① 审稿表单配置灵活，期刊可按需自定义审稿维度和问题，适应不同学科需求；② 审稿人管理功能完善，支持冲突利益声明、工作量统计、审稿质量评价等管理维度；③ 多轮审稿流程支持成熟，返修-复审链路完整；④ 系统稳定性高，被大量顶级期刊采用，流程经过验证。 |
| **不足** | ① 同样存在界面陈旧问题，操作流程冗长，用户体验差；② 审稿意见汇总功能仍以原文展示为主，缺乏智能对比和分歧标注；③ 无审稿知识库，审稿经验无法复用；④ 审稿人匹配主要基于关键词，精度有限，编辑仍需大量手动筛选；⑤ 系统高度封闭，API 能力弱，难以与第三方工具集成；⑥ 配置复杂，期刊上线 EM 需要专门培训和较长配置周期。 |
| **对本产品的启发** | ① **审稿表单的自定义能力**值得借鉴，但应在"配置灵活性"和"操作简洁性"之间找到平衡——EM 的配置太重，本产品应提供预设模板 + 轻量自定义；② **审稿人工作量统计**是有价值的管理功能，可在后续迭代（P1审稿人能力画像）中参考；③ **多轮审稿支持**是真实需求，本产品在任务管理中应预留返修-复审的流程扩展能力；④ **审稿意见智能汇总**和**知识库**同样是 EM 的功能空白，确认了本产品的差异化方向。 |

### 3.3 OpenReview

| 维度 | 详情 |
|------|------|
| **平台简介** | 开放式同行评审平台，由 MIT/康奈尔团队开发维护。最初服务于 ICLR、NeurIPS 等机器学习顶会，近年来逐步向更多会议和期刊扩展。核心理念是"开放审稿"——审稿意见和讨论过程公开可见。 |
| **核心功能** | ① 开放式审稿（审稿意见公开，支持审稿人-作者公开讨论）；② 审稿任务管理（含审稿人分配、截止日期追踪、进度看板）；③ 审稿意见结构化提交（含评分维度和文字意见）；④ 多轮讨论机制（审稿人-作者-Rebuttal 公开交互）；⑤ 审稿意见公开归档与检索。 |
| **优势** | ① 审稿过程透明度高，作者和公众可见审稿意见和讨论过程，解决了"进度不透明"痛点；② 审稿意见公开归档，天然形成了一种"审稿知识库"，可供后来者检索参考；③ 界面相对现代，操作流程比 ScholarOne/EM 简洁；④ 开放架构，支持 API 调用，生态扩展性好。 |
| **不足** | ① 开放审稿模式**不适合所有学科和场景**——许多期刊要求双盲审稿，审稿意见不能公开，OpenReview 的核心优势不适用；② 审稿意见虽有结构化字段，但维度较固定，缺乏期刊级自定义能力；③ 审稿意见汇总对比功能仍然缺失，编辑需手动整理多审稿人意见；④ 审稿知识库非主动设计，仅是公开归档的副产品，无结构化检索、模板复用等主动功能；⑤ 偏会议场景，对期刊的投稿-返修-多轮审稿流程支持不够完善。 |
| **对本产品的启发** | ① **审稿进度透明化**是核心趋势——本产品应在保护双盲的前提下，向作者提供更细粒度的状态追踪（分配中/审稿中/汇总中/决策中）；② **审稿意见归档检索**理念值得吸收，但应升级为主动的、结构化的审稿知识库（而非 OpenReview 的被动公开归档）；③ **审稿人-作者讨论机制**有价值，但需注意与 P2 禁令（不做社交功能）的边界——聚焦审稿意见的澄清交互而非通用社交；④ **开放 API 架构**值得借鉴，本产品应在设计时预留 API 接口，支持与学术工具生态集成。 |

### 竞品对比总结

| 能力维度 | ScholarOne | Editorial Manager | OpenReview | 本产品（目标） |
|---------|-----------|-------------------|------------|--------------|
| 审稿任务管理 | ✅ 成熟 | ✅ 成熟 | ⚠️ 基础 | ✅ 轻量高效 |
| 结构化审稿表单 | ⚠️ 固定 | ✅ 可配置 | ⚠️ 固定 | ✅ 模板+轻自定义 |
| 审稿意见汇总对比 | ❌ 缺失 | ❌ 缺失 | ❌ 缺失 | ✅ **核心差异化** |
| 审稿知识库 | ❌ 缺失 | ❌ 缺失 | ⚠️ 被动归档 | ✅ **核心差异化** |
| 审稿进度透明度 | ❌ 极低 | ❌ 极低 | ✅ 高（开放模式） | ✅ 中高（隐私保护下） |
| 用户体验 | ❌ 差 | ❌ 差 | ⚠️ 一般 | ✅ 审稿人友好 |
| 生态开放性 | ❌ 封闭 | ❌ 封闭 | ✅ 开放 | ✅ 预留API |

**核心结论**：三大竞品在审稿任务管理和结构化表单上已有成熟方案，但在**审稿意见汇总对比**和**审稿知识库**两个方向上存在明显功能空白。本产品应将这两项作为核心差异化能力，同时在用户体验和进度透明度上形成显著优势。

## 4. P0功能需求优先级排序

### 4.1 排序方法

采用 **痛点严重度 × 用户频次 × 实现难度** 三维综合评估模型，对P0四项功能进行优先级排序。

#### 评估维度说明

| 维度 | 评分标准 | 分值 |
|------|---------|------|
| **痛点严重度** | 该功能对应的痛点对用户的影响程度（对应痛点P1-P5的严重程度评级） | 高=3 / 中=2 / 低=1 |
| **用户频次** | 该功能被用户使用的频率（越高越优先） | 高频=3 / 中频=2 / 低频=1 |
| **实现难度** | 该功能的技术实现复杂度（越低越优先，难度高则优先级适当降低） | 低=3 / 中=2 / 高=1 |

> **综合得分 = 痛点严重度 × 用户频次 × 实现难度**（满分27分，得分越高优先级越高）

### 4.2 逐项评估

#### 功能1：审稿任务管理（创建/分配/追踪审稿任务，支持多审稿人协作）

| 维度 | 评分 | 评分理由 |
|------|------|---------|
| 痛点严重度 | **3（高）** | 直接对应痛点P1（任务分配效率低，严重程度高）和P5（审稿进度不透明，严重程度高）。两个高频痛点均影响三类角色。 |
| 用户频次 | **3（高频）** | 审稿人和编辑部每次审稿/管理稿件必用，是平台的基础入口功能。编辑部日均使用，审稿人每篇稿件使用。 |
| 实现难度 | **3（低）** | 核心是任务CRUD + 状态机 + 分配逻辑，技术方案成熟（标准Web应用功能），无复杂算法依赖。 |
| **综合得分** | **27** | 3 × 3 × 3 = **27** |

#### 功能2：结构化审稿表单（按维度输出评分+意见）

| 维度 | 评分 | 评分理由 |
|------|------|---------|
| 痛点严重度 | **3（高）** | 直接对应痛点P2（审稿意见格式不统一，严重程度高），影响审稿人和编辑部两类核心角色，是审稿质量的基础保障。 |
| 用户频次 | **3（高频）** | 每篇稿件的每位审稿人必用，是审稿流程的核心操作环节。编辑部通过表单配置间接使用。 |
| 实现难度 | **2（中）** | 表单渲染和数据采集本身不难，但需支持维度模板配置、评分约束、多轮审稿表单复用等灵活需求，设计复杂度中等。 |
| **综合得分** | **18** | 3 × 3 × 2 = **18** |

#### 功能3：审稿意见汇总（多审稿人意见聚合、分歧标注、终审建议生成）

| 维度 | 评分 | 评分理由 |
|------|------|---------|
| 痛点严重度 | **3（高）** | 直接对应痛点P3（多审稿人意见难以汇总对比，严重程度高），是编辑部最核心的效率瓶颈，直接影响终审决策质量和速度。 |
| 用户频次 | **2（中频）** | 每篇稿件汇总环节使用1次（所有审稿人提交后触发），编辑部使用频次低于任务管理。但每次使用价值密度高。 |
| 实现难度 | **1（高）** | 多审稿人意见的自动聚合、维度对齐、分歧标注涉及文本分析和结构化对比逻辑；终审建议生成需要规则引擎或AI辅助。技术复杂度在四项功能中最高。 |
| **综合得分** | **6** | 3 × 2 × 1 = **6** |

#### 功能4：审稿知识库（历史审稿意见检索、审稿模板复用）

| 维度 | 评分 | 评分理由 |
|------|------|---------|
| 痛点严重度 | **2（中）** | 直接对应痛点P4（审稿经验难以复用积累，严重程度中），影响审稿人（尤其新手）和编辑部。重要但不紧急——知识库需要先有数据积累才能发挥价值。 |
| 用户频次 | **2（中频）** | 审稿人在撰写审稿意见时参考历史案例和模板，频次与审稿任务挂钩但非每次必用。编辑部检索历史审稿数据频次更低。 |
| 实现难度 | **1（高）** | 需要全文检索、标签分类、模板管理、权限控制等功能，且依赖前三项功能产生的数据积累。在P0阶段数据量有限，功能价值难以充分体现。 |
| **综合得分** | **4** | 2 × 2 × 1 = **4** |

### 4.3 排序结果与逻辑

| 优先级排序 | P0功能 | 综合得分 | 痛点严重度 | 用户频次 | 实现难度 |
|-----------|--------|---------|-----------|---------|---------|
| **第1优先** | 审稿任务管理 | 27 | 高(3) | 高频(3) | 低(3) |
| **第2优先** | 结构化审稿表单 | 18 | 高(3) | 高频(3) | 中(2) |
| **第3优先** | 审稿意见汇总 | 6 | 高(3) | 中频(2) | 高(1) |
| **第4优先** | 审稿知识库 | 4 | 中(2) | 中频(2) | 高(1) |

### 4.4 排序逻辑说明

**第1优先：审稿任务管理（得分27，满分）**

排序逻辑：三项维度均得满分。审稿任务管理是整个平台的**基础设施和入口功能**——没有任务管理，审稿人无法进入审稿流程，编辑部无法分配和追踪，作者无法看到进度。它同时解决两个"高严重度"痛点（P1任务分配效率低 + P5进度不透明），影响全部三类角色。且技术实现最成熟，是标准的任务状态管理功能，可在最短时间内交付并验证核心流程。**必须最先完成，是后续三项功能的前提依赖。**

**第2优先：结构化审稿表单（得分18）**

排序逻辑：痛点严重度和用户频次均得高分，仅实现难度为中等。审稿表单是审稿人完成审稿的核心操作界面，直接决定审稿意见的质量和规范性。没有结构化表单，审稿意见汇总（第3优先）就失去了结构化数据基础——汇总功能依赖表单输出的标准化数据。因此表单必须先于汇总交付。实现难度评为中等而非高，是因为表单本质是配置化表单渲染+数据采集，技术方案成熟，灵活性需求可通过模板预设+轻量自定义控制复杂度。**是任务管理之后、汇总功能之前的必要中间层。**

**第3优先：审稿意见汇总（得分6）**

排序逻辑：痛点严重度最高（编辑部核心效率瓶颈），但用户频次为中等（每篇稿件汇总1次），实现难度最高（涉及意见聚合、分歧标注、终审建议生成等复杂逻辑）。排在第三的原因有二：① **数据依赖**——汇总功能需要审稿任务管理（分配了哪些审稿人）和结构化审稿表单（审稿人提交了结构化意见）两项功能先运行并产生数据，否则无内容可汇总；② **实现复杂度最高**——需要较长的设计和开发周期。但其价值密度极高（直接解决编辑部最痛的汇总对比问题），应在任务管理和表单交付后立即投入开发。**是本产品的核心差异化功能，虽排第三但战略价值最高。**

**第4优先：审稿知识库（得分4）**

排序逻辑：三项维度均非最高分。审稿知识库排在最后的核心原因是**数据冷启动问题**——知识库需要先有足够的历史审稿意见和模板积累才能发挥价值，而P0阶段是产品从零起步，前三项功能运行一段时间后才有数据可供知识库检索和复用。此外，痛点严重度为"中"（重要但不紧急），且实现难度为"高"（检索+分类+模板+权限）。但这不意味着知识库不重要——它是产品的长期竞争壁垒和差异化护城河，应在P0阶段完成基础架构设计，在后续迭代中持续丰富。**战略价值最高，但P0阶段应定位为基础架构搭建+最小可用版本。**

### 4.5 排序的依赖关系验证

上述排序也符合功能间的技术依赖链：

```
审稿任务管理（基础层）
    ↓ 产生任务数据
结构化审稿表单（采集层）
    ↓ 产生结构化审稿意见
审稿意见汇总（分析层）
    ↓ 产生汇总数据和决策记录
审稿知识库（沉淀层）
    ↓ 检索复用历史数据
```

四项功能构成**自底向上的数据流依赖链**，必须按此顺序交付才能确保每一层都有数据输入。逆序开发将导致上层功能无法验证（如先做汇总但没有审稿意见数据可汇总）。
