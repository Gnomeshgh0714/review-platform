| 痛点P3 | 用研报告§2 | 多审稿人意见难以汇总对比：2-4位审稿人意见汇总全靠手动阅读对比，耗时2-3小时，严重程度=高 |
| 痛点P4 | 用研报告§2 | 审稿经验难以复用积累：审稿意见随稿件归档，思考框架和评价标准无法独立沉淀复用，新手审稿耗时6小时+，严重程度=中 |
| 痛点P5 | 用研报告§2 | 审稿进度不透明：作者仅见"Under Review"笼统状态，编辑部需逐一邮件催问，严重程度=高 |
| 竞品分析 | 用研报告§3 | 三大竞品（ScholarOne、Editorial Manager、OpenReview）在审稿意见汇总对比和审稿知识库两个方向上存在明显功能空白，是本产品的核心差异化机会 |
| 优先级排序 | 用研报告§4 | 审稿任务管理(27分) > 结构化审稿表单(18分) > 审稿意见汇总(6分) > 审稿知识库(4分)，且构成自底向上的数据流依赖链 |

### 1.4 设计原则

基于用研报告竞品分析结论（§3），确立以下设计原则：

1. **审稿人友好**：以降低操作门槛为核心，避免ScholarOne/EM界面复杂、学习成本高的问题
2. **标准化+轻量自定义**：在统一数据结构基础上提供预设模板+轻量配置，避免EM配置过重
3. **隐私保护下的透明化**：在双盲审稿前提下向作者提供细粒度状态追踪，借鉴OpenReview的透明理念但不照搬开放模式
4. **自动化辅助**：通过结构化数据和规则引擎实现意见汇总、分歧标注、终审建议的自动化，填补竞品功能空白

### 1.5 边界声明

本PRD严格限定在P0范围内，以下功能**不在本文档范围内**（属于P1/P2）：

- ❌ 在线支付功能（P2禁令）
- ❌ 期刊管理系统（P2禁令）
- ❌ 用户社交功能（P2禁令）
- ❌ 审稿人能力画像与智能推荐（P1）
- ❌ 多轮审稿全流程支持，包括退稿重审（P1，P0仅在ReviewOpinion和SummaryReport中预留round字段，状态机中标注P1预留转换）
- ❌ 开放API与第三方集成（P1，P0仅预留接口设计）

> **[V1.1修改]** C-07：更新边界声明，明确退稿重审移至P1。P0阶段终审决策后流程结束，不支持回退。ReviewOpinion和SummaryReport实体中预留`round`字段（Integer，默认1），为P1多轮审稿预留数据结构扩展能力。状态机中"已决策→审稿中"转换标注为"P1预留转换，P0不实现"。

## 二、功能1：审稿任务管理（优先级1）

### 2.1 功能描述

**对应用研痛点**：P1（任务分配效率低）+ P5（审稿进度不透明）

**功能目标**：为编辑部提供高效的审稿任务创建、分配和追踪能力，同时为审稿人提供统一的任务管理入口，为作者提供细粒度的审稿进度可视化。通过标准化的任务状态机和自动化的进度推送，解决任务分配平均耗时3-7天（P1）和作者只能看到笼统状态（P5）的问题。

**核心价值**：
- 编辑部：减少任务分配中的反复沟通，实时掌握所有在审稿件进度，及时发现超时风险
- 审稿人：统一任务入口，不再散落在邮箱中，清晰的截止日期和优先级管理
- 作者：从"黑箱等待"变为"透明追踪"，减少焦虑和催问

### 2.2 用户故事

#### 审稿人视角
> **US-R-01**：作为一名审稿人，我希望在一个统一的任务列表中看到所有待处理的审稿任务，包括截止日期和优先级，这样我就不会遗漏任何任务或错过截止日期。

> **US-R-02**：作为一名审稿人，我希望收到审稿邀请后能一键接受或拒绝，而不需要回复邮件沟通，这样能更快地确认任务。

> **US-R-03**：作为一名审稿人，我希望在任务列表中看到距离截止日期的倒计时提醒，并在即将超期时收到系统通知，这样我能合理安排审稿时间。

> **US-R-04**：作为一名审稿人，我希望在提交审稿意见后能看到编辑部是否已查看以及最终决策结果，这样我就不会觉得意见"石沉大海"。

#### 编辑部视角
> **US-E-01**：作为一名编辑，我希望能在系统中快速创建审稿任务并关联稿件信息（标题、摘要、关键词、学科领域），而不需要在多个系统间切换。

> **US-E-02**：作为一名编辑，我希望能一次性为稿件分配1-N位审稿人并为每位设置截止日期，系统自动发送邀请通知，而不需要逐一发邮件。

> **US-E-03**：作为一名编辑，我希望在一个看板视图中看到所有在审稿件的状态（待分配/已分配/审稿中/已提交/已汇总/已决策），并能快速筛选出超时风险高的稿件。

> **US-E-04**：作为一名编辑，当审稿人拒绝邀请或超时未提交时，我希望系统能自动通知我并提供快速重新分配的操作入口，而不是等我手动发现。

> **US-E-05**：作为一名编辑，当所有审稿人提交意见后，我希望系统能自动提示我进入汇总环节，并一键跳转到汇总功能。

#### 作者视角
> **US-A-01**：作为一名作者，我希望投稿后能实时看到稿件处于审稿的哪个具体阶段（分配审稿人中/审稿人审稿中/意见汇总中/终审决策中），而不是只看到一个笼统的"Under Review"。

> **US-A-02**：作为一名作者，当审稿周期过长时，我希望系统能提供预计完成时间或当前阶段说明，这样我就不必焦虑地猜测或冒昧催问编辑。

> **US-A-03**：作为一名作者，当审稿结束后，我希望能在系统中直接查看结构化的审稿意见和终审决策结果，而不是等待邮件通知。

### 2.3 功能拆解

#### 2.3.1 任务创建

**功能说明**：编辑部在系统中创建审稿任务，关联稿件元数据信息，作为审稿流程的起点。

**操作主体**：编辑部

**创建字段**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 稿件标题 | 文本 | 是 | 论文完整标题 |
| 摘要 | 长文本 | 是 | 论文摘要（用于审稿人初步了解） |
| 关键词 | 标签数组 | 是 | 学科关键词，3-10个，用于审稿人匹配参考 |
| 学科领域 | 枚举 | 是 | 一级学科分类（如：经济学、计算机科学、生物学等） |
| 稿件类型 | 枚举 | 是 | 研究论文/综述/案例研究/短文等 |
| 稿件文件 | 文件上传 | 是 | PDF格式，≤20MB |
| 审稿模式 | 枚举 | 是 | 单盲/双盲（影响审稿人是否可见作者信息） |
| 期望审稿人数量 | 整数 | 是 | 期望分配的审稿人数量，默认3，范围1-5 |
| 截止日期 | 日期 | 是 | 期望完成审稿的日期，不得早于当前日期+7天 |
| 附加说明 | 长文本 | 否 | 编辑部对审稿人的特殊要求说明 |
| 作者用户ID | 用户引用 | 是 | 关联作者User实体，建立作者与稿件的关联关系 |

> **[V1.1修改]** C-05：新增"作者用户ID"字段（必填），关联User实体的authorUserId，解决作者与审稿任务的关联关系缺失问题。原文中"审稿模板"字段调整：任务创建时必须确定审稿模板（必填），如未指定则使用学科默认模板并自动关联，分配审稿人时自动关联同一模板。

> **[V1.1修改]** C-02：原"审稿模板"字段由"可选"改为"必填"。任务创建时强制确定模板（未指定则使用学科默认模板），分配审稿人时自动关联同一模板，从根源上消除跨模板对齐问题。

**业务规则**：
- 任务创建后自动进入"待分配"状态
- 系统自动生成唯一任务编号（格式：RT-YYYYMMDD-NNNN）
- 稿件文件上传后系统自动校验PDF格式和文件大小
- 双盲模式下，稿件文件中的作者信息由编辑部负责隐去，需按匿名化检查清单逐项确认（详见§2.6边界条件"双盲稿件匿名化检查"）

> **[V1.1修改]** S-04：双盲模式下稿件文件匿名化新增检查清单和系统校验机制，详见§2.6边界条件表。

#### 2.3.2 任务分配

**功能说明**：编辑部分配审稿任务给1-N位审稿人，设置每位审稿人的截止日期，系统自动发送邀请通知。

**操作主体**：编辑部

**分配方式**：
- **手动分配**：编辑从系统审稿人库中搜索和选择审稿人
- **批量分配**：一次选择多位审稿人，分别设置截止日期

> **[V1.1修改]** S-03：新增轻量标签匹配排序。编辑搜索审稿人时，系统基于稿件关键词与审稿人researchAreas（研究方向标签）的匹配度自动排序，降低编辑筛选成本。此为轻量标签匹配排序，非AI推荐。

**分配字段**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 审稿人 | 用户引用 | 是 | 从审稿人库中选择，支持按姓名/学科/关键词搜索，搜索结果按标签匹配度排序 |
| 截止日期 | 日期 | 是 | 该审稿人的审稿截止日期 |
| 邀请说明 | 文本 | 否 | 编辑部对该审稿人的个性化说明 |
| 邀请有效期 | 日期 | 是 | 审稿人接受/拒绝邀请的截止时间，默认3天 |

**业务规则**：
- 一篇稿件可分配1-5位审稿人
- 同一审稿人不可在同一稿件中被重复分配
- 分配后系统自动向审稿人发送邀请通知（站内消息+邮件）
- 审稿人在邀请有效期内未响应，系统自动通知编辑并标记为"邀请超时"
- 任务状态在首次成功分配后从"待分配"变更为"已分配"
- 审稿人接受邀请后，任务状态变更为"审稿中"（首个审稿人接受时触发）
- 编辑部可随时补充分配新的审稿人（在已分配状态下也可追加）

> **[V1.1修改]** C-02：分配审稿人时自动关联任务创建时确定的模板，确保同一任务的所有审稿人使用同一模板，不存在跨模板对齐场景。

> **[V1.1修改]** S-02：新增重试限制与超时升级机制。拒邀重试次数上限为3次，超过后标记该稿件为"分配困难"并通知主编。超时（审稿超时或邀请超时）48小时内编辑未处理时，系统自动通知主编介入。重新分配新审稿人的截止日期从重新分配时起算，至少7天后。

#### 2.3.3 任务追踪（状态机）

**功能说明**：通过标准化状态机管理审稿任务的全生命周期，所有状态变更可追溯。

**状态机定义**：

```
┌──────────────┐
│   待分配      │ ← 任务创建后初始状态
│ (PENDING)    │
└──────┬───────┘
       │ 编辑部分配审稿人
       ▼
┌──────────────┐
│   已分配      │ ← 审稿人已收到邀请，等待接受/拒绝
│ (ASSIGNED)   │
└──────┬───────┘
       │ 首位审稿人接受邀请
       ▼
┌──────────────┐
│   审稿中      │ ← 审稿人正在审稿，部分可能已提交
│ (REVIEWING)  │
└──────┬───────┘
       │ 全部审稿人提交意见 / 编辑强制提前汇总
       ▼
┌──────────────┐
│   已提交      │ ← 所有审稿意见已提交，等待汇总
│ (SUBMITTED)  │
└──────┬───────┘
       │ 编辑部触发汇总操作
       ▼
┌──────────────┐
│   已汇总      │ ← 汇总报告已生成，等待终审决策
│ (SUMMARIZED) │
└──────┬───────┘
       │ 编辑部录入终审决策
       ▼
┌──────────────┐
│   已决策      │ ← 终审决策已录入，P0流程结束
│ (DECIDED)    │
└──────────────┘
       │ P1预留转换：退稿重审（P0不实现）
       ▼ （虚线，P1实现）
┌──────────────┐
│   审稿中      │ ← [P1预留] 退稿重审时回退至此状态
│ (REVIEWING)  │
└──────────────┘
```

> **[V1.1修改]** C-01：新增REVIEWING→PENDING转换路径。在状态机定义图中，REVIEWING状态增加回退至PENDING的路径（全部已接受审稿人超时且无可提交意见时触发）。

> **[V1.1修改]** C-07：状态机图中"已决策→审稿中"转换标注为"P1预留转换，P0不实现"。P0阶段DECIDED为终态，不支持回退。

**状态流转规则**：

| 当前状态 | 目标状态 | 触发条件 | 操作者 |
|---------|---------|---------|--------|
| 待分配 | 已分配 | 编辑部成功分配至少1位审稿人 | 编辑部 |
| 已分配 | 审稿中 | 首位审稿人接受邀请 | 系统（自动） |
| 已分配 | 待分配 | 所有审稿人均拒绝邀请 | 系统（自动） |
| 审稿中 | 已提交 | 全部已接受的审稿人均提交意见 | 系统（自动） |
| 审稿中 | 已提交 | 编辑部强制提前汇总（至少1份意见已提交） | 编辑部 |
| 审稿中 | 待分配 | 全部已接受审稿人超时且无可提交意见 | 系统（自动） |
| 审稿中 | 待分配 | 部分已提交意见后其余全部超时，编辑选择"回退待分配，已提交意见保留为历史记录" | 编辑部 |
| 审稿中 | 已提交 | 部分已提交意见后其余全部超时，编辑选择"基于已提交意见强制汇总" | 编辑部 |
| 已提交 | 已汇总 | 编辑部触发汇总报告生成 | 编辑部 |
| 已汇总 | 已决策 | 编辑部录入终审决策 | 编辑部 |
| 已决策 | 审稿中 | ~~退稿重审（作者返修后重新审稿）~~ **[P1预留转换，P0不实现]** | ~~编辑部~~ |

> **[V1.1修改]** C-01：新增三条REVIEWING状态的异常出口转换规则：
> 1. `审稿中→待分配`：触发条件"全部已接受审稿人超时且无可提交意见"，系统自动执行
> 2. `审稿中→待分配`：触发条件"部分已提交意见后其余全部超时，编辑选择'回退待分配，已提交意见保留为历史记录'"，编辑部操作
> 3. `审稿中→已提交`：触发条件"部分已提交意见后其余全部超时，编辑选择'基于已提交意见强制汇总'"，编辑部操作
>
> **部分已提交后其余全部超时的处理**：当REVIEWING状态下部分审稿人已提交意见、其余全部超时且无可提交意见时，系统通知编辑并提供两种选择：
> - **选项A：基于已提交意见强制汇总**——任务推进至"已提交"状态，基于已提交的意见生成汇总报告，报告中注明"部分审稿人超时未提交"
> - **选项B：回退待分配**——任务回退至"待分配"状态，已提交的意见保留为历史记录（不删除），编辑重新分配审稿人

| 异常场景 | 处理方式 |

#### 2.3.4 进度可视化

**功能说明**：根据不同角色展示差异化的进度信息，在保护审稿隐私的前提下提供最大透明度。

**编辑部视图（全量信息）**：
- **稿件看板**：以看板形式展示所有稿件及其当前状态，支持按状态/学科/截止日期/超时风险筛选
- **稿件详情**：查看每个稿件下所有审稿人的状态（已邀请/已接受/已拒绝/审稿中/已提交/超时），含每位审稿人的截止日期和进度
- **超时预警**：高亮显示距离截止日期≤3天的审稿任务，红色标记已超时任务
- **统计概览**：显示当前在审稿件数、待分配稿件数、超时任务数等关键指标

**审稿人视图（个人任务）**：
- **任务列表**：展示所有分配给自己的审稿任务，含标题、截止日期、状态、倒计时
- **优先级排序**：按截止日期紧迫度自动排序，超时风险高的任务置顶高亮
- **截止提醒**：截止前7天/3天/1天分级提醒（站内消息+邮件）；截止当天红色高亮
- **任务详情**：点击任务进入审稿工作台，查看稿件、填写审稿表单（关联功能2）

**作者视图（稿件进度）**：
- **进度时间线**：以时间线形式展示稿件当前所处阶段及各阶段时间节点
- **细粒度状态**：展示具体阶段（分配审稿人中[N/M位已接受] -> 审稿人审稿中[N/M位已提交] -> 意见汇总中 -> 终审决策中）
- **预计时间**：根据截止日期显示预计完成时间
- **结果查看**：审稿完成后查看终审决策和审稿意见（经编辑部发布后可见）

### 2.6 边界条件（异常处理）

| 异常场景 | 触发条件 | 处理逻辑 | 通知对象 |
|---------|---------|---------|---------|
| **审稿人拒绝邀请** | 审稿人在邀请有效期内点击"拒绝" | 1. 标记该审稿人状态为"已拒绝"；2. 系统通知编辑部；3. 编辑部可重新分配新审稿人；4. 任务状态不变；5. 重试次数累计，超过3次标记"分配困难"并通知主编 | 编辑部（超3次时通知主编） |
| **邀请超时未响应** | 审稿人在邀请有效期（默认3天）内未接受也未拒绝 | 1. 标记该审稿人状态为"邀请超时"；2. 系统通知编辑部；3. 编辑部可重新分配或延期；4. 超时48小时编辑未处理时自动通知主编 | 编辑部（48小时未处理时通知主编） |
| **审稿超时未提交** | 审稿人接受邀请后未在截止日期前提交意见 | 1. 截止前7天/3天/1天系统自动发送提醒；2. 超时后标记"审稿超时"，通知编辑；3. 编辑可选择：基于已提交意见强制汇总/回退待分配（已提交意见保留为历史记录）/重新分配新审稿人（截止日期从重新分配时起算至少7天）；4. 超时48小时编辑未处理时自动通知主编 | 审稿人->编辑部->主编（48小时未处理时） |
| **全部审稿人拒绝或超时（无可提交意见）** | 稿件所有已分配审稿人均拒绝邀请或超时未响应，且无已提交意见 | 1. 任务自动回退至"待分配"状态；2. 系统通知编辑部并建议重新分配 | 编辑部 |
| **部分审稿人已提交后其余全部超时** | 部分审稿人已提交意见，其余全部超时 | 1. 系统通知编辑并提供选择：A.基于已提交意见强制汇总（任务推进至"已提交"，报告中注明"部分审稿人超时未提交"）；B.回退待分配（已提交意见保留为历史记录，编辑重新分配审稿人） | 编辑部 |
| **编辑部强制提前汇总** | 部分审稿人已提交但仍有未提交，编辑决定提前汇总 | 1. 需至少1份审稿意见已提交；2. 需填写提前汇总原因；3. 未提交的审稿人标记为"未提交-已汇总"；4. 任务状态推进至"已提交" | 未提交的审稿人 |
| **多审稿人并发提交** | 多位审稿人同时提交审稿意见 | 1. 采用数据库事务+行锁策略：每次审稿意见提交时，在数据库事务内存储意见并检查全部审稿人状态；2. 对ReviewTask记录加行锁，确保同一时间只有一个事务可检查和更新任务状态；3. 若全部已接受的审稿人均已提交，在同一事务内将任务状态从REVIEWING更新为SUBMITTED；4. 其他并发事务等待行锁释放后重新检查状态，避免状态判断错误 | 系统（自动处理） |
| **稿件文件格式错误** | 上传非PDF文件或文件超过20MB | 1. 上传时即时校验；2. 提示"仅支持PDF格式，文件不超过20MB"；3. 阻止上传 | 编辑部 |
| **截止日期设置不合理** | 截止日期早于当前日期+7天 | 1. 表单校验拦截；2. 提示"截止日期需至少在7天后" | 编辑部 |
| **并发操作冲突（编辑间）** | 两位编辑同时对同一任务进行操作 | 1. 采用乐观锁机制；2. 后提交者收到"任务已被他人更新"提示；3. 需刷新后重试 | 编辑部 |
| **双盲稿件匿名化检查** | 双盲模式下上传稿件文件 | 1. 编辑上传双盲稿件前需逐项确认匿名化检查清单；2. 系统自动检查PDF元数据中的作者字段，如有值则警告编辑；3. 检查清单包括：标题页已移除作者信息/页眉页脚已移除作者信息/PDF元数据作者字段已清除/致谢部分已移除或匿名化/基金资助信息已移除或匿名化/正文自引已改为第三人称表述 | 编辑部 |

> **[V1.1修改]** C-01：新增"部分审稿人已提交后其余全部超时"场景，明确编辑两种选择。

> **[V1.1修改]** C-04：新增"多审稿人并发提交"场景，明确数据库事务+行锁策略。

> **[V1.1修改]** S-02：审稿人拒绝邀请、邀请超时、审稿超时场景均新增重试次数上限3次和超时48小时自动通知主编机制。重新分配新审稿人截止日期从重新分配时起算至少7天。

> **[V1.1修改]** S-04：新增"双盲稿件匿名化检查"场景，定义匿名化检查清单和PDF元数据自动检查。

> **[V1.1修改]** C-07：删除原"退稿重审"边界条件场景（移至P1）。

## 三、功能2：结构化审稿表单（优先级2）

### 3.1 功能描述

**对应用研痛点**：P2（审稿意见格式不统一）

**功能目标**：提供结构化的审稿表单，预设标准审稿维度和评分机制，引导审稿人按统一格式输出审稿意见。同时支持编辑部轻量自定义审稿维度，在标准化和灵活性之间取得平衡。解决审稿人提交意见格式各异（自由文本/分维度/仅评分）、编辑部需1-2小时手动整理的问题。

**核心价值**：
- 审稿人：降低"不知道从何评起"的认知负担，尤其帮助新手审稿人快速上手
- 编辑部：统一审稿意见格式，为后续意见汇总（功能3）提供结构化数据基础，免去手动整理
- 作者：获得格式清晰、维度明确的审稿意见，准确理解修改方向

**依赖关系**：依赖功能1（审稿任务管理）--审稿表单在审稿任务中由审稿人填写，表单数据关联到具体审稿任务。

### 3.2 用户故事

#### 审稿人视角
> **US-R-05**：作为一名审稿人，我希望审稿表单有清晰的维度引导和评分标准说明，这样我就知道应该从哪些角度评价论文，不用从零开始思考。

> **US-R-06**：作为一名审稿人（尤其新手），我希望每个维度有评分指引和示例说明，帮助我判断什么样的论文给几分，降低评分主观性。

> **US-R-07**：作为一名审稿人，我希望表单支持分多次填写和自动保存，因为我通常利用碎片时间审稿，需要随时中断和继续。

#### 编辑部视角
> **US-E-06**：作为一名编辑，我希望系统提供预设的标准审稿维度模板，开箱即用，不需要每次从头配置。

> **US-E-07**：作为一名编辑，我希望能根据期刊/学科特点自定义审稿维度（增加/删除/修改维度），但保持统一的数据结构，这样不同期刊的审稿意见仍可横向对比。

> **US-E-08**：作为一名编辑，我希望审稿人提交的表单数据是结构化的（维度+评分+文字），而不是自由文本，这样汇总时可以自动对齐对比。

#### 作者视角
> **US-A-04**：作为一名作者，我希望收到的审稿意见是按维度结构化呈现的（如"研究意义：4分，评价：..."），而不是一段混沌的文字，这样我能准确理解每个方面的评价和修改方向。

### 3.3 功能拆解

#### 3.3.1 审稿维度模板

**功能说明**：预设标准审稿维度模板，审稿人按维度逐一评价，确保审稿意见结构统一。

**预设四维模板**：

| 维度编号 | 维度名称 | 评价说明 | 评分指引 |
|---------|---------|---------|---------|
| D1 | 研究意义 | 评估论文研究问题的学术价值、理论贡献和现实意义。研究是否 addressed 重要问题？结论是否有价值？ | 5=意义重大，具有突出理论或实践贡献；4=意义较大，有一定贡献；3=意义一般，有一定价值；2=意义较小，贡献有限；1=意义极小或无贡献 |
| D2 | 创新性 | 评估论文的研究视角、方法、结论的新颖程度。是否有原创性贡献？与已有文献的区分度如何？ | 5=高度创新，开辟新视角或新方法；4=有明确创新点；3=有一定新意但不突出；2=创新性不足，主要重复已有工作；1=无创新 |
| D3 | 研究方法 | 评估研究设计、数据采集、分析方法、论证逻辑的合理性和严谨性。方法是否适当？论证是否充分？ | 5=方法严谨，设计合理，论证充分；4=方法较好，个别可改进；3=方法基本合理但有明显不足；2=方法存在较大问题；1=方法严重不当 |
| D4 | 写作水平 | 评估论文的结构组织、语言表达、文献引用规范、图表呈现质量。 | 5=结构清晰，语言精炼，规范完善；4=写作良好，个别可改进；3=写作一般，需较多修改；2=写作较差，影响理解；1=写作极差，无法理解 |

**模板配置规则**：
- 预设四维模板为系统默认模板，适用于大多数学科
- 编辑部可基于预设模板创建期刊/学科专属模板
- 自定义模板操作：增加维度（最多8个）/删除维度（最少2个）/修改维度名称和说明/调整维度顺序
- 每个维度必须包含：维度名称、评价说明、评分指引
- 模板一经使用（关联审稿任务）后不可修改，如需变更需创建新模板

> **[V1.1修改]** S-06：P0模板配置规则精简。删除"模板一经使用后不可修改，如需变更需创建新版本"的版本管理逻辑。P0模板一经使用后不可修改（保留此约束），但不提供版本管理功能（版本管理属P1）。

#### 3.3.2 评分机制

**功能说明**：每个维度采用"1-5分整数评分+文字说明"的双重评价机制，确保评分可量化、意见可理解。

**评分规则**：

| 规则项 | 说明 |
|--------|------|
| 评分范围 | 1-5分，整数 |
| 评分含义 | 5=优秀，4=良好，3=一般，2=较差，1=极差 |
| 评分约束 | 必须选择评分，不可为空 |
| 文字说明 | 每个维度必须填写文字说明，最少50字，最多2000字 |
| 文字说明引导 | 表单中展示该维度的评价说明和评分指引，引导审稿人针对性撰写 |
| 自动保存 | 审稿人填写过程中每60秒自动保存草稿，防止数据丢失 |

**评分校验**：
- 提交前校验所有维度评分均已选择，文字说明均达到最低字数要求
- 未通过校验的维度高亮提示，阻止提交

#### 3.3.3 总体评价

**功能说明**：在各维度评价基础上，审稿人给出总体推荐意见和综合评语，作为编辑终审决策的直接参考。

**总体推荐意见（必选其一）**：

| 推荐编号 | 推荐意见 | 说明 |
|---------|---------|------|
| R1 | 接收（Accept） | 稿件质量优良，无需修改即可录用 |
| R2 | 小修（Minor Revision） | 稿件基本合格，需少量修改后可录用 |
| R3 | 大修（Major Revision） | 稿件有价值但存在较多问题，需大幅修改后重新评审 |
| R4 | 拒稿（Reject） | 稿件存在根本性问题，不建议录用 |

**综合评语（必填）**：
- 字数要求：最少100字，最多3000字
- 内容引导：建议审稿人综合说明推荐理由、主要优点、主要问题、修改建议
- 提供结构化引导提示："请综合以上各维度评价，说明您的总体推荐理由、论文主要优点、需要修改的核心问题及具体修改建议。"

**修改建议（可选）**：
- 审稿人可逐条列出具体修改建议
- 每条修改建议包含：建议类型（内容/方法/格式/其他）+ 建议内容文本
- 修改建议将单独结构化展示给作者，便于逐条对照修改

#### 3.3.4 模板配置

**功能说明**：编辑部可创建、编辑和管理审稿模板，在创建审稿任务时关联使用。

> **[V1.1修改]** S-06：P0模板管理功能精简。仅保留创建/编辑/启用停用/关联使用四项功能。删除版本管理、使用统计、标记推荐、复制模板等功能（移至P1）。

**模板管理功能**：

| 操作 | 说明 | 权限 |
|------|------|------|
| 创建模板 | 基于预设模板或空白创建新模板，定义维度、评分指引、文字说明引导 | 编辑部 |
| 编辑模板 | 修改未使用模板的维度配置 | 编辑部 |
| 启用/停用 | 停用的模板不可在新任务中关联，已关联的不受影响 | 编辑部 |
| 关联使用 | 在创建审稿任务时选择模板关联使用 | 编辑部 |

> **[V1.1修改]** S-06：删除原"复制模板"和"版本管理"操作行。模板管理功能从6项精简为4项。

**模板数据结构统一性要求**：
- 无论自定义维度如何变化，所有模板输出的审稿意见数据结构一致（维度数组+总体评价+修改建议）
- 维度数组中每个元素包含：维度编号、维度名称、评分、文字说明
- 这一统一数据结构是功能3（审稿意见汇总）能自动对齐对比的前提

### 3.6 边界条件

| 异常场景 | 触发条件 | 处理逻辑 |
|---------|---------|---------|
| **审稿人提交未完成表单** | 部分维度未评分或文字说明未达最低字数 | 提交校验拦截，高亮未完成项，提示具体缺失内容 |
| **草稿超时** | 草稿保存超过30天未提交 | 系统通知审稿人，草稿保留但标记"过期"，审稿人可继续编辑或放弃 |
| **模板被修改** | 审稿任务进行中关联的模板被编辑 | 已关联的模板不受影响（使用快照），已使用模板不可修改 |
| **字数超限** | 文字说明超过2000字/综合评语超过3000字 | 输入时实时字符计数，超限后阻止继续输入 |

## 四、功能3：审稿意见汇总（优先级3）

### 4.1 功能描述

**对应用研痛点**：P3（多审稿人意见难以汇总对比）

**功能目标**：当一篇稿件的多位审稿人提交审稿意见后，系统自动按维度聚合多审稿人评分和意见，标注评分分歧点，生成结构化汇总报告，并基于规则给出终审建议。解决编辑部手动阅读对比2-4份意见耗时2-3小时、且容易遗漏关键信息的问题。

**核心价值**：
- 编辑部：将2-3小时的手动汇总对比缩短至分钟级自动生成，快速定位分歧核心，辅助终审决策
- 作者：获得结构化的汇总反馈，清晰了解审稿人一致认可的优势和需要修改的问题

**核心差异化**：根据用研报告竞品分析（§3），三大竞品（ScholarOne、Editorial Manager、OpenReview）在审稿意见汇总对比功能上**均缺失**，这是本产品的核心差异化能力。

**依赖关系**：依赖功能1（审稿任务管理）提供审稿人和任务数据 + 功能2（结构化审稿表单）提供结构化审稿意见数据。

### 4.2 用户故事

#### 编辑部视角
> **US-E-09**：作为一名编辑，当所有审稿人提交意见后，我希望系统能自动生成一份汇总报告，将多份意见按维度对齐对比，而不是让我逐份阅读手动整理。

> **US-E-10**：作为一名编辑，我希望系统能自动标注审稿人评分差异大的维度（如某维度一位给5分另一位给2分），这样我能快速定位分歧核心，聚焦讨论重点。

> **US-E-11**：作为一名编辑，我希望系统能基于审稿人意见自动生成一个终审建议（如"多数接收""分歧需讨论"），作为我决策的参考，而不是完全从零开始判断。

> **US-E-12**：作为一名编辑，我希望汇总报告能清晰展示审稿人一致认可的优点和一致指出的问题，这样我能快速把握稿件的共识评价。

#### 作者视角
> **US-A-05**：作为一名作者，我希望审稿结束后能看到一份汇总的审稿意见，清楚知道审稿人们对我的论文在不同维度上的评价是否一致，哪些方面是共识需要修改，哪些方面存在分歧。

> **US-A-06**：作为一名作者，当审稿人意见存在分歧时，我希望终审决策能说明编辑的判断依据，而不仅仅是一个结论，这样我能理解为什么最终做出了这个决定。

### 4.3 功能拆解

#### 4.3.1 意见聚合

**功能说明**：按审稿维度自动对齐多审稿人的评分和文字意见，生成结构化对比数据。

**聚合逻辑**：
1. 读取该稿件所有已提交的审稿意见（结构化JSON数据）
2. 按维度对齐：同一任务的所有审稿人使用同一模板（任务创建时强制确定），直接按维度编号对齐，将不同审稿人在同一维度上的评分和文字说明排列对比
3. 聚合总体推荐意见：统计各审稿人的推荐意见分布
4. 聚合修改建议：将各审稿人的修改建议按类型分类汇总

> **[V1.1修改]** C-02：聚合逻辑第2条由"按维度编号对齐"更新为"同一任务的所有审稿人使用同一模板（任务创建时强制确定），直接按维度编号对齐"。由于强制统一模板，不存在跨模板对齐场景。

**聚合输出结构**：

| 聚合项 | 输出内容 |
|--------|---------|
| 维度对比表 | 每个维度的各审稿人评分、平均分、评分范围、各审稿人文字意见摘要 |
| 总体推荐分布 | 各推荐意见（接收/小修/大修/拒稿）的票数和占比 |
| 修改建议汇总 | 按类型（内容/方法/格式/其他）归类的所有修改建议列表 |
| 综合评语汇总 | 各审稿人综合评语的原文展示 |

#### 4.3.2 分歧标注

**功能说明**：自动识别审稿人评分差异较大的维度并高亮标注，帮助编辑快速定位分歧核心。

**分歧识别规则**：

| 判定条件 | 标注级别 | 展示方式 |
|---------|---------|---------|
| 同一维度评分最大值-最小值 ≥ 3 | 🔴 严重分歧 | 红色高亮+⚠️图标+标注分差+分布信息 |
| 同一维度评分最大值-最小值 = 2 | 🟡 明显分歧 | 黄色高亮+标注分差+分布信息 |
| 同一维度评分最大值-最小值 ≤ 1 | 🟢 基本一致 | 绿色标记+分布信息 |
| 总体推荐意见出现"接收"与"拒稿"并存 | 🔴 严重分歧 | 红色高亮+特殊标注"推荐意见对立"+分布信息 |

> **[V1.1修改]** S-05：分歧标注旁增加分布信息展示。每个分歧/一致标注旁显示评分分布（如"4/5位评分5分，1/5位评分1分"），让编辑直观判断是广泛分歧还是个别异常。

**分歧详情展示**：
- 分歧维度展开后显示各审稿人的具体评分和文字说明
- 标注分差值（如"审稿人A: 5分 vs 审稿人B: 2分，分差=3"）
- 分歧维度的文字意见并排对比，便于编辑快速阅读理解分歧原因
- 分歧标注旁显示评分分布信息（如"评分分布：5分×2位，2分×1位"）

#### 4.3.3 汇总报告生成

#### 4.3.4 终审建议

**功能说明**：基于审稿人评分和推荐意见，通过规则引擎自动生成推荐结论，辅助编辑决策。

> **[V1.1修改]** S-07：终审建议精简。移除"附加评分维度建议"（优势/薄弱维度标注和总结性建议语生成）。终审建议仅输出推荐意见分布 + 规则匹配结果。

> **[V1.1修改]** C-06：规则引擎重构。定义规则优先级顺序，统一"多数"定义，补充1-2位审稿人场景，消除Rule-4和Rule-7重叠。

**终审建议规则引擎**：

**规则优先级**：Rule-7 > Rule-4 > Rule-6 > Rule-5 > Rule-3 > Rule-2 > Rule-1（高优先级先匹配，匹配后不再检查低优先级规则）

**"多数"统一定义**：≥半数（即推荐某意见的审稿人数 ≥ 审稿人总数 / 2，向上取整）

| 规则编号 | 优先级 | 触发条件 | 建议结论 | 说明 |
|---------|--------|---------|---------|------|
| Rule-1 | 7（最低） | 全部审稿人推荐"接收" | ✅ 全票接收 | 所有审稿人一致认可，建议接收 |
| Rule-2 | 6 | 多数（≥半数）推荐"接收"或"小修"，无"拒稿" | ✅ 多数接收 | 多数审稿人认可，建议接收或小修后接收 |
| Rule-3 | 5 | 多数（≥半数）推荐"接收"或"小修"，但有"大修"或"拒稿" | ⚠️ 倾向接收但需讨论 | 多数认可但存在异议，建议编辑讨论后决策 |
| Rule-4 | 2 | 推荐意见分散（接收/大修/拒稿均有），但**非**"接收与拒稿直接对立" | ⚠️ 分歧需讨论 | 审稿人意见三选分散，建议编辑综合判断或增加审稿人 |
| Rule-5 | 4 | 多数（≥半数）推荐"大修"，无"拒稿" | 🔄 建议大修 | 多数认为需大幅修改，建议大修后重新评审 |
| Rule-6 | 3 | 多数（≥半数）推荐"拒稿" | ❌ 建议拒稿 | 多数审稿人建议拒稿 |
| Rule-7 | 1（最高） | 存在"接收"与"拒稿"并存（直接对立） | ⚠️ 严重分歧需讨论 | 推荐意见直接对立，建议编辑重点关注分歧维度或增加审稿人 |

> **[V1.1修改]** C-06：规则引擎重构说明：
> 1. **优先级顺序**：Rule-7（最高）> Rule-4 > Rule-6 > Rule-5 > Rule-3 > Rule-2 > Rule-1（最低）。高优先级规则先匹配，匹配后不再检查低优先级规则。
> 2. **"多数"统一定义**：≥半数（推荐某意见的审稿人数 ≥ 审稿人总数/2，向上取整）。例如3位审稿人中2位=67%≥50%满足"多数"；4位审稿人中2位=50%满足"多数"。
> 3. **消除Rule-4和Rule-7重叠**：Rule-7专门处理"接收vs拒稿"的直接对立（最严重分歧），Rule-4处理"接收+大修+拒稿三选分散但非接收-拒稿直接对立"的情况。当"接收"和"拒稿"同时存在时，优先匹配Rule-7（高优先级），不再匹配Rule-4。
> 4. **1位和2位审稿人场景**（标注"仅供参考，建议人工判断"）：
>    - 1位审稿人：匹配Rule-1（如推荐"接收"则为"全票接收"），但标注"仅1份意见，仅供参考，建议人工判断"
>    - 2位审稿人：
>      - 2位推荐相同（如均为"接收"）：匹配Rule-1（"全票接收"）
>      - 1位"接收"+1位"拒稿"：匹配Rule-7（"严重分歧需讨论"），标注"仅供参考，建议人工判断"
>      - 1位"接收"+1位"大修"：匹配Rule-3（"倾向接收但需讨论"），标注"仅供参考，建议人工判断"
>      - 1位"接收"+1位"小修"：匹配Rule-2（"多数接收"），标注"仅供参考，建议人工判断"
>      - 其他组合类推

**重要声明**：系统终审建议仅为辅助参考，最终决策权在编辑部。编辑可在建议基础上做出不同决策，但需填写决策说明。

## 五、功能4：审稿知识库（优先级4）

### 5.1 功能描述

**对应用研痛点**：P4（审稿经验难以复用积累）

**功能目标**：将已完成的审稿意见和模板结构化归档，支持按学科/关键词/评分等维度检索复用，帮助审稿人（尤其新手）参考历史案例提升审稿效率和质量，帮助编辑部积累审稿数据资产。在P0阶段定位为基础架构搭建+最小可用版本。

**核心价值**：
- 审稿人：参考历史审稿案例和模板，降低审稿认知负担，新手审稿时间可从6小时缩短至2-3小时
- 编辑部：积累审稿数据资产，为后续审稿人能力评估和模板优化提供数据基础

**核心差异化**：根据用研报告竞品分析（§3），三大竞品在审稿知识库功能上**均缺失**（OpenReview仅有被动公开归档，无主动检索和模板复用），是本产品的长期竞争壁垒。

**依赖关系**：依赖功能1-3产生的数据（审稿任务/审稿意见/汇总报告/审稿模板）作为知识库数据来源。

**P0阶段定位**：根据用研报告§4.4，知识库存在数据冷启动问题，P0阶段应完成基础架构设计和最小可用版本，在后续迭代中持续丰富。

> **[V1.1修改]** S-01：P0阶段定位补充冷启动策略。P0知识库成功指标调整为"归档完整率+检索可用性"（非"检索命中率/使用率"），P0验证的是架构和流程而非用户价值。

### 5.3 功能拆解

#### 5.3.1 审稿意见归档

**功能说明**：已完成的审稿意见在终审决策后自动入库，按学科/关键词分类存储。归档采用两阶段匿名化方案，确保双盲安全。

> **[V1.1修改]** C-03：归档处理重构为两阶段匿名化方案。第一阶段自动移除结构化身份字段，第二阶段人工审核文字内容身份线索，审核通过后才执行不可逆归档。

**自动归档触发**：审稿任务状态变更为"已决策"时，系统自动启动第一阶段匿名化处理。

**两阶段匿名化方案**：

**第一阶段：自动移除结构化身份字段（系统自动执行）**
- 移除作者姓名/单位信息
- 移除审稿人姓名/单位信息
- 移除稿件标题（替换为学科+关键词标签）
- 稿件文件不入库，仅存审稿意见数据
- 审稿日期仅保留年份和月份，移除具体日期
- 自动扫描文字内容，执行以下检测规则：
  - **指代词检测**：扫描"贵校""您团队""张教授""李老师"等指代词
  - **自引检测**：扫描"author's previous work""the author's earlier study"等自引模式
  - **机构名检测**：与已知机构名称数据库匹配，检测文字中出现的机构名称
  - **基金编号格式检测**：扫描符合基金编号格式模式的字符串（如"NSFC No.XXXXX""Grant XXXXX"等）
- 命中检测规则的文字段标记为"待人工审核"
- 第一阶段处理完成后，数据进入"待审核"状态，不执行不可逆归档

**第二阶段：人工审核文字内容身份线索（编辑部审核）**
- **审核人**：编辑部指定审核人（由处理该任务的编辑或指定审核编辑执行）
- **审核时限**：数据进入"待审核"状态后48小时内完成审核
- **审核内容**：
  - 检查自动标记的"待人工审核"文字段，判断是否构成身份线索
  - 人工通读审稿意见文字内容，检查自动检测未覆盖的语义级身份线索
  - 对于小众学科领域（审稿人圈子小，身份推断风险高），强制逐条审核文字意见
- **审核结果**：
  - **通过**：审核通过后执行不可逆归档，数据正式写入知识库
  - **退回修改**：退回编辑部修改文字内容中的身份线索后重新提交审核（此时匿名化尚未不可逆，可修改）
  - **永久不归档**：文字内容身份线索过多且无法有效移除，标记为"永久不归档"，数据不写入知识库
- **审核记录**：记录审核人、审核时间、审核结果、审核意见

> **[V1.1修改]** C-03：两阶段方案解决原"不可逆vs退回修改"矛盾——第一阶段自动处理后数据为"待审核"状态（可修改），第二阶段审核通过后才执行不可逆归档。审核不通过可退回修改（此时尚未不可逆），或选择永久不归档。

**归档数据结构**：
```
KnowledgeItem {
  id: 知识库条目ID
  subject: 学科领域
  manuscriptType: 稿件类型
  keywords: 关键词数组
  reviewDate: 审稿日期
  reviewMode: 审稿模式（单盲/双盲）
  dimensions: [
    {
      dimensionName: 维度名称
      scores: 各审稿人评分数组（匿名化）
      avgScore: 平均分
      opinions: 各审稿人文字意见数组（匿名化，经两阶段处理）
    }
  ]
  recommendations: 各审稿人推荐意见分布
  summaryReport: 汇总报告（匿名化）
  templateUsed: 使用的模板信息
  finalDecision: 终审决策
  anonymizationStatus: 匿名化状态（PENDING_REVIEW/APPROVED/REJECTED/PERMANENTLY_EXCLUDED）
  reviewedBy: 审核人（第二阶段）
  reviewedAt: 审核时间
}
```

### 5.6 边界条件

| 异常场景 | 触发条件 | 处理逻辑 |
|---------|---------|---------|
| **知识库为空（冷启动）** | P0初期知识库无数据 | 1. 检索结果为空时展示预设四维模板的评分指引和撰写示例（不展示空结果）；2. 提示"知识库将在审稿数据积累后逐步丰富"；3. 仍可使用预设模板和编辑部自定义模板 |
| **匿名化审核-退回修改** | 第二阶段审核发现文字内容有身份线索但可修改 | 1. 退回编辑部修改身份线索文字；2. 修改后重新提交审核；3. 此时匿名化尚未不可逆，可修改 |
| **匿名化审核-永久不归档** | 第二阶段审核发现文字内容身份线索过多且无法有效移除 | 1. 标记为"永久不归档"；2. 数据不写入知识库；3. 记录原因和审核人 |
| **匿名化审核超时** | 第二阶段审核48小时内未完成 | 1. 系统自动通知编辑部提醒审核；2. 数据保持"待审核"状态，不自动归档 |
| **检索结果过多** | 检索条件宽松导致返回大量结果 | 1. 默认分页显示（每页20条）；2. 提示"结果较多，建议增加筛选条件缩小范围"；3. 支持结果内二次搜索 |
| **检索结果为零** | 无匹配的知识库条目 | 展示预设四维模板的评分指引和撰写示例，提示"暂无匹配案例" |
| **模板被删除但有关联条目** | 编辑部停用模板但知识库中有使用该模板的条目 | 1. 知识库条目保留（使用模板快照）；2. 模板列表中标记"已停用"；3. 不影响历史数据检索 |
| **归档失败** | 数据异常导致自动归档失败 | 1. 记录失败日志；2. 系统通知编辑部；3. 编辑部可手动触发重新归档 |
| **导出数据量过大** | 编辑部尝试导出大量知识库数据 | 1. 单次导出上限1000条；2. 超限时提示分批导出；3. 导出数据均为匿名化（经两阶段处理） |

### 6.2 实体定义

#### 6.2.1 User（用户）

> **[V1.1修改]** C-05：新增User实体定义。

| 字段名 | 类型 | 说明 | 约束 |
|--------|------|------|------|
| userId | String | 用户唯一编号 | 主键，全局唯一 |
| name | String | 用户姓名 | 必填，≤100字符 |
| email | String | 邮箱地址 | 必填，唯一，用于登录和通知 |
| roles | Array\<Enum\> | 用户角色数组 | 必填，枚举值（REVIEWER/EDITOR/AUTHOR），支持多角色 |
| institution | String | 所属机构 | 可选，≤200字符 |
| researchAreas | Array\<String\> | 研究方向标签数组 | 可选，用于审稿人匹配排序 |
| createdAt | DateTime | 创建时间 | 必填，系统自动生成 |
| updatedAt | DateTime | 最后更新时间 | 必填，系统自动更新 |

**用户角色模型**：
- 同一用户可具备多个角色（roles为数组），如某用户同时具备REVIEWER和EDITOR角色
- 同一用户在不同任务中可具备不同角色：User.roles定义用户的全局角色能力，具体在某个任务中的角色由ReviewAssignment（审稿人）或ReviewTask.createdBy（编辑部）或ReviewTask.authorUserId（作者）确定
- 例如：某用户在任务A中是EDITOR（作为createdBy），在任务B中是REVIEWER（作为ReviewAssignment.reviewerUserId），在任务C中是AUTHOR（作为ReviewTask.authorUserId）

**用户创建流程**：
- 编辑部账号：系统初始化时创建或由管理员创建
- 审稿人账号：由编辑部创建（编辑部在审稿人库管理中新增审稿人，填写姓名/邮箱/学科领域/研究方向，系统自动生成账号并发送邀请邮件）
- 作者账号：由编辑部在创建审稿任务时关联创建（填写作者邮箱，系统自动生成账号并通知作者）

### 6.3 实体关系说明

| 关系 | 类型 | 说明 |
|------|------|------|
| User -> ReviewTask (as author) | 1:N | 一个用户可作为多篇稿件的作者 |
| User -> ReviewTask (as editor) | 1:N | 一个用户可创建多个审稿任务 |
| User -> ReviewAssignment (as reviewer) | 1:N | 一个用户可被分配多个审稿任务 |
| ReviewTask -> ReviewAssignment | 1:N | 一个任务可分配多位审稿人 |
| ReviewTask -> ReviewForm | 1:1 | 一个任务关联一个审稿表单（基于模板生成） |
| ReviewTask -> Template | N:1 | 多个任务可使用同一模板（使用快照） |
| ReviewAssignment -> ReviewOpinion | 1:1 | 一位审稿人提交一份审稿意见 |
| ReviewForm -> ReviewOpinion | 1:N | 一个表单对应多位审稿人的意见 |
| ReviewTask -> SummaryReport | 1:1 | 一个任务生成一份汇总报告 |
| SummaryReport -> KnowledgeItem | 1:1 | 汇总报告经两阶段匿名化后归档为知识库条目 |
| Template -> ReviewForm | 1:N | 一个模板可被多个表单使用 |
