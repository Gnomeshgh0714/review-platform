## 一、技术选型

### 1.1 前端：Vue 3 + Element Plus + ECharts

**选型理由**：

| 需求维度 | 选型方案 | 理由 |
|---------|---------|------|
| 表单渲染 | Element Plus 表单组件 | 审稿表单需动态渲染2-8个维度、评分单选、多行文本输入、自动保存草稿。Element Plus 的 `el-form` + `el-radio-group` + `el-input` 可快速实现，校验规则内置（必填、字数范围），动态表单通过 `v-for` 渲染维度列表 |
| 流程图展示 | ECharts + 自定义SVG | 作者进度时间线使用 ECharts 的自定义图类型或简单SVG时间轴；稿件看板使用 Element Plus 卡片组件 |
| 数据表格 | Element Plus `el-table` | 审稿意见维度对比表、任务列表、知识库检索结果列表均需结构化表格展示，支持排序、分页、筛选、行展开 |
| 拖拽排序 | vuedraggable (Sortable.js) | 模板维度配置需拖拽调整顺序 |
| 状态管理 | Pinia | 管理用户登录态、当前任务上下文、审稿表单草稿状态 |
| 路由 | Vue Router 4 | SPA 路由管理，按角色路由守卫（编辑部/审稿人/作者） |

**核心决策**：Vue 3 的 Composition API 适合将审稿表单、知识库检索面板等复杂组件逻辑复用；Element Plus 组件库覆盖表单/表格/对话框/通知等全部UI需求，与Vue 3深度集成，降低开发成本。

### 1.2 后端：Python Django + Django REST Framework

**选型理由**：

| 需求维度 | 选型方案 | 理由 |
|---------|---------|------|
| 事务+行锁 | Django ORM + `select_for_update()` | PRD明确要求多审稿人并发提交采用"数据库事务+行锁"策略（AC-T-14）。Django ORM 原生支持 `with transaction.atomic(): ReviewTask.objects.select_for_update().get(task_id=...)`，在PostgreSQL上自动使用 `SELECT ... FOR UPDATE` 行级锁 |
| 状态机 | 自定义状态机中间件 + Django Model 状态字段 | ReviewTask.status 字段存储当前状态，状态转换通过 `StateTransition` 配置表定义合法转换路径，中间件校验非法转换并抛出 `InvalidStateTransition` 异常。Django 的 `pre_save` 信号记录状态变更日志 |
| 规则引擎 | Python 链式规则匹配器 | 终审建议7条规则（Rule-1~Rule-7）按优先级链式匹配，实现为 `RuleEngine` 类，每个规则为独立 `Rule` 子类，按优先级排序后顺序匹配。纯Python实现无需引入重量级规则引擎框架 |
| 定时任务 | Celery + Redis | 截止日期提醒（7天/3天/1天）、邀请超时检测、审稿超时检测、48小时自动通知主编等定时逻辑，使用 Celery periodic task |
| 邮件通知 | Django邮件模块 + Celery异步 | 站内消息存数据库，邮件通过 Celery 异步发送，避免阻塞请求 |
| REST API | Django REST Framework | 序列化器（Serializer）天然映射8个实体到JSON，视图集（ViewSet）提供标准CRUD+自定义action |
| 全文检索集成 | Django + Elasticsearch DSL | 通过 `django-elasticsearch-dsl` 库将 KnowledgeItem 同步到 ES，支持多条件组合检索 |

### 1.3 数据库：PostgreSQL 15

**选型理由**：

| 需求维度 | 支持情况 |
|---------|---------|
| 结构化数据存储 | 8个实体均为结构化数据，关系型数据库天然适配 |
| 事务支持 | PostgreSQL 提供完整的 ACID 事务支持，Django ORM 的 `transaction.atomic()` 直接映射 |
| 行锁 | `SELECT ... FOR UPDATE` 行级锁，满足 AC-T-14 并发提交需求 |
| JSON字段 | PostgreSQL `JSONB` 类型存储 ReviewOpinion.dimensionScores、Template.dimensions、SummaryReport 各复杂子结构，支持JSON内部查询 |
| 全文检索（辅助） | PostgreSQL 自带 `tsvector` 全文检索，可作为知识库检索的降级方案或ES的补充 |
| 数组字段 | PostgreSQL `ARRAY` 类型存储 keywords、roles、researchAreas 等数组字段 |
| 枚举约束 | 通过 Django 模型的 `choices` + 数据库 CHECK 约束实现 |

### 1.4 全文检索引擎：Elasticsearch 8

**选型理由**：

| 需求维度 | 支持情况 |
|---------|---------|
| 审稿意见全文检索 | AC-K-05要求按关键词全文检索审稿意见文字内容，ES 的全文索引+分词器满足需求 |
| 多条件组合 | AC-K-06要求按学科/类型/评分/推荐意见/日期等多维度组合筛选，ES 的 bool query + filter 完美适配 |
| 相关度排序 | AC要求检索结果按相关度排序，ES 的 `_score` 提供标准TF-IDF/BM25相关度计算 |
| 中文分词 | ES 集成 IK 分词器，支持中文审稿意见的分词检索 |
| 冷启动降级 | 知识库为空时（冷启动期），后端直接返回模板评分指引数据，不查询ES |

### 1.5 文件存储：本地文件系统 + MinIO（可选）

**选型理由**：

| 需求维度 | 方案 |
|---------|------|
| 稿件PDF存储 | 存储路径：`/data/manuscripts/{taskId}/{filename}`，数据库仅存路径（ReviewTask.manuscriptFile） |
| 文件限制 | PDF格式、≤20MB，上传时即时校验（前端MIME类型+后端文件头校验+大小校验） |
| 访问控制 | 文件下载需鉴权，通过后端API中转（非直接暴露文件路径），按角色验证下载权限 |
| MinIO（可选） | 如需对象存储扩展能力，可部署 MinIO（S3兼容），P0阶段先用本地文件系统，预留存储接口抽象层 |

### 2.3 核心技术决策

#### 2.3.1 状态机实现方案

**方案：数据库状态字段 + 状态转换配置表 + 校验中间件**

```
数据库层：
  ReviewTask.status 字段存储当前状态（枚举：PENDING/ASSIGNED/REVIEWING/
    SUBMITTED/SUMMARIZED/DECIDED）

  StateTransition 配置表定义合法转换路径：
  ┌────────────┬────────────┬──────────────────────────────────┬──────────┐
  │ from_state │ to_state   │ trigger_condition                │ operator │
  ├────────────┼────────────┼──────────────────────────────────┼──────────┤
  │ PENDING    │ ASSIGNED   │ 分配≥1位审稿人                    │ EDITOR   │
  │ ASSIGNED   │ REVIEWING  │ 首位审稿人接受邀请                 │ SYSTEM   │
  │ ASSIGNED   │ PENDING    │ 所有审稿人均拒绝邀请               │ SYSTEM   │
  │ REVIEWING  │ SUBMITTED  │ 全部已接受审稿人均提交             │ SYSTEM   │
  │ REVIEWING  │ SUBMITTED  │ 编辑强制提前汇总（≥1份已提交）     │ EDITOR   │
  │ REVIEWING  │ PENDING    │ 全部超时且无可提交意见             │ SYSTEM   │
  │ REVIEWING  │ PENDING    │ 部分提交后其余全部超时，编辑选择回退│ EDITOR   │
  │ REVIEWING  │ SUBMITTED  │ 部分提交后其余全部超时，编辑选择汇总│ EDITOR   │
  │ SUBMITTED  │ SUMMARIZED │ 编辑触发汇总报告生成               │ EDITOR   │
  │ SUMMARIZED │ DECIDED    │ 编辑录入终审决策                   │ EDITOR   │
  │ DECIDED    │ REVIEWING  │ [P1预留，P0不实现]                │ -        │
  └────────────┴────────────┴──────────────────────────────────┴──────────┘

  StateLog 表记录所有状态变更日志：
  { logId, taskId, fromState, toState, operator, operatorUserId,
    triggerReason, createdAt }

应用层：
  StateMachineService 类封装状态转换逻辑：
  1. validate_transition(task, target_state, operator, context)
     → 查询StateTransition表验证合法性
     → 校验触发条件（如"全部已提交"需查询ReviewAssignment状态）
     → 不合法则抛出 InvalidStateTransition 异常
  2. execute_transition(task, target_state, operator, context)
     → 在事务内执行：更新status + 写StateLog + 触发通知
  3. 自动转换由系统定时任务或事件回调触发（如审稿人提交后检查是否全部提交）

中间件层：
  Django中间件拦截所有状态变更请求，调用StateMachineService.validate_transition
  在视图执行前校验，不通过返回 400 错误
```

#### 2.3.2 并发控制实现方案

**方案：数据库事务 + SELECT FOR UPDATE 行锁**

```python
# 多审稿人并发提交（AC-T-14）核心实现
@transaction.atomic
def submit_review_opinion(assignment_id, opinion_data):
    # 1. 加行锁锁定 ReviewTask 记录
    assignment = ReviewAssignment.objects.select_for_update().get(
        assignment_id=assignment_id
    )
    task = ReviewTask.objects.select_for_update().get(
        taskId=assignment.task_id
    )

    # 2. 存储审稿意见
    opinion = ReviewOpinion.objects.create(
        task_id=task.taskId,
        assignment_id=assignment_id,
        status='SUBMITTED',
        **opinion_data
    )

    # 3. 更新分配记录状态
    assignment.assignmentStatus = 'SUBMITTED'
    assignment.submittedAt = timezone.now()
    assignment.reviewOpinionId = opinion.opinionId
    assignment.save()

    # 4. 检查是否全部已接受的审稿人均已提交
    accepted_assignments = ReviewAssignment.objects.filter(
        task_id=task.taskId,
        assignmentStatus='ACCEPTED'
    ).exclude(assignmentStatus='SUBMITTED')

    if not accepted_assignments.exists():
        # 全部已提交，触发状态转换
        StateMachineService.execute_transition(
            task=task,
            target_state='SUBMITTED',
            operator='SYSTEM',
            context={'reason': 'all_reviewers_submitted'}
        )

    # 其他并发事务等待行锁释放后重新检查状态
    # 此时 task.status 可能已被前一个事务更新为 SUBMITTED
    # 重复提交会被 assignment.assignmentStatus == 'SUBMITTED' 拦截
```

**编辑间并发冲突（乐观锁）**：
```python
# ReviewTask 模型增加 version 字段（乐观锁）
class ReviewTask(models.Model):
    version = models.IntegerField(default=0)
    # ...

def update_task(task_id, update_data, expected_version):
    rows = ReviewTask.objects.filter(
        taskId=task_id, version=expected_version
    ).update(version=expected_version+1, **update_data)
    if rows == 0:
        raise OptimisticLockError("任务已被他人更新，请刷新后重试")
```

#### 2.3.3 规则引擎实现方案

**方案：优先级链式匹配（Python 实现）**

```python
from abc import ABC, abstractmethod
from enum import Enum
import math

class Recommendation(Enum):
    ACCEPT = "ACCEPT"
    MINOR_REVISION = "MINOR_REVISION"
    MAJOR_REVISION = "MAJOR_REVISION"
    REJECT = "REJECT"

class Rule(ABC):
    rule_id: str
    priority: int  # 数字越小优先级越高
    conclusion: str

    @abstractmethod
    def match(self, recommendations: list, reviewer_count: int) -> bool:
        """判断是否匹配当前推荐意见分布"""
        pass

class Rule7(Rule):
    """Rule-7（最高优先级）：接收与拒稿并存"""
    rule_id = "Rule-7"
    priority = 1
    conclusion = "⚠️ 严重分歧需讨论"

    def match(self, recommendations, reviewer_count):
        return (Recommendation.ACCEPT in recommendations
                and Recommendation.REJECT in recommendations)

class Rule4(Rule):
    """Rule-4：推荐意见三选分散（非接收-拒稿直接对立）
    N-01重新定义触发条件：
    - "小修+大修+拒稿分散但无接收"
    - "接收+小修+大修分散但无拒稿"
    """
    rule_id = "Rule-4"
    priority = 2
    conclusion = "⚠️ 分歧需讨论"

    def match(self, recommendations, reviewer_count):
        rec_set = set(recommendations)
        # 条件1：小修+大修+拒稿分散，无接收
        cond1 = ({Recommendation.MINOR_REVISION, Recommendation.MAJOR_REVISION,
                  Recommendation.REJECT}.issubset(rec_set)
                 and Recommendation.ACCEPT not in rec_set)
        # 条件2：接收+小修+大修分散，无拒稿
        cond2 = ({Recommendation.ACCEPT, Recommendation.MINOR_REVISION,
                  Recommendation.MAJOR_REVISION}.issubset(rec_set)
                 and Recommendation.REJECT not in rec_set)
        return cond1 or cond2

class Rule6(Rule):
    """Rule-6：多数拒稿"""
    rule_id = "Rule-6"
    priority = 3
    conclusion = "❌ 建议拒稿"

    def match(self, recommendations, reviewer_count):
        majority = math.ceil(reviewer_count / 2)
        reject_count = recommendations.count(Recommendation.REJECT)
        return reject_count >= majority

class Rule5(Rule):
    """Rule-5：多数大修，无拒稿"""
    rule_id = "Rule-5"
    priority = 4
    conclusion = "🔄 建议大修"

    def match(self, recommendations, reviewer_count):
        majority = math.ceil(reviewer_count / 2)
        major_count = recommendations.count(Recommendation.MAJOR_REVISION)
        return (major_count >= majority
                and Recommendation.REJECT not in recommendations)

class Rule3(Rule):
    """Rule-3：多数接收或小修，但有大修或拒稿"""
    rule_id = "Rule-3"
    priority = 5
    conclusion = "⚠️ 倾向接收但需讨论"

    def match(self, recommendations, reviewer_count):
        majority = math.ceil(reviewer_count / 2)
        accept_minor = (recommendations.count(Recommendation.ACCEPT)
                       + recommendations.count(Recommendation.MINOR_REVISION))
        has_major_or_reject = (Recommendation.MAJOR_REVISION in recommendations
                              or Recommendation.REJECT in recommendations)
        return accept_minor >= majority and has_major_or_reject

class Rule2(Rule):
    """Rule-2：多数接收或小修，无拒稿"""
    rule_id = "Rule-2"
    priority = 6
    conclusion = "✅ 多数接收"

    def match(self, recommendations, reviewer_count):
        majority = math.ceil(reviewer_count / 2)
        accept_minor = (recommendations.count(Recommendation.ACCEPT)
                       + recommendations.count(Recommendation.MINOR_REVISION))
        return (accept_minor >= majority
                and Recommendation.REJECT not in recommendations
                and Recommendation.MAJOR_REVISION not in recommendations)

class Rule1(Rule):
    """Rule-1（最低优先级）：全部接收"""
    rule_id = "Rule-1"
    priority = 7
    conclusion = "✅ 全票接收"

    def match(self, recommendations, reviewer_count):
        return all(r == Recommendation.ACCEPT for r in recommendations)

class RuleEngine:
    def __init__(self):
        # 按优先级排序（priority值越小越优先）
        self.rules = sorted([
            Rule1(), Rule2(), Rule3(), Rule4(),
            Rule5(), Rule6(), Rule7()
        ], key=lambda r: r.priority)

    def evaluate(self, recommendations: list, reviewer_count: int) -> dict:
        """按优先级链式匹配，匹配后不再检查低优先级规则"""
        # 1-2位审稿人标注"仅供参考"
        is_small_sample = reviewer_count <= 2

        for rule in self.rules:
            if rule.match(recommendations, reviewer_count):
                result = {
                    "matchedRuleId": rule.rule_id,
                    "conclusion": rule.conclusion
                }
                if is_small_sample:
                    result["note"] = "仅供参考，建议人工判断"
                return result

        # 无规则匹配
        result = {
            "matchedRuleId": None,
            "conclusion": "无法自动判定，请编辑综合判断"
        }
        if is_small_sample:
            result["note"] = "仅供参考，建议人工判断"
        return result
```

**方案：第一阶段自动处理 + 第二阶段人工审核工作流**

```

        · archivedAt = 当前时间
```

#### 2.3.5 标签匹配排序实现方案

**方案：关键词交集计数 + Jaccard相似度**

```python
def match_and_sort_reviewers(task_keywords: list, reviewers: list) -> list:
    """
    轻量标签匹配排序（非AI推荐）：
    基于稿件keywords与审稿人researchAreas的匹配度排序
    """
    task_kw_set = set(kw.lower() for kw in task_keywords)

    scored_reviewers = []
    for reviewer in reviewers:
        reviewer_kw_set = set(area.lower() for area in reviewer.researchAreas)

        # 计算匹配度（Jaccard相似度的变体：交集大小/任务关键词数）
        intersection = task_kw_set & reviewer_kw_set
        match_score = len(intersection) / len(task_kw_set) if task_kw_set else 0

        # 匹配关键词数量作为主要排序依据
        match_count = len(intersection)

        scored_reviewers.append({
            'reviewer': reviewer,
            'match_score': match_score,
            'match_count': match_count,
            'matched_keywords': list(intersection)
        })

    # 按匹配关键词数降序 → 匹配度降序 → 姓名排序
    scored_reviewers.sort(
        key=lambda x: (-x['match_count'], -x['match_score'], x['reviewer'].name)
    )

    return scored_reviewers
```

### 3.3 N-01处理：Rule-4触发条件重新定义

**问题**：PRD V1.1中Rule-4原触发条件为"推荐意见分散（接收/大修/拒稿均有），但非'接收与拒稿直接对立'"。由于Rule-7（优先级更高）已覆盖"接收与拒稿并存"的场景，当Rule-4要求"接收/大修/拒稿均有"时，必然同时满足Rule-7的条件（接收+拒稿并存），导致Rule-4永远不会被匹配（死规则）。

**解决方案**：按总监终审N-01裁决，重新定义Rule-4触发条件为两种子条件（满足任一即匹配）：

| 子条件 | 触发条件 | 含义 |
|--------|---------|------|
| 条件A | 小修+大修+拒稿分散，**无接收** | 审稿人意见偏负面分散（无接收认可），需编辑讨论 |
| 条件B | 接收+小修+大修分散，**无拒稿** | 审稿人意见偏正面分散（无拒稿否定），需编辑讨论 |

**规则优先级链不变**：Rule-7 > Rule-4 > Rule-6 > Rule-5 > Rule-3 > Rule-2 > Rule-1

**重新定义后的规则匹配逻辑验证**：

| 推荐意见分布 | 匹配规则 | 说明 |
|-------------|---------|------|
| 全部接收 | Rule-1 | 全票接收 |
| 接收+小修（无拒稿无大修） | Rule-2 | 多数接收 |
| 接收+小修+大修（无拒稿） | Rule-4（条件B） | 三选分散，无拒稿 |
| 接收+小修+大修+拒稿 | Rule-7 | 接收与拒稿对立（最高优先级） |
| 接收+拒稿 | Rule-7 | 直接对立 |
| 小修+大修+拒稿（无接收） | Rule-4（条件A） | 三选分散，无接收 |
| 多数大修（无拒稿） | Rule-5 | 多数大修 |
| 多数拒稿 | Rule-6 | 多数拒稿 |
| 多数接收/小修 + 大修/拒稿 | Rule-3 | 多数认可但有异议 |

> Rule-4现在成为有效规则，与Rule-7不再重叠（Rule-7处理"接收+拒稿并存"，Rule-4处理"无接收的三选分散"或"无拒稿的三选分散"）。

### 3.4 N-02处理：ReviewTask增加retryCount字段

**问题**：PRD V1.1中 `attemptCount` 字段语义模糊，无法区分"审稿人级分配次数"与"任务级总重试次数"。

**解决方案**：按总监终审N-02裁决，澄清语义并新增字段：

| 字段 | 所属实体 | 语义 | 用途 |
|------|---------|------|------|
| `attempt_count` | ReviewAssignment | 同一任务中同一审稿人的分配次数 | 记录某审稿人被分配的次数（默认1，重新分配同一审稿人时递增） |
| `retry_count` | ReviewTask（新增） | 任务级总重试次数 | 记录所有审稿人拒邀/超时的累计次数，超过3次标记"分配困难"通知主编 |

**retry_count递增逻辑**：

```python
def increment_retry_count(task_id, reason):
    """当审稿人拒绝邀请或超时未响应时，递增任务级重试次数"""
    task = ReviewTask.objects.select_for_update().get(task_id=task_id)
    task.retry_count += 1
    task.save()

    if task.retry_count > 3:
        # 标记"分配困难"并通知主编
        NotificationService.notify_editor_in_chief(
            task=task,
            message=f"任务 {task.taskId} 分配困难，已有 {task.retry_count} 次重试"
        )
```

**与attempt_count的配合使用**：
- `retry_count` 超过3次 → 任务级升级，通知主编介入
- `attempt_count` 记录在 ReviewAssignment 上，用于追踪单个审稿人的分配历史（避免对同一审稿人反复分配）

### 6.1 技术风险

| 风险编号 | 风险项 | 风险描述 | 影响程度 | 概率 | 应对措施 |
