### 1.4 设计原则

基于用研报告竞品分析结论（§3），确立以下设计原则：

1. **审稿人友好**：以降低操作门槛为核心，避免ScholarOne/EM界面复杂、学习成本高的问题
2. **标准化+轻量自定义**：在统一数据结构基础上提供预设模板+轻量配置，避免EM配置过重
3. **隐私保护下的透明化**：在双盲审稿前提下向作者提供细粒度状态追踪，借鉴OpenReview的透明理念但不照搬开放模式
4. **自动化辅助**：通过结构化数据和规则引擎实现意见汇总、分歧标注、终审建议的自动化，填补竞品功能空白

本PRD严格限定在P0范围内，以下功能**不在本文档范围内**（属于P1/P2）：

## 二、功能1：审稿任务管理（优先级1）

### 2.1 功能描述

**对应用研痛点**：P1（任务分配效率低）+ P5（审稿进度不透明）

**功能目标**：为编辑部提供高效的审稿任务创建、分配和追踪能力，同时为审稿人提供统一的任务管理入口，为作者提供细粒度的审稿进度可视化。通过标准化的任务状态机和自动化的进度推送，解决任务分配平均耗时3-7天（P1）和作者只能看到笼统状态（P5）的问题。

**核心价值**：
- 编辑部：减少任务分配中的反复沟通，实时掌握所有在审稿件进度，及时发现超时风险
- 审稿人：统一任务入口，不再散落在邮箱中，清晰的截止日期和优先级管理
- 作者：从"黑箱等待"变为"透明追踪"，减少焦虑和催问

### 2.2 用户故事

#### 审稿人视角
> **US-R-01**：作为一名审稿人，我希望在一个统一的任务列表中看到所有待处理的审稿任务，包括截止日期和优先级，这样我就不会遗漏任何任务或错过截止日期。

> **US-R-02**：作为一名审稿人，我希望收到审稿邀请后能一键接受或拒绝，而不需要回复邮件沟通，这样能更快地确认任务。

> **US-R-03**：作为一名审稿人，我希望在任务列表中看到距离截止日期的倒计时提醒，并在即将超期时收到系统通知，这样我能合理安排审稿时间。

> **US-R-04**：作为一名审稿人，我希望在提交审稿意见后能看到编辑部是否已查看以及最终决策结果，这样我就不会觉得意见"石沉大海"。

#### 编辑部视角
> **US-E-01**：作为一名编辑，我希望能在系统中快速创建审稿任务并关联稿件信息（标题、摘要、关键词、学科领域），而不需要在多个系统间切换。

> **US-E-02**：作为一名编辑，我希望能一次性为稿件分配1-N位审稿人并为每位设置截止日期，系统自动发送邀请通知，而不需要逐一发邮件。

> **US-E-03**：作为一名编辑，我希望在一个看板视图中看到所有在审稿件的状态（待分配/已分配/审稿中/已提交/已汇总/已决策），并能快速筛选出超时风险高的稿件。

> **US-E-04**：作为一名编辑，当审稿人拒绝邀请或超时未提交时，我希望系统能自动通知我并提供快速重新分配的操作入口，而不是等我手动发现。

> **US-E-05**：作为一名编辑，当所有审稿人提交意见后，我希望系统能自动提示我进入汇总环节，并一键跳转到汇总功能。

#### 作者视角
> **US-A-01**：作为一名作者，我希望投稿后能实时看到稿件处于审稿的哪个具体阶段（分配审稿人中/审稿人审稿中/意见汇总中/终审决策中），而不是只看到一个笼统的"Under Review"。

> **US-A-02**：作为一名作者，当审稿周期过长时，我希望系统能提供预计完成时间或当前阶段说明，这样我就不必焦虑地猜测或冒昧催问编辑。

> **US-A-03**：作为一名作者，当审稿结束后，我希望能在系统中直接查看结构化的审稿意见和终审决策结果，而不是等待邮件通知。

### 2.3 功能拆解

#### 2.3.1 任务创建

**功能说明**：编辑部在系统中创建审稿任务，关联稿件元数据信息，作为审稿流程的起点。

**操作主体**：编辑部

**创建字段**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 稿件标题 | 文本 | 是 | 论文完整标题 |
| 摘要 | 长文本 | 是 | 论文摘要（用于审稿人初步了解） |
| 关键词 | 标签数组 | 是 | 学科关键词，3-10个，用于审稿人匹配参考 |
| 学科领域 | 枚举 | 是 | 一级学科分类（如：经济学、计算机科学、生物学等） |
| 稿件类型 | 枚举 | 是 | 研究论文/综述/案例研究/短文等 |
| 稿件文件 | 文件上传 | 是 | PDF格式，≤20MB |
| 审稿模式 | 枚举 | 是 | 单盲/双盲（影响审稿人是否可见作者信息） |
| 期望审稿人数量 | 整数 | 是 | 期望分配的审稿人数量，默认3，范围1-5 |
| 截止日期 | 日期 | 是 | 期望完成审稿的日期，不得早于当前日期+7天 |
| 附加说明 | 长文本 | 否 | 编辑部对审稿人的特殊要求说明 |
| 审稿模板 | 关联引用 | 否 | 关联的审稿表单模板，未指定则使用学科默认模板 |

**业务规则**：
- 任务创建后自动进入"待分配"状态
- 系统自动生成唯一任务编号（格式：RT-YYYYMMDD-NNNN）
- 稿件文件上传后系统自动校验PDF格式和文件大小
- 双盲模式下，稿件文件中的作者信息由编辑部负责隐去

#### 2.3.2 任务分配

**功能说明**：编辑部分配审稿任务给1-N位审稿人，设置每位审稿人的截止日期，系统自动发送邀请通知。

**操作主体**：编辑部

**分配方式**：
- **手动分配**：编辑从系统审稿人库中搜索和选择审稿人
- **批量分配**：一次选择多位审稿人，分别设置截止日期

**分配字段**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 审稿人 | 用户引用 | 是 | 从审稿人库中选择，支持按姓名/学科/关键词搜索 |
| 截止日期 | 日期 | 是 | 该审稿人的审稿截止日期 |
| 邀请说明 | 文本 | 否 | 编辑部对该审稿人的个性化说明 |
| 邀请有效期 | 日期 | 是 | 审稿人接受/拒绝邀请的截止时间，默认3天 |

**业务规则**：
- 一篇稿件可分配1-5位审稿人
- 同一审稿人不可在同一稿件中被重复分配
- 分配后系统自动向审稿人发送邀请通知（站内消息+邮件）
- 审稿人在邀请有效期内未响应，系统自动通知编辑并标记为"邀请超时"
- 任务状态在首次成功分配后从"待分配"变更为"已分配"
- 审稿人接受邀请后，任务状态变更为"审稿中"（首个审稿人接受时触发）
- 编辑部可随时补充分配新的审稿人（在已分配状态下也可追加）

#### 2.3.3 任务追踪（状态机）

**功能说明**：通过标准化状态机管理审稿任务的全生命周期，所有状态变更可追溯。

**状态机定义**：

```
┌──────────────┐
│   待分配      │ ← 任务创建后初始状态
│ (PENDING)    │
└──────┬───────┘
       │ 编辑部分配审稿人
       ▼
┌──────────────┐
│   已分配      │ ← 审稿人已收到邀请，等待接受/拒绝
│ (ASSIGNED)   │
└──────┬───────┘
       │ 首位审稿人接受邀请
       ▼
┌──────────────┐
│   审稿中      │ ← 审稿人正在审稿，部分可能已提交
│ (REVIEWING)  │
└──────┬───────┘
       │ 全部审稿人提交意见 / 编辑强制提前汇总
       ▼
┌──────────────┐
│   已提交      │ ← 所有审稿意见已提交，等待汇总
│ (SUBMITTED)  │
└──────┬───────┘
       │ 编辑部触发汇总操作
       ▼
┌──────────────┐
│   已汇总      │ ← 汇总报告已生成，等待终审决策
│ (SUMMARIZED) │
└──────┬───────┘
       │ 编辑部录入终审决策
       ▼
┌──────────────┐
│   已决策      │ ← 终审决策已录入，流程结束
│ (DECIDED)    │
└──────────────┘
```

**状态流转规则**：

| 当前状态 | 目标状态 | 触发条件 | 操作者 |
|---------|---------|---------|--------|
| 待分配 | 已分配 | 编辑部成功分配至少1位审稿人 | 编辑部 |
| 已分配 | 审稿中 | 首位审稿人接受邀请 | 系统（自动） |
| 已分配 | 待分配 | 所有审稿人均拒绝邀请 | 系统（自动） |
| 审稿中 | 已提交 | 全部已接受的审稿人均提交意见 | 系统（自动） |
| 审稿中 | 已提交 | 编辑部强制提前汇总（至少1份意见已提交） | 编辑部 |
| 已提交 | 已汇总 | 编辑部触发汇总报告生成 | 编辑部 |
| 已汇总 | 已决策 | 编辑部录入终审决策 | 编辑部 |
| 已决策 | 审稿中 | 退稿重审（作者返修后重新审稿） | 编辑部 |

**异常状态处理**：

| 异常场景 | 处理方式 |
|---------|---------|
| 审稿人拒绝邀请 | 系统通知编辑，编辑可重新分配新审稿人；任务状态不变 |
| 邀请超时未响应 | 系统自动标记该审稿人"邀请超时"，通知编辑重新分配 |
| 审稿超时未提交 | 系统在截止前3天/1天分别发送提醒；超时后通知编辑，编辑可选择延期或重新分配 |
| 全部审稿人拒绝/超时 | 任务自动回退至"待分配"状态，通知编辑 |
| 编辑强制提前汇总 | 需填写提前汇总原因，至少1份审稿意见已提交方可操作 |

#### 2.3.4 进度可视化

**功能说明**：根据不同角色展示差异化的进度信息，在保护审稿隐私的前提下提供最大透明度。

**编辑部视图（全量信息）**：
- **稿件看板**：以看板形式展示所有稿件及其当前状态，支持按状态/学科/截止日期/超时风险筛选
- **稿件详情**：查看每个稿件下所有审稿人的状态（已邀请/已接受/已拒绝/审稿中/已提交/超时），含每位审稿人的截止日期和进度
- **超时预警**：高亮显示距离截止日期≤3天的审稿任务，红色标记已超时任务
- **统计概览**：显示当前在审稿件数、待分配稿件数、超时任务数等关键指标

**审稿人视图（个人任务）**：
- **任务列表**：展示所有分配给自己的审稿任务，含标题、截止日期、状态、倒计时
- **优先级排序**：按截止日期紧迫度自动排序，超时风险高的任务置顶高亮
- **截止提醒**：截止前7天/3天/1天分级提醒（站内消息+邮件）；截止当天红色高亮
- **任务详情**：点击任务进入审稿工作台，查看稿件、填写审稿表单（关联功能2）

**作者视图（稿件进度）**：
- **进度时间线**：以时间线形式展示稿件当前所处阶段及各阶段时间节点
- **细粒度状态**：展示具体阶段（分配审稿人中[N/M位已接受] → 审稿人审稿中[N/M位已提交] → 意见汇总中 → 终审决策中）
- **预计时间**：根据截止日期显示预计完成时间
- **结果查看**：审稿完成后查看终审决策和审稿意见（经编辑部发布后可见）

**作者可见状态映射**：

| 内部状态 | 作者可见状态 | 显示信息 |
|---------|-------------|---------|
| 待分配 | "正在为您匹配合适的审稿人" | 预计分配时间 |
| 已分配 | "审稿人邀请中（已邀请X位，X位已接受）" | 预计审稿开始时间 |
| 审稿中 | "审稿人审稿中（X/X位已提交意见）" | 最近截止日期 |
| 已提交 | "审稿意见汇总中" | 预计汇总完成时间 |
| 已汇总 | "编辑部终审决策中" | 预计决策完成时间 |
| 已决策 | "审稿已完成" | 终审决策结果 + 审稿意见 |

#### 输出定义

| 输出项 | 接收方 | 格式 | 说明 |
|--------|--------|------|------|

| 超时预警 | 编辑部 | 通知+看板高亮 | 截止前3天/1天/超时 |
| 截止提醒 | 审稿人 | 站内消息+邮件 | 截止前7天/3天/1天 |
| 状态变更通知 | 相关角色 | 站内消息+邮件 | 关键状态变更时触发 |
| 终审结果 | 作者 | 结构化页面 | 决策结果+审稿意见（经发布后） |

### 2.5 交互逻辑（核心操作流程）

#### 流程1：编辑部创建并分配审稿任务

```
[编辑部首页]
    │
    ├─ 点击「创建审稿任务」
    │
    ▼
[任务创建表单]
```

### 2.6 边界条件（异常处理）

| 异常场景 | 触发条件 | 处理逻辑 | 通知对象 |
|---------|---------|---------|---------|
| **审稿人拒绝邀请** | 审稿人在邀请有效期内点击"拒绝" | 1. 标记该审稿人状态为"已拒绝"；2. 系统通知编辑部；3. 编辑部可重新分配新审稿人；4. 任务状态不变 | 编辑部 |
| **邀请超时未响应** | 审稿人在邀请有效期（默认3天）内未接受也未拒绝 | 1. 标记该审稿人状态为"邀请超时"；2. 系统通知编辑部；3. 编辑部可重新分配或延期 | 编辑部 |
| **审稿超时未提交** | 审稿人接受邀请后未在截止日期前提交意见 | 1. 截止前7天/3天/1天系统自动发送提醒；2. 超时后标记"审稿超时"，通知编辑；3. 编辑可选择：延期（设置新截止日期）/重新分配/强制提前汇总 | 审稿人→编辑部 |
| **全部审稿人拒绝或超时** | 稿件所有已分配审稿人均拒绝邀请或超时未响应 | 1. 任务自动回退至"待分配"状态；2. 系统通知编辑部并建议重新分配 | 编辑部 |
| **退稿重审** | 终审决策为"大修"或"小修"，作者返修后需重新审稿 | 1. 编辑部在"已决策"状态点击"发起返修重审"；2. 任务状态回退至"审稿中"；3. 可选择原审稿人或新审稿人；4. 审稿人可见"返修稿"标记和前次审稿意见 | 编辑部→审稿人→作者 |
| **编辑部强制提前汇总** | 部分审稿人已提交但仍有未提交，编辑决定提前汇总 | 1. 需至少1份审稿意见已提交；2. 需填写提前汇总原因；3. 未提交的审稿人标记为"未提交-已汇总"；4. 任务状态推进至"已提交" | 未提交的审稿人 |
| **稿件文件格式错误** | 上传非PDF文件或文件超过20MB | 1. 上传时即时校验；2. 提示"仅支持PDF格式，文件不超过20MB"；3. 阻止上传 | 编辑部 |
| **截止日期设置不合理** | 截止日期早于当前日期+7天 | 1. 表单校验拦截；2. 提示"截止日期需至少在7天后" | 编辑部 |
| **并发操作冲突** | 两位编辑同时对同一任务进行操作 | 1. 采用乐观锁机制；2. 后提交者收到"任务已被他人更新"提示；3. 需刷新后重试 | 编辑部 |

## 三、功能2：结构化审稿表单（优先级2）

### 3.1 功能描述

**对应用研痛点**：P2（审稿意见格式不统一）

**功能目标**：提供结构化的审稿表单，预设标准审稿维度和评分机制，引导审稿人按统一格式输出审稿意见。同时支持编辑部轻量自定义审稿维度，在标准化和灵活性之间取得平衡。解决审稿人提交意见格式各异（自由文本/分维度/仅评分）、编辑部需1-2小时手动整理的问题。

**核心价值**：
- 审稿人：降低"不知道从何评起"的认知负担，尤其帮助新手审稿人快速上手
- 编辑部：统一审稿意见格式，为后续意见汇总（功能3）提供结构化数据基础，免去手动整理
- 作者：获得格式清晰、维度明确的审稿意见，准确理解修改方向

**依赖关系**：依赖功能1（审稿任务管理）——审稿表单在审稿任务中由审稿人填写，表单数据关联到具体审稿任务。

### 3.2 用户故事

#### 审稿人视角
> **US-R-05**：作为一名审稿人，我希望审稿表单有清晰的维度引导和评分标准说明，这样我就知道应该从哪些角度评价论文，不用从零开始思考。

> **US-R-06**：作为一名审稿人（尤其新手），我希望每个维度有评分指引和示例说明，帮助我判断什么样的论文给几分，降低评分主观性。

> **US-R-07**：作为一名审稿人，我希望表单支持分多次填写和自动保存，因为我通常利用碎片时间审稿，需要随时中断和继续。

#### 编辑部视角
> **US-E-06**：作为一名编辑，我希望系统提供预设的标准审稿维度模板，开箱即用，不需要每次从头配置。

> **US-E-07**：作为一名编辑，我希望能根据期刊/学科特点自定义审稿维度（增加/删除/修改维度），但保持统一的数据结构，这样不同期刊的审稿意见仍可横向对比。

> **US-E-08**：作为一名编辑，我希望审稿人提交的表单数据是结构化的（维度+评分+文字），而不是自由文本，这样汇总时可以自动对齐对比。

#### 作者视角
> **US-A-04**：作为一名作者，我希望收到的审稿意见是按维度结构化呈现的（如"研究意义：4分，评价：..."），而不是一段混沌的文字，这样我能准确理解每个方面的评价和修改方向。

### 3.3 功能拆解

#### 3.3.1 审稿维度模板

**功能说明**：预设标准审稿维度模板，审稿人按维度逐一评价，确保审稿意见结构统一。

**预设四维模板**：

| 维度编号 | 维度名称 | 评价说明 | 评分指引 |
|---------|---------|---------|---------|
| D1 | 研究意义 | 评估论文研究问题的学术价值、理论贡献和现实意义。研究是否 addressed 重要问题？结论是否有价值？ | 5=意义重大，具有突出理论或实践贡献；4=意义较大，有一定贡献；3=意义一般，有一定价值；2=意义较小，贡献有限；1=意义极小或无贡献 |
| D2 | 创新性 | 评估论文的研究视角、方法、结论的新颖程度。是否有原创性贡献？与已有文献的区分度如何？ | 5=高度创新，开辟新视角或新方法；4=有明确创新点；3=有一定新意但不突出；2=创新性不足，主要重复已有工作；1=无创新 |
| D3 | 研究方法 | 评估研究设计、数据采集、分析方法、论证逻辑的合理性和严谨性。方法是否适当？论证是否充分？ | 5=方法严谨，设计合理，论证充分；4=方法较好，个别可改进；3=方法基本合理但有明显不足；2=方法存在较大问题；1=方法严重不当 |
| D4 | 写作水平 | 评估论文的结构组织、语言表达、文献引用规范、图表呈现质量。 | 5=结构清晰，语言精炼，规范完善；4=写作良好，个别可改进；3=写作一般，需较多修改；2=写作较差，影响理解；1=写作极差，无法理解 |

**模板配置规则**：
- 预设四维模板为系统默认模板，适用于大多数学科
- 编辑部可基于预设模板创建期刊/学科专属模板
- 自定义模板操作：增加维度（最多8个）/删除维度（最少2个）/修改维度名称和说明/调整维度顺序
- 每个维度必须包含：维度名称、评价说明、评分指引
- 模板一经使用（关联审稿任务）后不可修改，如需变更需创建新版本

#### 3.3.2 评分机制

**功能说明**：每个维度采用"1-5分整数评分+文字说明"的双重评价机制，确保评分可量化、意见可理解。

**评分规则**：

| 规则项 | 说明 |
|--------|------|
| 评分范围 | 1-5分，整数 |
| 评分含义 | 5=优秀，4=良好，3=一般，2=较差，1=极差 |
| 评分约束 | 必须选择评分，不可为空 |
| 文字说明 | 每个维度必须填写文字说明，最少50字，最多2000字 |
| 文字说明引导 | 表单中展示该维度的评价说明和评分指引，引导审稿人针对性撰写 |
| 自动保存 | 审稿人填写过程中每60秒自动保存草稿，防止数据丢失 |

**评分校验**：
- 提交前校验所有维度评分均已选择，文字说明均达到最低字数要求
- 未通过校验的维度高亮提示，阻止提交

#### 3.3.3 总体评价

**功能说明**：在各维度评价基础上，审稿人给出总体推荐意见和综合评语，作为编辑终审决策的直接参考。

**总体推荐意见（必选其一）**：

| 推荐编号 | 推荐意见 | 说明 |
|---------|---------|------|
| R1 | 接收（Accept） | 稿件质量优良，无需修改即可录用 |
| R2 | 小修（Minor Revision） | 稿件基本合格，需少量修改后可录用 |
| R3 | 大修（Major Revision） | 稿件有价值但存在较多问题，需大幅修改后重新评审 |
| R4 | 拒稿（Reject） | 稿件存在根本性问题，不建议录用 |

**综合评语（必填）**：
- 字数要求：最少100字，最多3000字
- 内容引导：建议审稿人综合说明推荐理由、主要优点、主要问题、修改建议
- 提供结构化引导提示："请综合以上各维度评价，说明您的总体推荐理由、论文主要优点、需要修改的核心问题及具体修改建议。"

**修改建议（可选）**：
- 审稿人可逐条列出具体修改建议
- 每条修改建议包含：建议类型（内容/方法/格式/其他）+ 建议内容文本
- 修改建议将单独结构化展示给作者，便于逐条对照修改

#### 3.3.4 模板配置

**功能说明**：编辑部可创建、编辑和管理审稿模板，在创建审稿任务时关联使用。

**模板管理功能**：

| 操作 | 说明 | 权限 |
|------|------|------|
| 创建模板 | 基于预设模板或空白创建新模板，定义维度、评分指引、文字说明引导 | 编辑部 |
| 编辑模板 | 修改未使用模板的维度配置 | 编辑部 |
| 复制模板 | 从已有模板复制创建新模板，在此基础上修改 | 编辑部 |
| 启用/停用 | 停用的模板不可在新任务中关联，已关联的不受影响 | 编辑部 |
| 版本管理 | 模板修改后生成新版本，旧版本保留可追溯 | 系统（自动） |

**模板数据结构统一性要求**：
- 无论自定义维度如何变化，所有模板输出的审稿意见数据结构一致（维度数组+总体评价+修改建议）
- 维度数组中每个元素包含：维度编号、维度名称、评分、文字说明
- 这一统一数据结构是功能3（审稿意见汇总）能自动对齐对比的前提

### 3.4 输入输出定义

#### 输入定义

| 输入项 | 来源 | 格式 | 约束 |
|--------|------|------|------|
| 各维度评分 | 审稿人选择 | 整数（1-5） | 必填，每个维度必选 |
| 各维度文字说明 | 审稿人填写 | 长文本 | 必填，50-2000字/维度 |
| 总体推荐意见 | 审稿人选择 | 枚举（R1-R4） | 必选其一 |
| 综合评语 | 审稿人填写 | 长文本 | 必填，100-3000字 |
| 修改建议 | 审稿人填写 | 结构化列表 | 可选，每条含类型+内容 |
| 审稿模板配置 | 编辑部配置 | 结构化模板 | 维度2-8个，每维度含名称/说明/评分指引 |

#### 输出定义

## 四、功能3：审稿意见汇总（优先级3）

### 4.1 功能描述

**对应用研痛点**：P3（多审稿人意见难以汇总对比）

**功能目标**：当一篇稿件的多位审稿人提交审稿意见后，系统自动按维度聚合多审稿人评分和意见，标注评分分歧点，生成结构化汇总报告，并基于规则给出终审建议。解决编辑部手动阅读对比2-4份意见耗时2-3小时、且容易遗漏关键信息的问题。

**核心价值**：
- 编辑部：将2-3小时的手动汇总对比缩短至分钟级自动生成，快速定位分歧核心，辅助终审决策
- 作者：获得结构化的汇总反馈，清晰了解审稿人一致认可的优势和需要修改的问题

**核心差异化**：根据用研报告竞品分析（§3），三大竞品（ScholarOne、Editorial Manager、OpenReview）在审稿意见汇总对比功能上**均缺失**，这是本产品的核心差异化能力。

**依赖关系**：依赖功能1（审稿任务管理）提供审稿人和任务数据 + 功能2（结构化审稿表单）提供结构化审稿意见数据。

### 4.2 用户故事

#### 编辑部视角
> **US-E-09**：作为一名编辑，当所有审稿人提交意见后，我希望系统能自动生成一份汇总报告，将多份意见按维度对齐对比，而不是让我逐份阅读手动整理。

> **US-E-10**：作为一名编辑，我希望系统能自动标注审稿人评分差异大的维度（如某维度一位给5分另一位给2分），这样我能快速定位分歧核心，聚焦讨论重点。

> **US-E-11**：作为一名编辑，我希望系统能基于审稿人意见自动生成一个终审建议（如"多数接收""分歧需讨论"），作为我决策的参考，而不是完全从零开始判断。

> **US-E-12**：作为一名编辑，我希望汇总报告能清晰展示审稿人一致认可的优点和一致指出的问题，这样我能快速把握稿件的共识评价。

#### 作者视角
> **US-A-05**：作为一名作者，我希望审稿结束后能看到一份汇总的审稿意见，清楚知道审稿人们对我的论文在不同维度上的评价是否一致，哪些方面是共识需要修改，哪些方面存在分歧。

> **US-A-06**：作为一名作者，当审稿人意见存在分歧时，我希望终审决策能说明编辑的判断依据，而不仅仅是一个结论，这样我能理解为什么最终做出了这个决定。

### 4.3 功能拆解

#### 4.3.1 意见聚合

**功能说明**：按审稿维度自动对齐多审稿人的评分和文字意见，生成结构化对比数据。

**聚合逻辑**：
1. 读取该稿件所有已提交的审稿意见（结构化JSON数据）
2. 按维度编号对齐：将不同审稿人在同一维度上的评分和文字说明排列对比
3. 聚合总体推荐意见：统计各审稿人的推荐意见分布
4. 聚合修改建议：将各审稿人的修改建议按类型分类汇总

**聚合输出结构**：

| 聚合项 | 输出内容 |
|--------|---------|
| 维度对比表 | 每个维度的各审稿人评分、平均分、评分范围、各审稿人文字意见摘要 |
| 总体推荐分布 | 各推荐意见（接收/小修/大修/拒稿）的票数和占比 |
| 修改建议汇总 | 按类型（内容/方法/格式/其他）归类的所有修改建议列表 |
| 综合评语汇总 | 各审稿人综合评语的原文展示 |

#### 4.3.2 分歧标注

**功能说明**：自动识别审稿人评分差异较大的维度并高亮标注，帮助编辑快速定位分歧核心。

**分歧识别规则**：

| 判定条件 | 标注级别 | 展示方式 |
|---------|---------|---------|
| 同一维度评分最大值-最小值 ≥ 3 | 🔴 严重分歧 | 红色高亮+⚠️图标+标注分差 |
| 同一维度评分最大值-最小值 = 2 | 🟡 明显分歧 | 黄色高亮+标注分差 |
| 同一维度评分最大值-最小值 ≤ 1 | 🟢 基本一致 | 绿色标记 |
| 总体推荐意见出现"接收"与"拒稿"并存 | 🔴 严重分歧 | 红色高亮+特殊标注"推荐意见对立" |

**分歧详情展示**：
- 分歧维度展开后显示各审稿人的具体评分和文字说明
- 标注分差值（如"审稿人A: 5分 vs 审稿人B: 2分，分差=3"）
- 分歧维度的文字意见并排对比，便于编辑快速阅读理解分歧原因

#### 4.3.3 汇总报告生成

**功能说明**：将聚合数据和分歧标注组合生成结构化汇总报告，供编辑部决策参考。

**汇总报告结构**：


#### 4.3.4 终审建议

**功能说明**：基于审稿人评分和推荐意见，通过规则引擎自动生成推荐结论，辅助编辑决策。

**终审建议规则引擎**：

| 规则编号 | 触发条件 | 建议结论 | 说明 |
|---------|---------|---------|------|
| Rule-1 | 全部审稿人推荐"接收" | ✅ 全票接收 | 所有审稿人一致认可，建议接收 |
| Rule-2 | 多数（≥2/3）推荐"接收"或"小修"，无"拒稿" | ✅ 多数接收 | 多数审稿人认可，建议接收或小修后接收 |
| Rule-3 | 多数推荐"接收"或"小修"，但有"大修"或"拒稿" | ⚠️ 倾向接收但需讨论 | 多数认可但存在异议，建议编辑讨论后决策 |
| Rule-4 | 推荐意见分散（接收/大修/拒稿均有） | ⚠️ 分歧需讨论 | 审稿人意见严重分歧，建议编辑综合判断或增加审稿人 |
| Rule-5 | 多数推荐"大修"，无"拒稿" | 🔄 建议大修 | 多数认为需大幅修改，建议大修后重新评审 |
| Rule-6 | 多数（≥2/3）推荐"拒稿" | ❌ 建议拒稿 | 多数审稿人建议拒稿 |
| Rule-7 | 存在"接收"与"拒稿"并存 | ⚠️ 严重分歧需讨论 | 推荐意见对立，建议编辑重点关注分歧维度或增加审稿人 |

**附加评分维度建议**：
- 除推荐意见规则外，系统还计算各维度平均分作为辅助参考
- 平均分≥4.0的维度标注为"优势维度"
- 平均分≤2.5的维度标注为"薄弱维度"
- 生成总结性建议语："该稿件在[优势维度]方面表现突出，但在[薄弱维度]方面存在不足，综合审稿人推荐意见，建议[终审建议]。"

**重要声明**：系统终审建议仅为辅助参考，最终决策权在编辑部。编辑可在建议基础上做出不同决策，但需填写决策说明。

### 4.6 边界条件

| 异常场景 | 触发条件 | 处理逻辑 |
|---------|---------|---------|
| **仅1位审稿人提交** | 编辑部强制提前汇总，仅1份审稿意见 | 1. 可生成报告但标注"仅1份意见，对比功能受限"；2. 不执行分歧标注（无对比对象）；3. 终审建议标注"仅供参考，建议补充审稿人意见" |
| **部分审稿人使用不同模板** | 不同审稿人关联了不同模板，维度不完全一致 | 1. 以维度编号为基准对齐；2. 对不存在的维度标注"该审稿人未评价此维度"；3. 在报告中注明模板差异 |
| **审稿人全部给出相同推荐** | 全票接收或全票拒稿 | 正常生成报告，分歧标注全部为🟢，终审建议为"全票接收"或"建议拒稿" |
| **规则引擎无法判定** | 审稿人推荐意见分布无法匹配任何规则 | 终审建议显示"无法自动判定，请编辑综合判断"，提供全部原始数据供参考 |
| **报告生成后审稿人补充意见** | 报告已生成但有审稿人补交意见 | 1. 需编辑手动触发"重新生成汇总报告"；2. 旧报告归档保留；3. 新报告标注更新时间和变更内容 |
| **编辑决策与系统建议不一致** | 编辑录入的决策与系统建议不同 | 正常允许，但需填写决策说明（≥100字），说明与建议不一致的原因 |
| **维度自定义导致无法对齐** | 自定义维度在不同审稿人间完全不重叠 | 以维度编号对齐，完全不重叠时报告标注"维度差异较大，对比价值有限" |

## 五、功能4：审稿知识库（优先级4）

### 5.1 功能描述

**对应用研痛点**：P4（审稿经验难以复用积累）

**功能目标**：将已完成的审稿意见和模板结构化归档，支持按学科/关键词/评分等维度检索复用，帮助审稿人（尤其新手）参考历史案例提升审稿效率和质量，帮助编辑部积累审稿数据资产。在P0阶段定位为基础架构搭建+最小可用版本。

**核心价值**：
- 审稿人：参考历史审稿案例和模板，降低审稿认知负担，新手审稿时间可从6小时缩短至2-3小时
- 编辑部：积累审稿数据资产，为后续审稿人能力评估和模板优化提供数据基础

**核心差异化**：根据用研报告竞品分析（§3），三大竞品在审稿知识库功能上**均缺失**（OpenReview仅有被动公开归档，无主动检索和模板复用），是本产品的长期竞争壁垒。

**依赖关系**：依赖功能1-3产生的数据（审稿任务/审稿意见/汇总报告/审稿模板）作为知识库数据来源。

**P0阶段定位**：根据用研报告§4.4，知识库存在数据冷启动问题，P0阶段应完成基础架构设计和最小可用版本，在后续迭代中持续丰富。

### 5.2 用户故事

#### 审稿人视角
> **US-R-08**：作为一名新手审稿人，我希望能在审稿前搜索同领域的历史审稿案例，了解有经验的审稿人是如何评价类似论文的，这样能帮助我快速建立审稿框架。

> **US-R-09**：作为一名审稿人，我希望在填写审稿表单时能一键参考相关的历史审稿意见和模板，获得撰写灵感，不用完全从零开始。

> **US-R-10**：作为一名审稿人，我希望知识库中的审稿意见是匿名化的，我看不到原作者和原审稿人身份，这样既保护了隐私又能学习经验。

#### 编辑部视角
> **US-E-13**：作为一名编辑，我希望已完成的审稿意见能自动归档到知识库，按学科和关键词分类，而不需要我手动整理。

> **US-E-14**：作为一名编辑，我希望能检索历史审稿数据，了解某学科领域的审稿常见问题和评价标准，用于优化审稿模板和培训审稿人。

> **US-E-15**：作为一名编辑，我希望能在知识库中管理审稿模板（创建/编辑/复用），这样不同期刊和学科可以维护自己的模板库。

#### 作者视角
> （注：知识库功能主要面向审稿人和编辑部，作者在P0阶段无直接交互需求。作者通过功能1查看审稿意见，不直接使用知识库。）

### 5.3 功能拆解

#### 5.3.1 审稿意见归档

**功能说明**：已完成的审稿意见在终审决策后自动入库，按学科/关键词分类存储。

**自动归档触发**：审稿任务状态变更为"已决策"时，系统自动将以下数据归档：
- 审稿意见（含各维度评分和文字说明）
- 总体推荐意见和综合评语
- 修改建议
- 汇总报告
- 关联的审稿模板

**归档处理**：
- **匿名化处理**：移除作者身份信息和审稿人身份信息，仅保留学科领域、稿件类型、关键词、评分数据和文字意见
- **分类标签**：自动打标签——学科领域、稿件类型、关键词、评分区间、推荐意见
- **去重检查**：检查是否已存在高度相似的归档条目（相同稿件的不同轮次审稿合并为一条）

**归档数据结构**：
```
KnowledgeItem {
  id: 知识库条目ID
  subject: 学科领域
  manuscriptType: 稿件类型
  keywords: 关键词数组
  reviewDate: 审稿日期
  reviewMode: 审稿模式（单盲/双盲）
  dimensions: [
    {
      dimensionName: 维度名称
      scores: 各审稿人评分数组（匿名化）
      avgScore: 平均分
      opinions: 各审稿人文字意见数组（匿名化）
    }
  ]
  recommendations: 各审稿人推荐意见分布
  summaryReport: 汇总报告（匿名化）
  templateUsed: 使用的模板信息
  finalDecision: 终审决策
}
```

#### 5.3.2 模板管理

**功能说明**：审稿模板的创建、编辑、复用管理，作为知识库的组成部分。

**模板管理功能**：

| 操作 | 说明 | 权限 |
|------|------|------|
| 查看模板库 | 浏览所有可用模板，按学科/使用频次排序 | 审稿人（查看）、编辑部（查看+管理） |
| 创建模板 | 基于预设模板或空白创建新模板 | 编辑部 |
| 编辑模板 | 修改未使用模板的配置 | 编辑部 |
| 复用模板 | 从知识库中选取合适模板关联到审稿任务 | 编辑部 |
| 标记推荐 | 编辑部可标记优质模板为"推荐模板" | 编辑部 |
| 使用统计 | 查看模板被使用次数和关联审稿意见 | 编辑部 |

**模板与知识库关联**：
- 每个模板记录使用次数、平均评分分布、关联的审稿意见条目
- 审稿人在填写审稿表单时可查看关联模板的历史使用统计（"该模板已使用N次，平均评分分布..."）

#### 5.3.3 检索功能

**功能说明**：支持按多维度检索历史审稿意见，帮助审稿人和编辑部快速找到参考案例。

**检索条件**：

| 检索维度 | 类型 | 说明 |
|---------|------|------|
| 关键词 | 全文检索 | 搜索审稿意见文字内容中的关键词 |
| 学科领域 | 枚举筛选 | 按一级学科分类筛选 |
| 稿件类型 | 枚举筛选 | 研究论文/综述/案例研究等 |
| 评分区间 | 范围筛选 | 按某维度评分范围筛选（如创新性3-5分） |
| 推荐意见 | 枚举筛选 | 接收/小修/大修/拒稿 |
| 审稿日期 | 日期范围 | 按时间范围筛选 |
| 模板 | 关联筛选 | 按使用的审稿模板筛选 |

**检索结果展示**：
- 列表展示匹配的知识库条目，显示：学科/关键词/评分摘要/推荐意见/日期
- 点击条目查看详情：各维度评分和意见（匿名化）、汇总报告、修改建议
- 支持结果排序：按相关度/按时间/按评分

**检索权限**：
- 审稿人：可检索全部匿名化知识库条目
- 编辑部：可检索全部匿名化知识库条目 + 可查看与本期刊关联的条目来源信息

#### 5.3.4 权限控制

**功能说明**：确保双盲审稿的隐私保护，知识库中的所有数据均经过匿名化处理。

**匿名化规则**：

| 数据项 | 匿名化处理 |
|--------|-----------|
| 作者姓名/单位 | 移除，不可见 |
| 审稿人姓名/单位 | 移除，不可见 |
| 稿件标题 | 移除，替换为学科+关键词标签 |
| 稿件文件 | 不入库，仅存审稿意见数据 |
| 审稿意见文字 | 保留原文，但移除可能识别身份的信息（如"贵校""您团队"等指代） |
| 审稿日期 | 保留年份和月份，移除具体日期 |

**权限矩阵**：

| 操作 | 审稿人 | 编辑部 | 作者 |
|------|--------|--------|------|
| 检索知识库 | ✅ 全部匿名化条目 | ✅ 全部匿名化条目 | ❌ P0无权限 |
| 查看条目详情 | ✅ 匿名化内容 | ✅ 匿名化内容 | ❌ P0无权限 |
| 管理模板 | 🔍 仅查看 | ✅ 增删改查 | ❌ |
| 导出数据 | ❌ | ✅ 匿名化导出 | ❌ |
| 查看来源信息 | ❌ | ✅ 本期刊关联条目 | ❌ |

**安全措施**：
- 知识库数据与生产数据物理隔离（独立存储/独立索引）
- 匿名化处理在归档时一次性完成，不可逆
- 访问日志记录所有检索和查看操作

```
    ├─ 自动打标签（学科/类型/关键词/评分/推荐）
    │
    ├─ 去重检查
    │
    ├─ 写入知识库（独立存储）
    │
    └─ 归档完成（系统日志记录）
```

### 5.6 边界条件

| 异常场景 | 触发条件 | 处理逻辑 |
|---------|---------|---------|
| **知识库为空（冷启动）** | P0初期知识库无数据 | 1. 检索结果为空时显示"暂无匹配案例，知识库将在审稿数据积累后逐步丰富"；2. 仍可使用预设模板和编辑部自定义模板 |
| **匿名化不彻底** | 文字意见中残留可识别身份的信息 | 1. 归档时自动扫描关键词列表（如"贵校""您团队"等指代词）；2. 命中关键词的文字段标记待审核；3. 编辑部审核后确认归档或退回修改 |
| **检索结果过多** | 检索条件宽松导致返回大量结果 | 1. 默认分页显示（每页20条）；2. 提示"结果较多，建议增加筛选条件缩小范围"；3. 支持结果内二次搜索 |
| **检索结果为零** | 无匹配的知识库条目 | 显示"暂无匹配案例"，推荐使用预设模板或放宽检索条件 |
| **模板被删除但有关联条目** | 编辑部删除模板但知识库中有使用该模板的条目 | 1. 知识库条目保留（使用模板快照）；2. 模板列表中标记"已停用"；3. 不影响历史数据检索 |
| **归档失败** | 数据异常导致自动归档失败 | 1. 记录失败日志；2. 系统通知编辑部；3. 编辑部可手动触发重新归档 |
| **导出数据量过大** | 编辑部尝试导出大量知识库数据 | 1. 单次导出上限1000条；2. 超限时提示分批导出；3. 导出数据均为匿名化 |

### 5.7 验收标准

### 6.3 实体关系说明

| 关系 | 类型 | 说明 |
|------|------|------|
| ReviewTask → Reviewer | 1:N | 一个任务可分配多位审稿人 |
| ReviewTask → ReviewForm | 1:1 | 一个任务关联一个审稿表单（基于模板生成） |
| ReviewTask → Template | N:1 | 多个任务可使用同一模板（使用快照） |
| Reviewer → ReviewOpinion | 1:1 | 一位审稿人提交一份审稿意见 |
| ReviewForm → ReviewOpinion | 1:N | 一个表单对应多位审稿人的意见 |
| ReviewTask → SummaryReport | 1:1 | 一个任务生成一份汇总报告 |
| SummaryReport → KnowledgeItem | 1:1 | 汇总报告匿名化后归档为知识库条目 |
| Template → ReviewForm | 1:N | 一个模板可被多个表单使用 |

## 附录B：术语表

| 术语 | 说明 |
|------|------|
| 单盲审稿（Single Blind） | 审稿人知道作者身份，作者不知道审稿人身份 |
| 双盲审稿（Double Blind） | 审稿人和作者互不知道对方身份 |
| 终审决策 | 编辑部基于审稿人意见做出的最终稿件处理决定（接收/小修/大修/拒稿） |
| 返修重审 | 作者根据审稿意见修改后重新提交，编辑部安排新一轮审稿 |
| 分歧标注 | 系统自动识别多审稿人评分差异≥2分的维度并高亮标注 |
| 状态机 | 审稿任务从创建到完成的状态流转模型 |
| 匿名化 | 移除数据中可识别个人身份的信息，保护审稿人和作者隐私 |
| 冷启动 | 知识库在初期无数据积累，功能价值暂时无法充分体现的阶段 |
| 预设四维模板 | 系统内置的标准审稿模板，包含研究意义、创新性、研究方法、写作水平四个维度 |
| 终审建议规则引擎 | 基于审稿人推荐意见分布，通过预设规则自动生成推荐结论的系统 |
