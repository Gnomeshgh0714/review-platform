## 二、实质性问题清单

### Q1：状态机存在不可达/死锁路径——REVIEWING状态下全部审稿人超时后无合法回退路径

| 项目 | 内容 |
|------|------|
| **问题编号** | Q1 |
| **问题级别** | 严重 |
| **问题类别** | 逻辑漏洞 |
| **PRD位置** | §2.3.3 状态流转规则表 + §2.6 异常状态处理表 |

**问题描述**：

PRD在§2.3.3状态流转规则表中定义了以下合法状态转换：

- `已分配 → 待分配`：所有审稿人均拒绝邀请
- `审稿中 → 已提交`：全部已接受的审稿人均提交意见 / 编辑强制提前汇总

异常处理表（§2.6）中定义"全部审稿人拒绝或超时"时"任务自动回退至'待分配'状态"。但状态流转规则表中**没有定义 `审稿中(REVIEWING) → 待分配(PENDING)` 的转换路径**。

考虑以下场景：
1. 编辑分配3位审稿人，审稿人A接受 → 任务进入REVIEWING状态
2. 审稿人B、C拒绝邀请
3. 审稿人A接受后审稿超时（OVERDUE）
4. 此时全部审稿人要么拒绝、要么超时，但任务处于REVIEWING状态，而非ASSIGNED状态

此时系统应将任务回退到PENDING，但状态流转规则表中REVIEWING状态仅有两个出口（→已提交），**没有REVIEWING→PENDING的转换定义**。系统要么无法处理此异常（任务卡死在REVIEWING），要么违反状态机定义执行未定义的转换。

此外，`已决策 → 审稿中`（退稿重审）也仅定义了流转方向，未定义已提交的旧审稿意见如何处理——是保留还是清除？数据一致性无保障。

**改进建议**：
1. 在状态流转规则表中增加 `审稿中 → 待分配` 转换路径，触发条件为"全部已接受审稿人超时且无可提交意见"；
2. 明确REVIEWING状态下部分审稿人已提交意见后、其余全部超时时的处理：应允许编辑选择"基于已提交意见强制汇总"或"回退到待分配（已提交意见保留为历史记录）"；
3. 明确退稿重审时历史审稿意见的数据处置策略（保留/归档/清除），并在ReviewOpinion实体中增加`round`（审稿轮次）字段。

### Q2：跨模板维度对齐逻辑存在根本性错误——以dimensionId做跨模板对齐将导致数据错乱

| 项目 | 内容 |
|------|------|
| **问题编号** | Q2 |
| **问题级别** | 严重 |
| **问题类别** | 逻辑漏洞 |
| **PRD位置** | §4.3.1 意见聚合逻辑 + §4.6 边界条件"部分审稿人使用不同模板" + §6.2.3 Dimension子结构定义 |

**问题描述**：

PRD §4.3.1聚合逻辑第2条："按维度编号对齐：将不同审稿人在同一维度上的评分和文字说明排列对比"。§4.6边界条件"部分审稿人使用不同模板"处理逻辑第1条："以维度编号为基准对齐"。

但§6.2.3中Dimension子结构的`dimensionId`定义为"必填，模板内唯一"——即dimensionId**仅在模板范围内唯一**，不同模板可以使用相同的dimensionId（如"D1"）但表示完全不同的维度。

考虑以下场景：
- 模板A（自定义）：D1=研究意义，D2=方法论严谨性，D3=文献综述质量
- 模板B（自定义）：D1=实验设计，D2=数据分析，D3=结论可靠性

当审稿人1使用模板A、审稿人2使用模板B时，系统按dimensionId对齐会将"研究意义"与"实验设计"对比、"方法论严谨性"与"数据分析"对比，**生成完全错误的对比结果**，且编辑可能基于错误对比做出终审决策。

虽然PRD在§2.3.1任务创建中规定"审稿模板"为可选字段且"未指定则使用学科默认模板"，暗示同一任务应使用同一模板。但§4.6明确考虑了"不同审稿人使用不同模板"的场景并给出了对齐方案，说明PRD认为跨模板对齐是可能发生的——而给出的对齐方案是错误的。

**改进建议**：
1. 在任务分配时**强制统一模板**：一篇稿件的所有审稿人必须使用同一模板（任务创建时确定模板，分配审稿人时自动关联），从根源上消除跨模板对齐问题；
2. 如确需支持同一任务不同审稿人使用不同模板（当前PRD无此需求场景），则不能使用dimensionId对齐，应改为以dimensionName做模糊匹配并人工确认，或直接标注"维度不同无法对齐"；
3. 删除§4.6中"以维度编号为基准对齐"的处理逻辑，替换为"同一任务强制使用同一模板，不存在跨模板对齐场景"。

### Q3：知识库匿名化方案不足以保障双盲安全——关键词过滤无法覆盖学术文本中的身份线索

| 项目 | 内容 |
|------|------|
| **问题编号** | Q3 |
| **问题级别** | 严重 |
| **问题类别** | 安全风险 |
| **PRD位置** | §5.3.4 权限控制-匿名化规则 + §5.6 边界条件"匿名化不彻底" |

**问题描述**：

PRD §5.3.4匿名化规则对"审稿意见文字"的处理为"保留原文，但移除可能识别身份的信息（如'贵校''您团队'等指代）"。§5.6边界条件"匿名化不彻底"的处理为"归档时自动扫描关键词列表（如'贵校''您团队'等指代词）；命中关键词的文字段标记待审核"。

这一方案存在严重缺陷：

1. **关键词列表无法覆盖所有身份线索**：学术审稿意见中常见的身份线索包括但不限于：
   - 自引线索："The author's previous work (Smith et al., 2023)..."——通过自引可直接识别作者
   - 机构线索："The experimental setup appears similar to the facilities at [某具体机构特征]..."
   - 项目线索："This work appears to be funded by [某具体基金编号]..."
   - 方法线索：极为具体的方法论描述可能暗示作者所在团队的技术路线
   - 称谓线索：中文审稿中"张教授""李老师"等直接称谓

2. **关键词匹配方式过于简单**：基于固定关键词列表的扫描无法处理语义层面的身份推断。例如"该论文引用了12篇来自同一课题组的文献"虽然没有直接点名，但在小领域中足以推断身份。

3. **人工审核机制不完善**：§5.6仅说"编辑部审核后确认归档或退回修改"，但未定义：
   - 审核时限（知识库归档是否需要等待审核完成？）
   - 审核标准（编辑如何判断哪些内容构成身份线索？）
   - 审核责任归属（哪位编辑审核？是否需要双人复核？）
   - 漏审追责机制（如果编辑审核后仍泄露身份，责任如何界定？）

4. **匿名化不可逆但审核可逆**：§5.3.4声明"匿名化处理在归档时一次性完成，不可逆"，但§5.6又说"编辑部审核后确认归档或退回修改"——如果审核不通过需要退回修改，但匿名化已不可逆，如何"退回修改"？逻辑矛盾。

**改进建议**：
1. 将匿名化处理改为**两阶段**：第一阶段（自动）移除结构化身份字段（姓名、单位、标题等）；第二阶段（人工审核）在归档前审核文字内容的身份线索，审核通过后才执行不可逆归档；
2. 扩展自动扫描规则：除指代词外，增加自引检测（"author's previous work"等模式）、机构名检测（与已知机构数据库匹配）、基金编号格式检测等；
3. 明确审核流程：定义审核人、审核时限（如归档后48小时内）、审核结果（通过/退回修改/永久不归档）、双人复核机制；
4. 增加"高风险领域"标记：对于小众学科领域（审稿人圈子小，身份推断风险高），强制人工逐条审核文字意见后才可归档；
5. 增加"作者/审稿人投诉"机制：如知识库内容泄露身份，当事人可申请删除该条目。

### Q4：多审稿人并发提交时"全部已提交"状态判定存在竞态条件——可能导致任务状态卡死

| 项目 | 内容 |
|------|------|
| **问题编号** | Q4 |
| **问题级别** | 严重 |
| **问题类别** | 数据一致性 |
| **PRD位置** | §2.3.3 状态流转规则"审稿中→已提交"触发条件 + §2.6 "并发操作冲突" |

**问题描述**：

PRD §2.3.3定义状态转换规则：`审稿中 → 已提交`，触发条件为"全部已接受的审稿人均提交意见"，操作者为"系统（自动）"。

§2.6"并发操作冲突"仅处理"两位编辑同时对同一任务进行操作"的场景（乐观锁），**未处理多位审稿人同时提交审稿意见的并发场景**。

考虑以下竞态条件：
1. 稿件分配3位审稿人（A、B、C），均已接受，任务处于REVIEWING
2. 审稿人A已提交，B和C尚未提交
3. 审稿人B和C几乎同时点击"提交"：
   - 线程1（B提交）：校验通过→存储B的意见→检查"全部已提交？"→读取C状态为"未提交"→不触发状态变更
   - 线程2（C提交）：校验通过→存储C的意见→检查"全部已提交？"→读取B状态可能为"未提交"（取决于事务隔离级别）→不触发状态变更
4. 结果：B和C的意见均已存储，但任务状态仍停留在REVIEWING，**永远不会自动转为SUBMITTED**

这会导致：
- 编辑部看板不显示"已提交"状态，无法收到"进入汇总环节"的提示
- 作者看到的进度停留在"审稿人审稿中"
- 整个流程卡死，需编辑手动发现并干预

**改进建议**：
1. 在PRD中明确多审稿人并发提交的数据一致性保障策略，如：
   - **方案A（推荐）**：使用数据库事务+行锁，每次审稿意见提交时在事务内检查全部审稿人状态，满足条件则在同一事务内更新任务状态；
   - **方案B**：使用乐观锁+重试，提交后检查状态，如发现应触发状态变更但被其他事务抢先，则重试；
   - **方案C**：异步补偿——提交后发送事件到消息队列，消费者统一处理状态变更（最终一致性）；
2. 在§2.6边界条件表中新增"多审稿人并发提交"场景的处理逻辑；
3. 在验收标准中增加并发测试用例（AC-T-14：3位审稿人同时提交，任务状态正确变更为SUBMITTED）。

### Q5：数据模型缺失核心实体——无User/Account实体，用户身份与角色管理无定义

| 项目 | 内容 |
|------|------|
| **问题编号** | Q5 |
| **问题级别** | 严重 |
| **问题类别** | 边界遗漏 |
| **PRD位置** | §六 数据结构设计（§6.1-§6.3全部实体定义） |

**问题描述**：

PRD §6数据结构设计定义了7个核心实体（ReviewTask、Reviewer、ReviewForm、ReviewOpinion、SummaryReport、KnowledgeItem、Template），但**完全没有定义User/Account实体**。

这导致以下关键问题无法回答：

1. **用户身份从何而来**：ReviewTask.createdBy（创建人/编辑部用户ID）、Reviewer.reviewerUserId（审稿人用户ID）引用的"用户ID"指向哪个实体？没有User实体，这些外键引用是悬空的。

2. **用户角色如何确定**：PRD定义了三类角色（审稿人、编辑部、作者），但没有定义：
   - 角色是全局的（一个用户只能是审稿人/编辑部/作者之一）还是按任务上下文的（同一用户在不同稿件中角色不同）？
   - 在学术审稿中，编辑部本身也经常作为审稿人参与审稿（跨期刊甚至同期刊），一个用户同时具备"编辑部"和"审稿人"角色是常态。PRD的权限模型无法处理这种情况。
   
3. **作者如何进入系统**：§7.3流程图显示作者"登录平台→查看投稿列表"，但没有定义作者账号如何创建、作者与稿件的关联关系如何建立。ReviewTask实体中没有authorUserId字段——作者与审稿任务的关联关系在数据模型中完全缺失。

4. **审稿人库从何而来**：§2.3.2任务分配说"编辑从系统审稿人库中搜索和选择审稿人"，但审稿人库的数据结构未定义。Reviewer实体是"任务分配记录"（assignment），不是审稿人档案（profile）——审稿人的学科领域、研究方向、历史审稿记录等属性无处存储。

5. **权限模型无法落地**：§5.3.4权限矩阵定义了"审稿人/编辑部/作者"的操作权限，但没有User实体，权限判断的主体不明确。

**改进建议**：
1. 新增`User`实体，字段至少包括：userId、name、email、role（或多角色数组）、institution、researchAreas、createdAt等；
2. 新增`Author`实体或ReviewTask增加authorUserId字段，建立作者与稿件的关联；
3. 将现有`Reviewer`实体重命名为`ReviewAssignment`（审稿分配记录），消除"Reviewer"既是用户角色又是分配记录的命名歧义；
4. 明确用户角色模型：支持同一用户在不同场景下具备不同角色（如某用户在期刊A是编辑、在期刊B是审稿人），角色与任务的关联关系需明确定义；
5. 定义用户注册/创建流程（至少在P0中定义编辑部创建审稿人账号的流程）。

### Q6：终审建议规则引擎存在规则重叠与边界未覆盖——多条规则可同时触发，优先级未定义

| 项目 | 内容 |
|------|------|
| **问题编号** | Q6 |
| **问题级别** | 中等 |
| **问题类别** | 逻辑漏洞 |
| **PRD位置** | §4.3.4 终审建议规则引擎（Rule-1至Rule-7） |

**问题描述**：

PRD §4.3.4定义了7条终审建议规则，但存在以下逻辑问题：

1. **规则重叠，优先级未定义**：
   - **Rule-3**："多数推荐'接收'或'小修'，但有'大修'或'拒稿'" → "倾向接收但需讨论"
   - **Rule-7**："存在'接收'与'拒稿'并存" → "严重分歧需讨论"
   
   考虑场景：3位审稿人中2位推荐"接收"、1位推荐"拒稿"。此场景同时满足Rule-3（多数接收但有拒稿）和Rule-7（接收与拒稿并存）。系统应触发哪条规则？输出哪个建议结论？PRD未定义规则优先级。

2. **"多数"定义不精确**：
   - Rule-2："多数（≥2/3）推荐'接收'或'小修'"——2/3是按比例还是按绝对数量？3位审稿人中2位=67%≥2/3，满足；4位审稿人中2位=50%<2/3，不满足。但4位中3位=75%≥2/3，满足。这个定义在2位审稿人时（2/3=0.67，2位中2位=100%）总是满足，似乎过于宽松。
   - Rule-3："多数推荐"——此处"多数"是>50%还是≥2/3？与Rule-2的"多数"定义是否一致？

3. **2位审稿人的边界情况**：
   - 2位审稿人，1位"接收"、1位"拒稿"：50%对50%，谁是"多数"？Rule-3和Rule-7都可触发，但"多数"的定义不明确。
   - 2位审稿人，1位"接收"、1位"大修"：没有"拒稿"，Rule-7不触发；Rule-3的"多数"无法判定（50%不是多数）。

4. **仅1位审稿人时规则引擎如何执行**：
   - §4.6定义了"仅1位审稿人提交"的边界条件，终审建议标注"仅供参考"。但1位审稿人的推荐意见应该匹配哪条规则？如1位推荐"接收"，是Rule-1（全票接收）还是无法匹配任何规则？PRD未说明。

5. **Rule-4与Rule-7重叠**：
   - Rule-4："推荐意见分散（接收/大修/拒稿均有）" → "分歧需讨论"
   - Rule-7："存在'接收'与'拒稿'并存" → "严重分歧需讨论"
   
   "接收/大修/拒稿均有"必然包含"接收与拒稿并存"，因此Rule-4触发时Rule-7必然也触发。两者的建议结论不同（"分歧需讨论"vs"严重分歧需讨论"），系统应输出哪个？

**改进建议**：
1. 为规则引擎定义明确的**优先级顺序**（如Rule-7 > Rule-4 > Rule-6 > Rule-5 > Rule-3 > Rule-2 > Rule-1），高优先级规则先匹配，匹配后不再检查低优先级规则；
2. 统一定义"多数"：建议改为"≥半数"或"≥2/3"的明确比例，并在术语表中定义；
3. 补充2位审稿人和1位审稿人时的规则匹配逻辑（或定义这些场景不执行规则引擎，仅展示原始数据供编辑判断）；
4. 合并或区分Rule-4和Rule-7：如Rule-7专门处理"接收vs拒稿"的对立（最严重），Rule-4处理"接收+大修+拒稿三选分散"（严重但非对立），明确两者不重叠的触发条件。

### Q7：知识库冷启动缺乏种子数据策略——P0阶段功能价值无法体现，"新手审稿时间缩短"的核心承诺无法兑现

| 项目 | 内容 |
|------|------|
| **问题编号** | Q7 |
| **问题级别** | 中等 |
| **问题类别** | 用户体验风险 |
| **PRD位置** | §5.1 功能描述（P0阶段定位）+ §5.6 边界条件"知识库为空（冷启动）" + §5.2 用户故事US-R-08/US-R-09 |

**问题描述**：

PRD §5.1明确知识库在P0阶段"定位为基础架构搭建+最小可用版本"。§5.6冷启动处理为"检索结果为空时显示'暂无匹配案例，知识库将在审稿数据积累后逐步丰富'"。

但PRD §5.2用户故事US-R-08的核心价值主张是"新手审稿时间可从6小时缩短至2-3小时"，§5.1核心价值也声称"参考历史审稿案例和模板，降低审稿认知负担"。

问题在于：

1. **冷启动期间知识库价值为零**：P0上线初期，知识库完全为空。审稿人点击"参考知识库"只能看到"暂无匹配案例"。这不仅没有价值，还会造成**负向用户体验**——用户被引导使用一个空功能，产生"这个功能没用"的认知，后续即使数据积累也可能不再尝试。

2. **数据积累速度极慢**：知识库的入库触发条件是"审稿任务状态变更为已决策"（§5.3.1），即只有走完全流程的稿件才贡献数据。假设P0上线后第一个月有10篇稿件走完全流程，知识库仅有10条数据，对于"按学科+关键词检索"来说几乎不可能命中。在学术论文审稿中，学科领域和关键词组合极其多样，10条数据的命中率趋近于零。

3. **缺少种子数据策略**：PRD没有定义任何种子数据（seed data）的引入方案。用研报告§4.4已指出冷启动问题，但PRD仅承认问题存在，未给出实质解决方案。

4. **模板管理功能在冷启动期的价值也有限**：§5.3.2模板管理虽不依赖历史数据（有预设四维模板），但"模板与知识库关联"（使用统计、历史评分分布）在冷启动期无法提供有效信息。

**改进建议**：
1. **定义种子数据引入策略**：P0上线前预置一批匿名化的示例审稿意见（可从公开审稿平台如OpenReview获取并匿名化处理，或由编辑部专家撰写示例），覆盖主要学科领域，每学科至少20-30条，确保检索有基本命中率；
2. **冷启动期的功能降级**：知识库为空时，"参考知识库"入口不展示空检索结果，而是直接展示预设四维模板的评分指引和撰写示例（将模板的"评分指引"内容作为冷启动期的参考内容），避免负向体验；
3. **调整P0阶段价值预期**：将P0阶段知识库的成功指标从"检索命中率/使用率"调整为"归档数据完整率+检索功能可用性"，明确P0验证的是"架构和流程"而非"用户价值"；
4. **定义冷启动结束标准**：如"知识库条目数≥500条且覆盖≥5个学科领域"时视为冷启动结束，届时评估实际用户价值。

### Q8：退稿重审流程隐性突破P0边界——多轮审稿属P1功能但在P0中已部分实现

| 项目 | 内容 |
|------|------|
| **问题编号** | Q8 |
| **问题级别** | 中等 |
| **问题类别** | 边界冲突 |
| **PRD位置** | §1.5 边界声明 + §2.3.3 状态流转规则"已决策→审稿中" + §2.6 边界条件"退稿重审" + §7.4 异常处理流程场景C |

**问题描述**：

PRD §1.5边界声明明确"❌ 多轮审稿全流程支持（P1，P0仅预留流程扩展能力）"。

但PRD在以下位置实际实现了退稿重审功能：
- §2.3.3状态流转规则表：定义了`已决策 → 审稿中`（退稿重审，作者返修后重新审稿）的转换
- §2.6边界条件：定义了退稿重审的完整处理逻辑（编辑部发起返修重审→状态回退→可选原审稿人或新审稿人→审稿人可见返修稿标记和前次审稿意见）
- §7.4异常处理流程场景C：绘制了完整的退稿重审时序图
- 验收标准AC-T-10：定义了退稿重审的验收标准

这已经超出了"预留流程扩展能力"的范畴，实际实现了多轮审稿的核心流程。问题在于：

1. **退稿重审的数据模型未支持**：ReviewOpinion实体没有`round`（轮次）字段，无法区分第一轮和第二轮审稿意见。SummaryReport实体也没有轮次标识，一个任务多轮审稿会生成多份汇总报告，但taskId是1:1关系，数据结构不支持。

2. **退稿重审的状态管理复杂度被低估**：退稿重审涉及"返修稿上传→分配审稿人→重新审稿→重新汇总→重新决策"的完整流程，实质上是新一轮审稿。但PRD将其简化为"状态回退至审稿中"，未定义：
   - 返修稿如何上传和关联（ReviewTask.manuscriptFile是单文件，返修稿如何处理？）
   - 前次审稿意见如何展示给审稿人（全部展示？汇总展示？仅展示修改建议？）
   - 前次终审决策是否保留（状态回退后DECIDED状态的历史记录是否保留？）
   - 多轮退稿重审的上限（大修后重审→再大修→再重审，是否有限制？）

3. **与P1边界声明的矛盾**：边界声明说"多轮审稿全流程支持"是P1，但P0已实现了退稿重审的核心流程。如果P0只"预留扩展能力"，则应只定义数据结构中的轮次字段和状态机中的预留转换路径，而非实现完整的退稿重审流程。

**改进建议**：
方案一（缩减P0范围，推荐）：
1. 将退稿重审的完整流程移至P1，P0仅在ReviewOpinion和SummaryReport实体中预留`round`字段，在状态机中注释"已决策→审稿中（退稿重审）为P1预留转换，P0不实现"；
2. 删除§2.6中退稿重审的详细处理逻辑、§7.4场景C的流程图、AC-T-10验收标准；
3. P0阶段终审决策后流程结束，不支持回退。

方案二（保留退稿重审在P0，但完善设计）：
1. 修改边界声明，将"多轮审稿全流程支持（P1）"改为"多轮审稿全流程支持（P1），P0支持单次退稿重审"；
2. 在ReviewOpinion和SummaryReport实体中增加`round`字段（Integer，默认1）；
3. 在ReviewTask中增加`manuscriptFileRevised`字段（返修稿文件路径）；
4. 明确退稿重审仅支持一次（DECIDED→REVIEWING仅允许一次，防止无限循环）；
5. 完善退稿重审的数据流定义（前次意见如何关联、展示规则等）。

### Q9：审稿人拒邀/超时的降级策略不完善——无最大重试次数限制，可形成无限循环

| 项目 | 内容 |
|------|------|
| **问题编号** | Q9 |
| **问题级别** | 中等 |
| **问题类别** | 边界遗漏 |
| **PRD位置** | §2.3.3 状态流转规则 + §2.6 异常状态处理 |

**问题描述**：

PRD定义的拒邀/超时处理逻辑为：
1. 审稿人拒绝邀请 → 通知编辑 → 编辑重新分配新审稿人 → 任务状态不变
2. 全部审稿人拒绝/超时 → 任务回退至"待分配" → 通知编辑重新分配

问题在于：

1. **无最大重试次数限制**：编辑可以无限次重新分配审稿人。如果某稿件因学科冷门或主题争议大，审稿人反复拒邀，编辑每次只能逐一重新邀请。系统不会在多次失败后升级处理（如通知主编、标记为"分配困难"稿件、建议改变审稿策略等），可能导致编辑陷入"拒绝→重新分配→再拒绝"的循环，大量消耗编辑时间。

2. **超时后"重新分配"的审稿人截止日期如何设置**：§2.6说编辑可选择"延期（设置新截止日期）/重新分配/强制提前汇总"，但重新分配的新审稿人的截止日期从何时起算？是从原任务截止日期起算（可能已经过期）还是从重新分配时起算（新设7天后）？PRD未定义。

3. **邀请超时后的审稿人状态管理**：§2.6说"邀请超时未响应"时"标记该审稿人'邀请超时'"，但该审稿人在审稿人库中的状态是否变化？是否影响后续被邀请的概率？是否记录拒邀/超时次数用于后续审稿人画像（P1功能）？P0阶段至少应记录拒邀和超时事件。

4. **"全部超时"回退到待分配后的二次分配流程未定义**：任务从REVIEWING回退到PENDING后，编辑重新分配审稿人时，之前的审稿人分配记录（Reviewer/ReviewAssignment记录）如何处理？是保留为历史记录还是删除？如果保留，新分配的审稿人与旧记录的关系如何？如果部分审稿人已提交意见后其他全部超时，任务回退后已提交的意见如何处理？

5. **缺少超时的自动升级机制**：审稿超时后仅通知编辑，但如果编辑也未及时处理（如编辑出差、休假），任务会无限期停留在OVERDUE状态。没有自动升级到主编或备用编辑的机制。

**改进建议**：
1. 定义最大重试次数（如3次），超过后系统标记该稿件为"分配困难"，通知编辑部上级或主编介入；
2. 明确重新分配的新审稿人截止日期规则（建议：从重新分配时起算，至少7天后）；
3. 在Reviewer/ReviewAssignment实体中增加`attemptCount`字段，记录该审稿人被分配的总次数；
4. 明确任务回退到PENDING后历史分配记录的处置策略（建议保留为历史记录，新增分配记录通过attemptCount区分轮次）；
5. 定义超时自动升级机制：审稿超时后若编辑48小时未处理，自动通知备用编辑或主编。

### Q10：用研痛点P1"任务分配效率低"的解决方案不完整——PRD仅提供手动搜索，未实现任何效率提升工具

| 项目 | 内容 |
|------|------|
| **问题编号** | Q10 |
| **问题级别** | 中等 |
| **问题类别** | 用户体验风险 |
| **PRD位置** | §2.3.2 任务分配 + 用研报告§2 痛点P1 + 附录A 追溯矩阵 |

**问题描述**：

用研报告§2痛点P1描述："编辑部分配审稿任务时，缺乏智能匹配工具，主要依赖编辑个人经验、人脉记忆和手动查找。审稿人信息散落在通讯录、往期审稿记录、学术数据库等多处，编辑需要逐一筛选、邮件邀请、等待回复，流程冗长且成功率不稳定。从稿件分配到审稿人确认接受，平均耗时3-7天。"

PRD §2.3.2任务分配的解决方案为：
- 手动分配：编辑从系统审稿人库中搜索和选择审稿人
- 批量分配：一次选择多位审稿人，分别设置截止日期
- 系统自动发送邀请通知（站内消息+邮件）

对比用研痛点和PRD解决方案：

1. **"缺乏智能匹配工具"未解决**：用研痛点明确指出"缺乏智能匹配工具"是核心问题，但PRD仅提供"按姓名/学科/关键词搜索"的手动搜索功能，没有任何匹配推荐能力。搜索≠匹配——编辑仍需自己判断谁合适，只是从"散落各处"变为"在一个库中搜索"，效率提升有限。

2. **"审稿人信息散落"部分解决**：PRD将审稿人集中到系统审稿人库中，解决了信息散落问题。但由于P0不定义User实体（见Q5），审稿人库中到底有哪些信息（学科领域、研究方向、历史审稿记录等）未定义，编辑搜索时能用的筛选维度可能很有限。

3. **"平均耗时3-7天"难以显著缩短**：PRD通过"批量分配+自动通知"可减少邮件往返时间，但审稿人确认接受的等待时间（邀请有效期默认3天）不受影响。如果审稿人拒绝，重新分配又需3天邀请有效期。最坏情况下（第一次分配全部拒绝→重新分配→部分接受），耗时仍可达6天以上，与用研报告的3-7天相比改善有限。

4. **追溯矩阵声称解决了P1**：附录A追溯矩阵中"任务分配→P1任务分配效率低"，但实际上PRD的方案仅部分解决了P1的信息散落和通知效率问题，核心的"匹配效率低"未解决。

**改进建议**：
1. 在P0中增加**轻量级的审稿人推荐**功能：基于稿件关键词与审稿人研究方向的标签匹配，在编辑搜索时按匹配度排序展示审稿人列表（非AI推荐，仅标签匹配排序），显著降低编辑筛选成本；
2. 在User/Reviewer实体中定义审稿人的研究方向标签（researchAreas），支持与稿件关键词的自动匹配计算；
3. 调整追溯矩阵：将P1的解决程度标注为"部分解决"（信息集中化+通知自动化），明确"智能匹配推荐"属P1功能，P0仅提供标签匹配排序；
4. 或调整P1痛点描述，将"缺乏智能匹配工具"拆分为"信息散落"（P0解决）和"缺乏智能推荐"（P1解决），使追溯矩阵更准确。

### Q11：双盲模式下稿件文件匿名化责任归属不明——编辑部"负责隐去"缺乏操作定义和校验机制

| 项目 | 内容 |
|------|------|
| **问题编号** | Q11 |
| **问题级别** | 中等 |
| **问题类别** | 安全风险 |
| **PRD位置** | §2.3.1 任务创建-业务规则 + §2.7 验收标准AC-T-13 |

**问题描述**：

PRD §2.3.1业务规则第4条："双盲模式下，稿件文件中的作者信息由编辑部负责隐去"。§2.7验收标准AC-T-13："双盲模式下，审稿人不可见作者信息，作者不可见审稿人身份"。

问题在于：

1. **"由编辑部负责隐去"缺乏操作定义**：
   - 编辑部如何隐去？手动编辑PDF？使用工具？上传已匿名化的版本？
   - PDF文件中的作者信息可能出现在：标题页、页眉页脚、文件元数据（PDF属性中的作者字段）、致谢部分、基金资助信息、正文中自引等。手动编辑PDF很容易遗漏。
   
2. **无系统校验机制**：
   - 系统不检查上传的PDF是否已充分匿名化。如果编辑忘记删除PDF元数据中的作者信息，审稿人可通过"查看PDF属性"直接获取作者姓名。
   - 验收标准AC-T-13要求"双盲模式下审稿人不可见作者信息"，但没有任何机制保障这一点——完全依赖编辑的手动操作。

3. **责任归属与追责机制不明**：
   - 如果审稿人通过稿件文件中的线索识别出作者，责任在谁？编辑（未充分匿名化）？系统（未提供校验）？审稿人（不应主动识别）？
   - PRD未定义双盲泄露的事件处理流程。

4. **单盲模式下的信息隔离未定义**：
   - 单盲模式下审稿人可见作者信息，但作者不可见审稿人身份。审稿人可见哪些作者信息（姓名/单位/邮箱？）未定义。

**改进建议**：
1. 定义双盲稿件文件匿名化检查清单（checklist），编辑上传双盲稿件前需逐项确认：
   - ☐ 标题页已移除作者信息
   - ☐ 页眉/页脚已移除作者信息
   - ☐ PDF元数据（作者字段）已清除
   - ☐ 致谢部分已移除或匿名化
   - ☐ 基金资助信息已移除或匿名化
   - ☐ 正文自引已改为第三人称表述
2. 系统自动检查PDF元数据中的作者字段，如有值则警告编辑；
3. 定义双盲泄露事件处理流程：审稿人发现身份线索→通知编辑部→编辑部处理（更换匿名稿件/更换审稿人）；
4. 明确单盲模式下审稿人可见的作者信息范围。

### Q12：分歧标注规则未考虑审稿人数量和异常分布——极端情况下标注失真

- ≤1 → 🟢基本一致

问题在于该规则仅基于极值差，未考虑审稿人数量和分数分布：

1. **5位审稿人中1位异常值**：4位给5分、1位给1分，max-min=4→严重分歧。但实际上4/5的审稿人一致认为优秀，仅1位异常。标注"严重分歧"会误导编辑认为该维度存在广泛争议，而实际可能只是1位审稿人评分偏差。

2. **2位审稿人评分差2分**：1位给5分、1位给3分，max-min=2→明显分歧。但2位审稿人的意见差异在学术审稿中非常常见，标注"明显分歧"可能过度预警。

3. **"全部1分"vs"全部5分"**：两种场景max-min均为0→基本一致（🟢）。但全1分意味着稿件极差，全5分意味着稿件优秀，两者在终审建议中应有不同表述。分歧标注虽不负责区分好坏，但在"一致点分析"中应体现差异——全1分的"一致"是"一致认为差"，全5分的"一致"是"一致认为好"。当前PRD的一致点分析（§4.3.3报告模板）仅展示"三位审稿人一致认为..."，未区分正向一致和负向一致。

4. **2位审稿人都给3分**：max-min=0→基本一致。但3分="一般"，"基本一致"的绿色标记可能让编辑误以为稿件质量尚可，而实际是"一致认为一般"。

**改进建议**：
1. 分歧标注增加审稿人数量权重：5位审稿人中4位一致+1位异常时，标注"个别分歧"而非"严重分歧"；
2. 在分歧标注旁增加分布信息：如"4/5位评分5分，1/5位评分1分"，让编辑直观判断是广泛分歧还是个别异常；
3. 在一致点分析中区分"正向一致"（高分一致）和"负向一致"（低分一致），如"✅ 三位审稿人一致认可写作水平（平均4.3分）"vs"⚠️ 三位审稿人一致认为研究方法存在不足（平均2.0分）"；
4. 考虑引入标准差作为辅助指标：max-min相同但标准差不同的分布，分歧程度不同。

## 四、总体评审意见

### 4.1 优点总结

1. **结构完整、逻辑清晰**：PRD按功能模块组织，每个功能包含功能描述、用户故事、功能拆解、输入输出定义、交互逻辑、边界条件、验收标准七大要素，结构化程度高，便于技术团队理解和实施。

2. **用研追溯性强**：附录A提供了完整的"P0功能→用研痛点"追溯矩阵，每个功能拆解项均可追溯到用研报告的具体痛点描述，设计依据可追溯。

3. **状态机设计基本完整**（正常路径）：正常审稿流程的状态流转（PENDING→ASSIGNED→REVIEWING→SUBMITTED→SUMMARIZED→DECIDED）定义清晰，触发条件和操作者明确。

4. **数据结构设计详实**：7个核心实体定义了完整的字段、类型、约束和关系，子结构（Dimension、DimensionScore、Suggestion等）定义细致，为技术设计提供了良好基础。

5. **边界条件考虑较充分**：每个功能模块都列出了边界条件/异常处理表，涵盖了常见异常场景（拒邀、超时、并发、草稿丢失等），体现了较好的产品思维。

6. **双盲保护意识到位**：在多处（任务创建、意见展示、知识库归档）考虑了双盲保护，验收标准中包含安全测试项，体现了隐私保护意识。

7. **差异化定位明确**：将"审稿意见汇总对比"和"审稿知识库"作为核心差异化功能，与竞品分析结论一致，战略方向正确。

### 4.2 核心问题总结

1. **状态机异常路径不完整（Q1）**：REVIEWING→PENDING转换缺失，可能导致任务卡死。退稿重审时历史数据处理未定义。这是阻断性缺陷。

2. **跨模板维度对齐逻辑根本性错误（Q2）**：以模板内唯一的dimensionId做跨模板对齐，将导致汇总报告数据错乱。虽然可通过强制统一模板规避，但PRD当前方案是错误的。

3. **知识库匿名化方案不足以保障双盲安全（Q3）**：关键词过滤无法覆盖学术文本中的语义级身份线索，且审核流程存在逻辑矛盾（不可逆vs退回修改）。安全合规风险高。

4. **并发数据一致性未定义（Q4）**：多审稿人并发提交时"全部已提交"状态判定存在竞态条件，可能导致任务卡死。高频场景，影响面大。

5. **用户实体缺失（Q5）**：数据模型无User实体，用户身份、角色、账号管理无定义，技术设计无法落地。

6. **退稿重审隐性突破P0边界（Q8）**：边界声明将多轮审稿归为P1，但PRD实际实现了退稿重审完整流程且数据模型不支持，产生矛盾。

7. **终审规则引擎存在逻辑冲突（Q6）**：多条规则可同时触发但优先级未定义，"多数"定义不精确，边界场景未覆盖。

### 4.3 评审结论

**需重大修改**

PRD整体框架和专业度较高，但存在3项严重问题（Q1状态机缺陷、Q2维度对齐错误、Q3匿名化安全风险）和2项严重数据模型问题（Q4并发一致性、Q5用户实体缺失），这些问题将直接阻断技术设计或导致上线后安全/稳定性事故。必须修改后重新评审。
